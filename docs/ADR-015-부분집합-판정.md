# ADR-015 — 부분집합 판정: 넓은 양식이 좁은 양식을 삼킨다

날짜: 2026-08-19 · 상태: 확정 · 관련: [ADR-010](ADR-010-프로파일-라우팅-규약.md) · [ADR-002](ADR-002-파싱-원칙.md)

Recognition은 필수 헤더가 **전부 있는지**로 프로파일을 고른다(`headerMatch: "all"`).
이 규칙에는 구멍이 하나 있고, 좁은 양식을 더하는 순간 반드시 드러난다.

---

## 문제 — 실측

원가표 프로파일(`cost-master@1`)을 만들자마자 **매출 파일이 원가표로 100% 판정됐다.**

```
원가표          상품번호 · 상품명 · 모델명 · 원가 · 배송비 · 카테고리 · Model    (7열)
B2B_매출정리    … 위 7열을 **전부 포함하는** 101열 …
```

두 시트가 같은 워크북 안에 있고, 매출 시트의 열 집합이 원가표 열 집합의
**상위집합**이다. `headerMatch: "all"`은 「필수 헤더가 다 있다」만 보므로 넓은 표는
좁은 표의 조건을 **언제나** 만족한다. 신뢰도도 1.0으로 같아 순위로도 안 갈린다.

★ **필수 헤더를 아무리 고쳐도 안 갈린다.** 원가표에서 고를 수 있는 어떤 열 조합도
매출 파일에 이미 들어 있기 때문이다. 이건 프로파일을 잘못 쓴 게 아니라 판정 규칙의
구조적 성질이다.

## 버린 길 — 열 수 제한

「필수 헤더 다 있고 **총 열 수가 N 이하**일 때만」이 제일 먼저 떠오르는 답이고,
그래서 적어 둔다. **버렸다.**

「열 추가는 공짜」라는 성질이 깨진다. 지금은 사용자가 자기 원가표에 메모 열을
하나 더해도 그대로 들어가는데, 열 수로 막으면 그 순간 「맞는 양식 없음」이 된다.
사용자 입장에서 원인을 짐작할 수 없는 실패다 — 늘어난 열은 우리가 **안 읽는**
열인데도 판정을 뒤집는다.

## 결정 — **의미로 막는다**: `forbiddenHeaders`

`recognitionRules`에 선택 항목을 둔다. 하나라도 파일에 있으면 그 프로파일은
후보에서 **빠진다**.

```json
"recognitionRules": {
  "requiredHeaders": ["상품번호", "상품명", "원가"],
  "headerMatch": "all",
  "forbiddenHeaders": ["주문 번호", "주문번호", "상품주문번호", "주문일자", "결제일"]
}
```

고르는 기준은 **grain의 모순**이다. 원가는 상품 단위라 주문 번호·주문일자·결제일이
**있을 수 없다.** 「이 파일에는 없더라」가 아니라 「이 종류의 파일에는 있으면 안
된다」로 골라야 한다 — 앞의 방식으로 고르면 다음 사용자의 파일에서 무너진다.

열 수 제한과 달리 이 규칙은 **읽지 않는 열이 늘어나는 것에 무관하다.** 카테고리를
더하든 메모를 더하든 원가표는 원가표로 남고, 주문 번호가 붙는 순간에만 아니게 된다.
그 순간은 실제로 다른 종류의 파일이 된 순간이다.

## 언제 쓰나

**좁은 양식을 더할 때마다 확인한다.** 새 프로파일의 필수 헤더 집합이 이미 있는
어떤 프로파일의 부분집합이면 — 또는 사용자 워크북의 넓은 시트에 통째로 들어가면 —
`forbiddenHeaders` 없이는 갈리지 않는다.

확인 방법은 판정을 직접 돌려 보는 것이다. `analyzeImport`가 전 시트를 훑으므로
워크북 하나로 충돌이 바로 보인다. `tests/reference-import.test.ts`가
「`B2B_매출정리`는 원가표가 아니다」를 그렇게 고정해 뒀다.

## 안 하는 것

**행 내용은 안 본다.** 값을 보고 갈라야 하는 자리가 분명히 있지만(§20의 «값 신호»),
Recognition은 헤더만 보고 끝나야 파일을 열기 전에 후보를 좁힐 수 있다. 값까지
봐야 갈리는 충돌이 나오면 그건 이 ADR이 아니라 §20 확인 질문의 자리다 — 사람에게
묻는다.
