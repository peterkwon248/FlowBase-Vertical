# ADR-009 — 회계 정책: 인식 기준 · 부호 · 배분 잔차 · 대사 키

날짜: 2026-08-12 · 상태: 확정 (사용자 결정) · 관련: [ADR-002](ADR-002-파싱-원칙.md) · [ADR-004](ADR-004-되돌리기-의미론.md) · [ADR-006](ADR-006-source-key-전략.md)

손익 숫자가 **언제·어떤 부호로·어디에 귀속되는지**를 정한다. 세션 3의 손익 엔진과
목업 이식이 전부 이 문서를 참조한다. 여기서 정하지 않으면 화면마다 다른 답이 나온다.

---

## ① 손익 인식 기준 — 발생주의, 소급 없음

**대시보드 순이익 = 주문일(`ordered_at`) 기준.**

클레임(취소·반품·환불)은 **발생일(`claimed_at`)에 음수로 반영**한다.
**원거래 월로 소급하지 않는다.**

```
7월: 주문 1,000만원                        → 7월 매출 1,000만원
8월: 그중 7월 주문 200만원이 반품됨         → 8월에 −200만원
                                              7월은 그대로 1,000만원
```

### 왜 소급하지 않는가

**확정된 과거는 흔들리지 않아야 한다.** 소급하면 지난달 손익이 이번 달에 바뀐다.
사용자가 7월 마감을 보고 판단을 내렸는데 8월에 7월 숫자가 달라지면, 그 판단의
근거가 사후에 사라진다. 세금 신고·정산 대조도 이미 끝난 뒤다.

대가는 명확하다 — **월별 손익이 그 달의 "진짜" 원가를 반영하지 않는다.** 반품이 많은
달은 실제보다 나빠 보이고, 그 반품의 원인이 된 매출은 이미 지난달에 좋게 잡혔다.
이건 감출 수 없는 구조적 한계이고, 화면이 클레임 금액을 **따로 보여줘서** 사용자가
그 차이를 읽을 수 있게 한다.

### 두 화면의 관점 분업

| 화면 | 관점 | 기준 날짜 | 답하는 질문 |
|---|---|---|---|
| **대시보드 · 손익** | 발생주의 | `fact_order.ordered_at` · `fact_claim.claimed_at` · `fact_ad_spend.spent_on` | "이번 달 장사를 잘했나" |
| **정산** | 현금주의 | `fact_settlement.pay_out_on` | "돈이 언제 얼마 들어오나" |

**두 화면의 숫자는 일치하지 않는다. 그게 정상이다.** 마켓은 이번 달 주문을 다음 달에
정산하고, 정산 주기도 마켓마다 다르다. 화면은 이 차이를 버그처럼 보이게 두지 않고
관점이 다르다는 것을 명시한다 (CLAUDE.md "상품별 손익의 합은 회사 순이익이 아니다"와
같은 종류의 정직함이다).

`fact_settlement`는 **손익 인식에 쓰지 않는다.** 현금 관점 전용이다.

## ② 부호 규약 — 저장은 양수, 의미는 타입이 정한다

**모든 fact 금액 컬럼은 양수로 저장한다.** 차감인지 가산인지는 **행의 타입**이 정한다.

```
fact_claim.amount = 200000, claim_type = 'REFUND'
  → 저장은 +200000
  → 손익 계산기가 claim_type을 보고 뺀다
```

### 왜 부호를 데이터에 넣지 않는가

마켓 파일마다 부호 관습이 다르다. 어떤 파일은 반품을 `-200,000`으로, 어떤 파일은
`200,000`으로 적고 컬럼 이름으로만 구분한다. 부호를 그대로 저장하면 **같은 사실이
마켓마다 다른 부호로 쌓이고**, 합계는 조용히 틀린다 (헌장 A-5).

타입이 정하면 규칙이 한 곳에 모인다 — 손익 계산기다. `SUM(amount)`이 무엇을 의미하는지
보는 사람이 컬럼만으로 알 수 있고, 부호 실수가 SQL 집계에 섞이지 않는다.

### 정규화 지점 — 어디서 절대값을 취하는가

파일의 음수 입력은 **절대값 + 타입**으로 정규화한다.

**단, 값 수준 정규화(`normalization/value.ts`)에서는 하지 않는다.** 그 단계는 셀이
무슨 의미인지 모른다 — `-500`이 반품액인지 온도인지 잔액 변동인지 구분할 수 없고,
거기서 `abs()`를 걸면 정당한 음수까지 뭉갠다.

**절대값은 Mapping 단계에서 취한다.** 그 필드가 금액이라는 것은 프로파일이 알고 있고
(`fieldMappings[].kind`), 타입 컬럼도 거기서 함께 채워진다. 구현은
`src/core/accounting/sign.ts`의 `toMagnitude()`이며, 프로파일이 금액 필드에
`signPolicy: "magnitude"`를 선언한 경우에만 적용된다.

> **미결**: 스키마에 `CHECK (amount >= 0)`을 넣을지는 마이그레이션 결정이라
> [대기목록](다음-마이그레이션-대기목록.md)에 올렸다. 스키마 LOCK(헌장 규칙 1) 때문에
> 001을 고치지 않는다.

## ③ 배분 잔차 — 최대 항목에 귀속

광고비·고정비를 여러 항목에 정수 안분할 때 남는 **잔차는 금액이 가장 큰 항목에
전부 귀속**한다.

```
고정비 100,000원을 3개 상품에 매출 비중 (1:1:1)으로 안분
  → 33,333 · 33,333 · 33,333 = 99,999
  → 잔차 1원을 최대 항목에 → 33,334 · 33,333 · 33,333
```

### 왜 최대 항목인가

원 단위 정수이므로(스키마 `INTEGER`, 부동소수 금지) 잔차는 **반드시 생긴다.**
버리면 합이 안 맞고, 나누면 다시 잔차가 생긴다.

최대 항목에 몰아주는 이유는 **상대 오차가 가장 작기 때문**이다. 1원을 3,000원짜리
항목에 얹으면 0.03%, 30원짜리에 얹으면 3.3%다. 그리고 규칙이 결정적이라 같은 입력이
항상 같은 답을 낸다 — 무작위 배분이나 "첫 항목" 규칙보다 재현 가능하다.

동점이면 **먼저 오는 항목**이 받는다 (인덱스 순). 결정성을 위해서다.

### 불변식 — 이건 테스트가 강제한다

```
배분 결과의 합 === 원금          (항상, 예외 없이)
```

`tests/accounting.test.ts`의 속성 테스트가 무작위 입력 수백 건으로 이걸 확인한다.
합이 안 맞는 배분은 **상품 기여이익의 합이 채널 기여이익과 어긋나게** 만들고,
그 어긋남은 화면에서 원인 불명의 몇 원 차이로 나타난다.

## ④ 대사 키 — `recon_key = (connection_id, doc_type, 기간)`

`recon_ack.recon_key`의 형식을 정한다.

```
recon_key = "{doc_type}:{period_start}:{period_end}"
UNIQUE (connection_id, recon_key)   ← 스키마에 이미 있다
```

`connection_id`는 컬럼으로 이미 분리돼 있으므로 키 문자열에 다시 넣지 않는다.

### 날짜 경계는 KST 자정 — 파서 출력 시점에 확정한다

기간 경계는 **KST(UTC+9) 자정**이다. 그리고 그 확정은 **파서가 값을 내놓는 시점**에
끝난다 — 이후 단계는 이미 확정된 날짜 문자열만 본다.

이건 [ADR-002](ADR-002-파싱-원칙.md)의 연장이다. 그 문서가 "날짜는 UTC 게터로 읽는다"고
정한 이유와 같다: 실행 기기의 시간대에 따라 답이 달라지면 안 된다. 노트북을 들고
여행하면 7월 31일 주문이 8월로 넘어가는 일이 실제로 생긴다.

따라서:

- 파서는 날짜를 `YYYY-MM-DD` 또는 `YYYY-MM-DDTHH:MM:SS` 문자열로 확정해 내놓는다
  (이미 그렇게 한다 — `normalization/value.ts`의 `parseDateLike`)
- 기간 비교는 **문자열 비교**로 한다. `Date` 객체를 만들지 않는다 — 만드는 순간
  실행 기기의 시간대가 끼어든다
- 대사는 **원본 대 원본**이다 (헌장 규칙 3). 조정으로 불일치를 일치로 만들 수 없다

## 재검토 트리거

1. 사용자가 "반품을 원거래 월로 소급해서 보고 싶다"고 요구 → ①을 **화면 옵션**으로
   푼다. 저장 구조는 그대로다(발생일이 사실이다). 소급은 조회 시 재계산이다
2. 마켓이 정산 파일에 손익 판정에 필요한 유일 정보를 담기 시작 → `fact_settlement`의
   손익 사용 금지 조항을 재검토
3. 잔차 배분이 특정 상품에 계속 몰려 사용자가 문제 제기 → 최대잔차법(Hare) 검토.
   단 결정성은 유지한다
4. 다국가·다시간대 지원 → ④의 KST 고정을 라이브러리 설정으로 승격
