## 문제 — 사용자가 앱의 정체를 다시 말했다

> *"나는 지금 정산 대시보드를 위한 **에어테이블+메타베이스**를 만들고 싶은 거 같아."*
>
> *"가져오기 기록 ← 이게 문제야. 가져오기는 모든 파일을 가져올 수 있는 곳이고,
> 가져오기 기록은 **가져온 파일들이 전부 저장되는 공간** 느낌으로 변경해야겠어.
> 지금은 batch들만 가져오잖아? 그러면 **가져온 파일의 원문 데이터 테이블을 어떻게 봐?**"*
>
> *"내 필드 ← 사실상 유명무실한 거고, 필드 매핑은 있지만 **원본 파일의 데이터를
> 보여주는 테이블은 없고, 각종 선택된 데이터만 시각화하는 기능도 없어.**"*
>
> *"**데이터 묶음을 만들기 전까지는 시각화가 되어선 안 됨.** 앱이 요구하는 전용
> 필드를 갖춘 데이터 묶음이 만들어져야지만 시각화가 가능해야 함."*
>
> *"대시보드의 경우 지금 고정형임. … **입구부터 설계가 잘못된 건물 같음.**"*

### 실측 — 불만이 가리키는 자리는 전부 코드로 확인된다

| 사용자가 겪은 것 | 코드 |
|---|---|
| 원가 파일이 기록에 안 나온다 | `repository.ts:2515` — 기록은 `FROM batch b`뿐. `run-reference.ts`에 `openBatch` 0건 |
| 원본 표를 다시 못 본다 | `import-grid`가 적재 **전에만** 그린다. 파싱된 표를 저장하는 코드 0건 |
| 「내 필드」가 유명무실 | `Template.tsx:5540` 설명 문단 + 무동작 [필드 추가](`vals.ts:849 addCf: () => {}`) |
| 선택한 데이터만 시각화 못 함 | `collection_batch.batch_id REFERENCES batch(id)` — 묶음이 **batch만** 묶는다 |
| 입구가 출력이다 | 사이드바 첫 항목이 「손익 대시보드」. 아무것도 안 넣어도 숫자가 뜬다 |

### 왜 「원가도 batch를 쓰게 한다」로 풀면 안 되나

가장 쉬운 길이고 **틀린 길이다.** `batch.connection_id`가 `NOT NULL`이라 채널 없는
파일마다 유령 연결을 만들어야 하고(`App.tsx:1183-1189`가 이미 그 이유를 적어 뒀다),
그러면 아래 결정 1을 나중에 얹기가 **더** 어려워진다.

batch는 제 일을 하고 있다 — **사실 적재 장부**다. append-only이고 되돌리기 단위이며
연결에 매달린다(LOCK 2). **문제는 「가져오기 기록」 화면이 batch를 장부로 착각한 것이다.**

## 조사 — 버린 길 둘

### ✗ (a) 사용자가 파일을 「광고 / 원가 / 정산」 3부류로 골라 등록한다

사용자가 후보로 올린 안이다. 버린다 — **사용자에게 분류를 시키는 순간 사용자가
틀릴 수 있게 된다.** 그리고 프로파일 판정이 이미 그 일을 한다: 2026-08-20 실측에서
앱이 13MB 단가표를 스스로 「상품별 단가표(카드형) 100%」로 맞혔다. 사람이 할 일은
**앱이 헷갈릴 때 답하는 것**(§20 확인 질문)이지 매번 분류하는 게 아니다.

덤: docType은 3종이 아니라 **4종**이다 — `order | settlement | ad | cost`
(`coverage/index.ts:34`). 주문이 빠지면 수량·매출이 안 나온다. 3부류로 받는 UI는
그 사실부터 틀린다.

### ✗ (b) 대시보드가 묶음의 성격에 따라 통째로 달라진다

사용자 본인이 *"사실상 어려움"*이라고 판단했고 **동의한다.** 손익 3층은 도메인
지식이고 **그게 이 제품의 값**이다. Metabase처럼 아무 차트나 그리게 하면 그 값이
사라진다. 그리고 목업(디자인 정본)이 고정 레이아웃이다.

### ✓ 셋째 길 — §22가 이미 그 기계를 만들어 놨다

```
metric → requires[docType]          §22-1
```

> **`required` 필드를 두지 않는다.** 서류가 강요하는 것이 아니라 지표가 요구한다.
> *광고를 하지 않는 셀러에게 `ad`는 영원히 잠긴 지표일 뿐이지 결핍이 아니다.*

대시보드는 **고정으로 두고**, 각 지표가 자기 입력을 선언하고, 갖춰진 것만 열린다.
유연함을 만드는 것이 아니라 **못 여는 지표를 안 그리는 것**으로 흉내낸다.

## 결정

### 결정 1 — 파일이 척추다. 통을 세운다

넣은 파일은 **전부** 한 줄. batch는 그 줄에 달리는 「이 파일이 무엇이 됐나」 중 하나다.

```
파일 접수 장부(통)  ← 척추
  ├ 얕게: 파일 메타 + 결과(batch / cost_history / pending_cost / 실패)
  └ 깊게: 파싱된 표 보관 → 아무 파일이나 표로 다시 본다
```

얕은 층이 [작업-상태](작업-상태.md)의 「다음 손 ①」, 깊은 층이 「② 원본 보관층」이다.
**둘은 따로 할 일이 아니라 같은 척추의 깊이 두 단계다.**

### 결정 2 — 묶음이 시각화의 자격을 갖는다 ✅ 확인됨 (2026-08-21)

**§22의 판정 단위를 「연결」에서 「묶음」으로 올린다.** 지금 §22는 연결별 보유
docType을 본다. 묶음별로 올리면 사용자의 *"데이터 묶음을 만들기 전까지는 시각화가
되어선 안 됨"* 이 **구조가 된다.**

```
묶음 「2026년 7월 결산」
  order      ✅   settlement ✅   cost ⚠ 236/261   ad ❌ 없음
  → 열림: 매출 · 수량 · 수수료 · 매입원가 · 상품 기여이익
  → 잠김: 채널 기여이익  ← 광고비를 넣으면 열립니다
```

요건을 못 갖춘 묶음은 **「0원」을 그리는 게 아니라 문이 안 열린다.**

### 결정 3 — 대시보드 하드코딩은 유지한다

위 (b) 참조. 손익 3층은 제품의 값이므로 일반화하지 않는다.

### 결정 4 — 입구 순서를 뒤집는다

```
지금   현황(대시보드·정산·상품·진단·비용·주문) → 연동 → 기준
       ↑ 출력이 입구에 있다. 안 넣어도 숫자가 뜬다

앞으로 ① 가져오기 → ② 통(원본 표를 다시 본다) → ③ 묶음(요건 확인) → ④ 대시보드
```

### 결정 5 — API는 새 층이 아니라 **통의 새 입구**다

```
파일 ─┐
URL  ─┼→ 통 → 필드 매핑 → Fact → 묶음 → 대시보드
API  ─┘   ↑ 여기만 다르다. 아래는 전부 같다
```

API가 주는 것도 결국 행의 집합이고, 파일이 주는 표와 같은 물건이다. 통이 「어디서
왔나」만 기록하고 그 아래는 손대지 않는다. **그래서 지금 파일로 만드는 것이 그대로
API에서도 돈다** — 통 없이 API를 붙이면 그때 또 따로 만들어야 한다.

어휘는 그대로 **연결 / 가져오기 / batch**다 (LOCK 10 — 「동기화」 금지).

### 결정 6 — 용어를 셋으로 가른다

| 이름 | 무엇 | 앱이 뜻을 아나 |
|---|---|---|
| **표** | 통에 담긴 파일 원본 그리드 | ❌ 모른다 |
| **묶음** | 무엇을 합쳐 볼 것인가 + 시각화 자격 | ⚠ docType 단위로만 |
| **Fact** | 매핑을 통과해 손익이 아는 데이터 | ✅ 안다 |

**「테이블」이라 부르지 않는다** — 셋 다 가리킬 수 있어서 회의에서 서로 다른 것을
말하게 된다. 사용자 본인이 *"이걸 테이블이라고 불러야 하나? 용어는 긴가민가한데"*
라고 물은 자리다.

### ★ 뒤집는 것 하나 — §22-3 ①「원가는 «전부»여야 열린다」 ★

확인 ②(「열되 부족분을 말한다」)는 **§22-3 ①과 정면으로 부딪힌다.** 명시하지 않으면
번복이 아니라 사고가 되므로(`CLAUDE.md` 문서 우선순위 사슬 1) 여기와 §22 **양쪽에**
적는다. §22 쪽에도 이 ADR을 가리키는 줄을 넣었다.

```
§22-3 ① (2026-08-14)   원가가 전부 갖춰져야 매입원가·기여이익이 열린다
확인 ②   (2026-08-21)   열되 부족분을 말한다 — 잠기는 것은 «아예 없을 때»뿐이다
```

**근거는 살아 있고 처방만 바뀌었다.** 「절반만 입력된 원가로 그리면 이익이 부풀려진다」는
여전히 참이다. 답이 «안 보여준다»에서 **«보여주고 그 자리에서 말한다»**로 바뀐 것이다.

★ **실측 — 코드 안에 이미 두 답이 있었다 (2026-08-21 · 이 저장소 · `npm run state` 계열 조회)** ★

같은 사실에 두 층이 다른 답을 내고 있다. 따름 조건 5가 금지한 바로 그 모양이다:

```
커버리지 (§22)   src/core/coverage/load.ts   costed === skus 여야 cost 보유
                 → 236/261이면 «매입원가 잠김» · «상품 기여이익 잠김»
손익     (3층)   src/core/profit/gaps.ts     cogs-missing 「일부 미입력」
                 → 열고 계산한 뒤 «그만큼 기여이익이 부풀어 있다»를 말한다
```

**손익 쪽이 이미 확인 ②대로 동작하고 있었다.** 그래서 이 번복은 새 규칙을 들이는 것이
아니라 **뒤처진 한 층을 나머지에 맞추는 것**이다.

> ★ 그래서 19번의 뜻이 바뀐다 ★ 「비율 절단점을 **만들지 마라**」로 읽었는데, 실측하면
> **이미 있는 것을 걷어내라**다. `costed === skus`가 그 절단점이고 **100%짜리**다.
> 90%가 안 되는 것과 100%를 요구하는 것은 같은 물건이다 — 둘 다 부분을 «없음»으로 접는다.

## 따름 조건

1. **통은 마켓을 모른다.** `src/core`의 통 코드에 마켓 문자열이 들어오면 위반 (LOCK 4)
2. **표 뷰어는 읽기 전용이다** (LOCK 3·9)
3. **표는 통째로 메모리에 안 올린다** (LOCK 5) — 80,137행이 정기 입력이다
4. **자격 미달은 침묵이 아니라 문장이다** (LOCK 6 · §22-3)
5. **묶음 자격 판정은 §22의 `metric → requires` 한 곳에서만** 한다. 화면마다 다시
   판정하면 두 화면이 다른 답을 낸다 (2026-08-20 할인 3단이 그렇게 갈렸다)

## 확인 결과 (2026-08-21 · 사용자 본인)

**네 질문 전부 이 문서가 권한 쪽으로 답이 왔다.** 그래서 상태를 「결정」으로 올린다.

| | 물은 것 | 답 | 그래서 |
|---|---|---|---|
| ① | 판정 단위를 연결 → **묶음**으로 | **묶음이 기준** | 결정 2가 확정됐다. §22의 `requires[docType]` 판정이 연결이 아니라 묶음 위에서 돈다 |
| ② | 묶음 자격의 기준선 | **열되 부족분을 말한다** | **비율 기준선을 만들지 않는다.** 90% 같은 절단점을 안 둔다 — 지표는 열고 「원가 미입력 25건 — 이익이 실제보다 큽니다」를 그 자리에서 말한다. §22가 이미 그 문법이고, 방금 선 L2 근거 패널도 같은 문장을 쓴다 |
| ③ | 통의 보관 깊이 | **파싱된 표 전 행** | 「아무 파일이나 표로 다시 본다」가 실제로 된다. **원본 바이트는 안 둔다** — 구매자 실명이 든 원본을 앱이 계속 들고 있게 되고, 재파싱 이득보다 그 위험이 크다 |
| ④ | 목업 정합 | **기존 화면에 얹는다** | 새 화면을 안 판다. ADR-021의 「묶음」이 3커밋 만에 선 그 방식 — 「가져오기 기록」을 통으로 바꾸고 행을 누르면 표가 열린다. §21에 항목을 추가할 필요가 없고 E-1에도 안 걸린다 |

> ★ **②가 이 넷 중 제일 무겁다** ★ 「비율로 막지 않는다」는 **자격이라는 말의 뜻을
> 바꾼다** — 묶음은 «통과/탈락»을 판정받는 것이 아니라 **«무엇이 갖춰졌고 무엇이
> 비었나»를 선언**한다. 그래서 결정 2의 이름은 「자격」이지만 실제 기계는 **게이트가
> 아니라 명세**다. 구현할 때 `if (ratio < 0.9) return locked` 같은 코드가 나오면
> 그건 이 확인을 어긴 것이다.
>
> **잠기는 것은 오직 «서류가 아예 없을 때»다** — `ad` 파일이 하나도 없으면 ROAS는
> 열리지 않는다. 그건 부족이 아니라 부재이고, §22-1이 이미 그렇게 적었다
> (「광고를 하지 않는 셀러에게 `ad`는 영원히 잠긴 지표일 뿐이지 결핍이 아니다」).

## 원래 물었던 것 (기록)

1. **결정 2가 사용자의 그림과 같은가** — 「§22 판정 단위를 연결 → 묶음으로 올린다」
2. **묶음 자격의 기준선** — cost가 236/261이면 자격이 있는가 없는가? 비율인가, 사용자가 정하는가, 아니면 「열되 부족분을 말한다」인가
3. **통에 보관하는 깊이** — 전 행인가, 표본인가, 원본 바이트도 두는가 (13MB 파일이 실재한다)
4. **목업 정합** — 「표 뷰어」와 「묶음 자격」 화면이 동결 목업 어디에 앉는가.
   ADR-021은 새 화면 대신 기존 화면에 얹었다(`0658a69`). 같은 방식이 가능한가
