# ADR-024 — DB 파일의 자리: 설치본은 자기 데이터 폴더를 연다

- 상태: **채택** (2026-08-21)
- 관련: [ADR-003](ADR-003-sqlite-바인딩.md) 커맨드 표면 · [ADR-013](ADR-013-파일-바이트-획득.md) IPC 표면 ·
  [ADR-014](ADR-014-열기-설정의-세-갈래.md) 열기 설정 · [코드-남은일 2.9](코드-남은일-2026-08-20.md)

## 문제

앱이 여는 DB 경로가 **빌드한 기계의 프로젝트 폴더**로 굳어 있다.

```
vite.config.ts:35   __PROJECT_ROOT__ = <빌드한 기계의 절대경로>   ← 빌드 시점에 구워진다
data.ts:57          DEV_DB_PATH = `${root}/.tmp/pnl.sqlite`
data.ts:283         openTauriDriver(DEV_DB_PATH, …)
db.rs:174           Connection::open(path)                       ← 부모 폴더를 만들지 않는다
```

`@tauri-apps/api/path`를 부르는 곳이 **0곳**이다. 그래서:

- **다른 PC에 설치하면 첫 열기에서 실패한다.** 그 기계에 `C:\Users\<남>\Desktop\
  Flowbase-Vertical\.tmp\`는 없고, `Connection::open`은 부모 폴더를 만들지도 않는다.
  화면은 「이 동작을 마치지 못했습니다」 모달 하나로 끝난다.
- 같은 기계라도 **프로젝트 폴더를 옮기거나 지우면** 설치본이 데이터를 잃는다.
- `vite.config.ts:25`의 주석은 이 주입을 「스모크 측정 전용(dev에서만 쓴다)」이라
  적어 뒀는데 **실제로는 앱의 유일한 DB 경로**다. 주석이 코드보다 낡은 자리다.

> **왜 지금까지 안 드러났나** — 개발 기계에서는 그 경로가 실재한다. 이 결함은
> 「사용자가 무엇을 해야」 드러나는 종류가 아니라 **아무것도 안 해도 이미 깨져 있는**
> 종류이고, 배포를 생각하는 순간 0순위가 된다.

## 조사 — 남들은 어떻게 하나

데스크톱 로컬퍼스트 앱의 관례는 **OS가 정한 앱 데이터 폴더**다. Tauri는 번들
identifier로 그 자리를 준다 (`com.flowbase.pnl`):

```
Windows   %APPDATA%\com.flowbase.pnl\
macOS     ~/Library/Application Support/com.flowbase.pnl/
Linux     ~/.local/share/com.flowbase.pnl/
```

Obsidian(볼트=사용자가 고른 폴더)처럼 **사람이 자리를 고르게** 하는 설계도 있다.
매력적이지만 지금은 **버린다** — 「어느 폴더를 쓰시겠습니까」는 첫 실행에 질문을
하나 더 얹는 일이고, 그 질문에 답할 근거가 사용자에게 아직 없다. 다만 이 결정이
그 길을 막지 않는다(아래 재검토 트리거).

## 결정

**1. 설치본은 `appDataDir()/pnl.sqlite`를 연다. 개발은 `.tmp/pnl.sqlite` 그대로다.**

가르는 신호는 **`import.meta.env.DEV`** 하나다. `npm run app`(= tauri dev)은 vite가
dev 모드라 참, `tauri build`는 거짓 — 우리가 원하는 것과 정확히 겹친다.

> **왜 Rust의 `debug_assertions`가 아닌가** — `tauri build --no-bundle`로 구운
> **릴리즈 바이너리를 개발 기계에서 돌리는 것**이 바로 이 결함을 재현하는 방법이다.
> 그때 dev 경로로 새면 재현이 안 된다. 판정은 **프론트 빌드 모드**를 따른다.

**2. 개발 DB를 자동으로 복사해 오지 않는다.**

새 설치의 첫 화면은 **빈 DB**이고 그게 참이다. 남의 기계에서 만든 35MB를 몰래
가져오면 「내가 넣은 적 없는 데이터」가 생긴다. §22대로 화면이 「이 기간 파일 없음」을
말한다 — 조용히 0원을 그리지 않는다.

**3. 부모 폴더는 Rust가 만든다.** `Connection::open` 직전에 `create_dir_all`.

경로를 누가 정하든 **폴더가 없으면 열기가 실패한다**는 사실은 같다. 그러므로 이
보정은 경로 결정과 **독립**이고, JS가 어떤 경로를 주든 성립해야 한다.

**4. 커맨드 표면을 늘리지 않는다.** `db_open(path, force)` 그대로다.

ADR-003이 「커맨드 표면이 결정 근거」라고 못박았고 ADR-013이 「IPC 표면 0」의 값을
보였다. 경로 결정은 **프론트가 이미 아는 것**(빌드 모드)에 달려 있으므로 Rust에
새 커맨드를 만들 이유가 없다. `appDataDir()`는 `@tauri-apps/api/path`가 주고,
그 권한은 `core:default`에 이미 들어 있다 — capabilities도 안 늘어난다.

## ★ 파급면 — 이 결정이 닿는 표면 전수 ★

### 무엇이 함께 움직이나

| 층 | 닿나 | 무엇 |
|---|---|---|
| 스키마 | ❌ | 표·컬럼·뷰 변화 없다. **여는 파일의 자리**만 바뀐다 |
| 조회 | ❌ | 모든 조회가 `open()` 뒤에 있어 경로를 모른다 |
| 화면 | ⚠ | 새 vals 없음. 다만 **열기 실패 문구**가 이제 진짜로 뜰 수 있다 (아래) |
| 도구 | ⚠ | `smoke.ts`·`pnl.ts`·`render-screen.ts`·하네스는 **전부 개발 경로 유지**. 도구가 앱 데이터 폴더를 건드리면 사용자 DB를 실험 대상으로 삼는 것이다 |
| 게이트 | ⚠ | 화면 단언 33건은 `.tmp/pnl.sqlite`를 본다 — dev 경로가 안 바뀌므로 그대로 돈다 |

**화면이 함께 움직이는 자리 하나** — 지금까지 열기 실패는 개발 기계에서 사실상
일어나지 않았다. 설치본에서는 디스크 권한·꽉 참 등으로 **실재하는 경우**가 된다.
004fcb6이 세운 오류 화면(「무슨 일이 났는지 · 데이터는 안전하다 · 다시 열기」)이
그 자리를 이미 받고 있고, 이 결정은 **그 화면을 처음으로 실전에 세운다.**

### 앞선 결정을 뒤집나

**뒤집지 않는다.** 셋 다 이 결정과 같은 방향이다:

- **ADR-003** — 커맨드 표면을 늘리지 않는 쪽을 골랐다(결정 4). 표면 유지.
- **ADR-013** — 「IPC 표면 0」의 정신 그대로. 경로는 프론트가 안다.
- **ADR-014** — `journal_mode`가 **파일에 남는다**는 사실은 여기서도 유효하다.
  DB가 앱 데이터 폴더로 가면 **외부 도구가 그 파일을 건드릴 확률이 오히려 줄어든다**
  (ADR-014를 낳은 사고가 정확히 그것이었다). 세션 설정은 그대로 세션 설정이다.

`vite.config.ts:25`의 「dev에서만 쓴다」 주석은 **이 결정으로 비로소 참이 된다** —
지금까지 거짓이었다.

## 따름 조건

1. `appDataDir()` 호출은 **한 곳**이어야 한다. 여러 곳에서 경로를 만들면
   「앱에서는 되는데 스모크에서는 안 되는」 자리가 갈래마다 생긴다 (`isWebDemo`와 같은 규율).
2. **도구는 개발 경로만 쓴다.** 하네스·CLI가 사용자 DB를 열면 실험이 사고가 된다.
3. 열기 실패는 **기존 오류 화면**에 편입한다 (LOCK 6 — 새 실패 상태 발명 금지).

## 재검토 트리거

- 사용자가 **DB 자리를 직접 고르고 싶다**고 하면 → Obsidian식 「볼트 고르기」를 다시 연다.
  이 결정은 그 길을 막지 않는다: 경로를 만드는 자리가 한 곳이므로 거기에 «저장된 선택»을
  얹으면 된다
- **백업·다른 기기로 옮기기**가 요구로 올라오면 → 자리가 예측 가능해진 것이 전제조건이고,
  그때 「이 폴더를 통째로 복사하세요」가 답이 될 수 있다
- 여러 라이브러리(`library_id`가 실제로 둘 이상)가 생기면 → 파일 하나 대 폴더 하나를 다시 판정한다

## 예약한 측정

- **다른 기계에서 설치본 첫 열기** — 이 결함의 정본 재현이다. 개발 기계에서는
  `tauri build --no-bundle`로 구운 릴리즈 바이너리로 근사한다(그때 dev 경로로
  새지 않는 것이 결정 1의 요점이다)
- 첫 열기에서 **마이그레이션 14까지 서는지** — 빈 파일에서 시작하는 경로는
  지금까지 CLI만 지났다
