# ADR-010 — 프로파일 라우팅 규약: 미지의 값을 흘리지 않는다

날짜: 2026-08-12 · 상태: 확정 · 관련: [ADR-006](ADR-006-source-key-전략.md) · [ADR-009](ADR-009-회계-정책.md)

한 파일에 성격이 다른 행이 섞여 들어올 때 어떻게 가르는가, 그리고 **가르는 기준을
벗어난 값이 오면 어떻게 하는가**를 정한다.

---

## 결정 1 — 라우팅은 프로파일 **안**에서 한다

ESM 주문통합검색은 주문과 클레임이 `진행상태` 한 컬럼으로 섞여 있다. 프로파일을
`esm-order@1` / `esm-claim@1`로 쪼개는 대신 **하나 안에 `rowRouting`을 둔다.**

```json
"targetTable": "fact_order",
"rowRouting": {
  "column": "진행상태",
  "knownValues": ["송금완료", "구매결정완료", "취소완료", "반품완료", "환불완료", "구매거부취소"],
  "routes": [
    { "match": ["취소완료", "반품완료", "환불완료", "구매거부취소"],
      "targetTable": "fact_claim",
      "fieldMappings": [ … ] }
  ]
}
```

### 왜 쪼개지 않는가

**Recognition이 모호해진다.** 프로파일 둘이 같은 파일에 매칭되면 어느 것을 고를지
파일만 보고는 알 수 없다. 헤더도 같고 파일명도 같다 — 고를 근거가 없다.

그리고 **batch가 둘로 갈린다.** 한 번의 가져오기가 batch 둘을 만들면 되돌리기가
두 번이 되고, 사용자는 "왜 한 파일이 기록에 두 줄이지"를 묻게 된다. 라우팅은
적재 대상의 문제이지 가져오기 단위의 문제가 아니다.

`MappingResult.byTable`이 테이블별 행을 돌려준다. **`rows`만 보고 적재하면 다른
경로로 간 행을 통째로 놓친다** — 그래서 `rows`는 기본 경로만 담는다는 것을
타입 주석에 명시했다.

---

## ★ 결정 2 — `knownValues` 선언 의무 ★

> **판별 컬럼 기반 라우팅은 반드시 `knownValues`를 선언한다.
> 미지의 값은 기본 경로로 흘리지 않고 오류로 표면화한다.**

이것이 이 문서의 핵심이고, **모든 프로파일에 적용되는 규약**이다.

### 왜 — 라우팅은 "안 걸린 값"의 운명을 정하지 않으면 구멍이 된다

`routes[].match`는 **클레임 상태만** 열거한다. 마켓이 `"부분취소완료"` 같은 상태를
새로 만들면 어느 route에도 안 걸리고 **기본 경로(매출)로 조용히 들어간다.**
클레임이 매출로 잡히는 바로 그 사고이며, 라우팅을 도입한 이유 자체를 무효로 만든다.

`valueMap`의 "사전에 없는 값" 가드는 **이 경우를 잡지 못한다.** 그 가드는 클레임
경로로 들어온 행만 검사하는데, 미지의 값은 애초에 그 경로로 오지 않기 때문이다 —
**도달할 수 없는 가드**다 ([ADR-007](ADR-007-정규화-표현.md)의 "파괴 시험의 안 깨짐"이
그대로 재현된 사례).

### 처방

```
아는 값을 전부 선언한다 → 벗어나면 오류로 보고한다
행은 버리지 않고 기본 경로로 보내되, 모르는 상태가 왔다는 사실을 남긴다
```

**버리지 않는 이유**: 그 행이 정말 매출일 수도 있다. 데이터를 없애는 것은
잘못 분류하는 것만큼 나쁘다.
**표면화하는 이유**: 새 상태가 생겼다는 건 사람이 봐야 하는 사건이다 (헌장 A-5).

### 적용 범위 — 앞으로 만들 프로파일 전부

11번가 주문 · 쿠팡 매출 · 네이버 정산 등 **판별 컬럼으로 행을 가르는 모든
프로파일**이 이 규약을 따른다. 하나라도 빠뜨리면 그 양식은 같은 함정을 갖고
태어난다.

라우팅이 **없는** 프로파일에는 해당하지 않는다 — 가를 것이 없으면 미지의 값도 없다.

---

## 결정 3 — `valueMap`은 스키마의 `CHECK`를 지킨다

파일은 `"취소완료"`라 적고 스키마는 `claim_type IN ('CANCEL','RETURN','EXCHANGE','REFUND')`를
요구한다. 그 사이를 프로파일이 사전으로 잇는다.

- **사전에 없는 값은 통과시키지 않는다.** 통과시키면 적재 시점에 `CHECK`가 터지거나,
  더 나쁘게는 엉뚱한 분류로 집계된다
- 값이 뭉개지면 **원문을 다른 컬럼에 보존한다.** ESM에서 `구매거부취소`와 `취소완료`는
  둘 다 `CANCEL`이 되지만 `status`에 원문이 남는다

---

## 따름 조건

1. `rowRouting`이 있으면 `knownValues`도 있어야 한다 — 없으면 미지의 값이 조용히 샌다
2. 적재하는 쪽은 **`byTable`로 읽는다.** `rows`만 읽는 코드는 라우팅이 추가되는 순간
   조용히 행을 잃는다
3. `knownValues`는 **실측으로 채운다.** 문서에서 베끼지 않는다 — 실제 파일에 없는
   상태를 넣으면 가드가 헐거워지고, 있는 상태를 빠뜨리면 매달 오류가 뜬다
4. 오류가 실제로 뜨면 **프로파일을 고쳐 새 버전을 낸다** (헌장 B-6). 기존 버전을
   수정하지 않는다

---

## 재검토 트리거

1. 판별 컬럼이 둘 이상 필요한 양식 등장 → `routes[].match`를 조건식으로 확장.
   단 선언적으로 유지한다 (프로파일은 코드가 아니라 데이터다 — 헌장 B-6)
2. `knownValues` 오류가 매달 반복 → 마켓이 상태 체계를 바꾼 것이다. 프로파일 새 버전
3. 한 행이 **두 테이블에 동시에** 들어가야 하는 양식 등장 (주문 헤더 + 품목 등) →
   지금 구조는 행 하나가 한 경로다. 다중 목적지는 별도 설계가 필요하다
