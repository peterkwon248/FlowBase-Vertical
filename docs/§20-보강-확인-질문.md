# §20 보강 — 확인 질문 · 드리프트 다이제스트

채택 2026-08-14. **설계만. 구현은 트리거 후.**

두 갈래다 — **처음 보는 양식**은 «확인 질문»이, **아는데 달라진 양식**은
«드리프트 다이제스트»가 맡는다. 트리거는 같다.

> ⚠ 이 문서는 «아직 짓지 않은 것»의 설계다. 워터폴(§21)이 검증층 부재를 이유로
> 3단으로 밀린 것과 **같은 논리**다 — 실측할 대상이 없으면 짓지 않는다.

## 원칙

결정론 5층이 확정하지 못한 컬럼은 **조용히 고르지 않고 소리 내어 묻는다.**

```
별칭 → 값 신호 → 문서 맥락 → 항등식 → 개인 프로파일
```

다섯을 다 통과하고도 남는 것만 질문이 된다.

## 규칙 5

1. **질문 최소화.** 5층을 전부 통과한 뒤 남는 것만 묻는다. **3개를 넘으면 설계
   실패**로 간주하고, 질문을 다듬기 전에 원인(프로파일 부족)을 먼저 본다.
2. **후보에 근거 필수.** %가 아니라 **검증 문장**이다 —
   *"판매합계−공제와 128행 일치"*. §21-1 계보이고, 결함 52에서 «일치도 %»를
   «선언»으로 바꾼 것과 같은 이유다.
3. **«이 열은 쓰지 않음»이 항상 선택지다.** 강제로 고르게 하지 않는다.
4. **답 = 프로파일 갱신** (기억하기 체크 시). 다음 파일부터 질문 0.
5. **답 = 사용자 판단으로 기록** (`entered_by`, L2에서 추적 가능).

## 레이아웃

확인 단계의 **매핑 표는 유지한다** (사용자 확정 — 전체를 조망하는 값이 있다).
그 **위에** «확인이 필요한 항목 N» 카드 섹션을 얹는다.

동작 셋:

| | |
|---|---|
| 카드 ↔ 표 행 | 양방향 연결 |
| 질문 0개 | **섹션 자체가 없다** (빈 섹션을 그리지 않는다 — §21-7 계보) |
| 미응답 | **진행 가능.** 해당 열은 «쓰지 않음» 처리하고 **다이제스트에 명시**한다 |

미응답을 막지 않는 이유는 §22의 금지 조항과 같다 — **안내지 검문이 아니다.**

## 드리프트 다이제스트 — **아는 양식이 달라졌을 때** (설계, 2026-08-14)

확인 질문이 «처음 보는 양식»의 문제라면, 이쪽은 **«지난달에 넣어 본 양식»**의 문제다.
마켓은 예고 없이 컬럼을 더한다. 그때 전체를 다시 매핑하라고 하면 사용자는 이미
확정한 40개 컬럼을 처음부터 다시 본다 — **바뀐 것은 하나인데.**

> **묻는 것은 전체가 아니라 diff다.**

```
지난달과 달라진 점: 새 컬럼 1개
  적립금차감 — 값 표본 「0 · 1,200 · 0 · 3,500」. 금액으로 보입니다.
  [지금 확인]  [이번엔 무시]
```

### 두 답이 각각 무엇을 뜻하는가

| 답 | 뜻 | 결과 |
|---|---|---|
| **이번엔 무시** | «이 열은 쓰지 않음» (규칙 3의 그 선택지다) | **미매핑으로 정직하게 남는다** — 다이제스트가 «버린 컬럼 N개»에 그대로 센다 |
| **지금 확인** | 이 열을 쓰겠다 | 확인 질문 카드로 이어지고, 답이 **프로파일의 새 버전**이 된다 (규칙 4) |

**«무시»가 조용한 실패가 되지 않는 것이 이 설계의 핵심이다.** 무시는 «없던 일»이
아니라 «세고 있는 부재»다 — LOCK 6이 요구하는 것이 정확히 그것이고, 이미
`unmappedColumns.policy: "keep-count"`가 그 자리를 잡고 있다.

### 재료는 전부 이미 있다 — 새 저장이 없다

| 재료 | 어디에 |
|---|---|
| «지난번엔 어떤 양식이었나» | `batch.mapping_version` — batch마다 기록된다 (헌장 B-6) |
| «지금 이 파일은 어떤 모양인가» | 헤더 탐지 + `columnRoles()` |
| «새 컬럼이 무슨 값인가» | 결정론 5층의 **값 신호** 층. 표본을 그대로 보여준다 |
| «어떻게 물을 것인가» | 위 «레이아웃»의 확인 질문 카드 |

새 테이블도, 새 컬럼도 필요 없다. `mapping_version`이 같은 마지막 batch의 헤더와
지금 헤더를 비교하면 diff가 나온다.

> ⚠ **다만 헤더 원본을 저장하고 있지 않다.** batch는 `mapping_version`·`sheet_name`은
> 알아도 «그때 헤더가 무엇이었나»는 모른다. 구현 시 첫 결정은 «헤더를 batch에
> 남길 것인가»이고, 대안은 **프로파일의 선언 컬럼 집합과 비교**하는 것이다 —
> 후자가 저장을 늘리지 않아 먼저 볼 쪽이다. (`columnRoles`가 이미 그 집합을 낸다.)

### 같은 절에 — **다이제스트 브리핑 확장**

같은 «달라진 점을 먼저 말한다»의 계보다. 지금 다이제스트는 «넣은 것/못 넣은 것»만
말하는데, 넣고 나서 **사용자가 할 일이 생겼다**는 사실은 말하지 않는다:

```
새 리스팅 12개 — 그중 5개는 기존 SKU 후보가 있습니다  [연결하러 가기]
```

후보 판정은 이미 `packs/…/listing-match.ts`가 점수로 내고 있고 연결 화면이 그걸
쓴다. **여기서는 «있다»만 말하고 확정하지 않는다** — 자동 확정 금지는 그대로다
(리포지토리 쓰기 함수가 점수를 인자로 받지 않아 구조적으로 불가능하다).

없으면 이 줄은 **뜨지 않는다.** 「새 리스팅 0개」를 그리지 않는 것은 §21-7의
«빈 섹션을 그리지 않는다»와 같은 규율이다.

## 구현 트리거

**8월 실전 이후, 드리프트 또는 애매 컬럼이 실물로 1회 이상 발생했을 때.**

두 기능은 트리거가 같다 — 둘 다 «실측할 대상이 없으면 짓지 않는다»에 걸린다.
드리프트 쪽은 특히 그렇다: **같은 양식을 두 달 넣어 봐야 diff가 존재한다.**

그 전까지는 이 문서만 있는다. 오늘 지으면 물어볼 것이 없어 빈 섹션만 렌더되고,
그것을 확인하려고 가짜 애매 컬럼을 만드는 순간 3a 게이트(시드 잔재 0건)를
검증을 위해 어기는 순환에 빠진다.

## 지금 쌓인 관련 실측

리허설(2026-08-14)에서 **확인 단계가 컬럼의 역할을 과소 보고**하는 결함이 나왔다.
`fieldMappings`만 읽고 `sourceKey`·`listing`·`rowRouting`을 안 봐서, 행 식별 키와
리스팅 제목의 출처가 «이 프로파일이 쓰지 않는 컬럼»으로 표시된다
([목업-결함-발견분](목업-결함-발견분.md) 53).

**이 결함은 트리거를 기다리지 않는다.** 확인 질문은 «모르는 것을 묻는» 기능이고,
저것은 «아는 것을 틀리게 말하는» 결함이라 계열이 다르다.
