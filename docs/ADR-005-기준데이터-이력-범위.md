# ADR-005 — v1 기준 데이터의 변경 이력 범위

- **상태**: 채택
- **일자**: 2026-08-12
- **범위**: 헌장 B-4 (데이터 3종 분류 — 기준 데이터의 "수동 편집 + 변경 이력")
- **발견**: 헌장 B부 대비 diff 검수 (U-2). 조용한 축소를 막기 위한 명시적 결정 요구

---

## 결정

**v1의 변경 이력은 원가만 시계열로 갖는다. 나머지 기준 데이터는 `updated_at`만 둔다.**

| 기준 데이터 | v1 | 근거 |
|---|---|---|
| 원가 (`cost_history`) | **시계열 이력** | 아래 |
| 상품 (`product`) | `updated_at` | |
| SKU (`sku`) | `updated_at` | |
| 상품 연결 (`marketplace_listing`) | `updated_at` + `linked_at`·`linked_by` | |
| 매핑 프로파일 (`mapping_profile`) | **버전이 곧 이력** (B-6) | 기존 버전 수정 금지, 변경은 새 행 |

---

## 왜 원가만인가 — 이력의 성격이 다르다

원가의 이력은 **과거를 다시 계산하기 위해** 필요하다. 인계 문서 §5:

> 원가는 숫자 하나가 아니라 시계열이다. `SKU.cost = 12000`이 아니라 적용 시작일이 붙은
> 이력이다. `costAt(skuId, 주문일)`이 그 주문일 이전 중 가장 늦은 단가를 쓴다.

7월 주문의 손익은 **7월에 유효했던 원가**로 계산해야 한다. 오늘 원가를 올렸다고 지난달
이익이 바뀌면 그건 틀린 숫자다. 즉 원가 이력은 감사 기록이 아니라 **계산의 입력**이다.

나머지는 다르다. 상품명이 바뀌었을 때 지난달 리포트를 옛 이름으로 다시 그릴 이유가 없고,
연결을 바꿨을 때 과거 집계를 옛 연결로 되돌릴 이유도 없다. 이들의 과거 값은 **감사
목적**이고, v1에는 그 요구가 없다.

## 이 결정이 축소인 것은 맞다

헌장 B-4는 기준 데이터 전반에 "변경 이력"을 적었다. 이 결정은 그 범위를 좁힌다.
**조용히 좁히지 않기 위해** 여기 적는다.

되돌릴 수 있는 형태로 좁혔다는 점이 근거다:
- `cost_history`가 **패턴을 이미 확립**했다 (대상 + 종류 + 금액 + 적용 시작일 + 입력자)
- 다른 기준 데이터에 이력이 필요해지면 같은 모양의 테이블을 추가하면 된다.
  기존 테이블의 컬럼을 바꾸지 않으므로 소급 문제가 없다
- 헌장 B-1의 "소급 추가 불가"는 **Fact 행의 공통 컬럼**에 대한 규정이고, 기준 데이터의
  이력 테이블은 거기 해당하지 않는다

## 재검토 트리거

1. 상품·SKU 이름 변경이 과거 리포트에 영향을 준다는 요구 발생 → 해당 이력 테이블 추가
2. 감사 요구(누가 언제 무엇을 바꿨나)가 생김 → 기준 데이터 전반에 변경 로그 도입 검토
3. 연결 재매핑으로 과거 집계가 흔들리는 사례 발생 → `marketplace_listing` 이력화
