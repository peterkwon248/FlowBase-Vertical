# ADR-006 — 자연 키가 없는 양식의 `source_key`

- **상태**: 채택
- **일자**: 2026-08-12
- **범위**: 헌장 B-2 (`source_key` 중복은 UPSERT), Mapping 프로파일
- **발견**: 픽스처 #13(쿠팡 광고 80,137행)으로 첫 실프로파일을 관통시키던 중

---

## 문제

헌장 B-2는 이렇게 적었다.

> append-only. 가져오기는 덮어쓰기가 아니라 batch 추가다. **`source_key` 기준 중복은 UPSERT.**

이 문장은 마켓 파일에 행을 구분하는 자연 키가 있다고 전제한다. **#13에는 없다.**

### 실측

```
데이터 행 80,137

캠페인ID+옵션ID                        고유     83   중복 80,054
캠페인ID+그룹+옵션ID                    고유     83   중복 80,054
캠페인ID+그룹+옵션ID+지면                고유    182   중복 79,955
캠페인ID+그룹+옵션ID+지면+키워드           고유 79,682   중복    455
캠페인ID+그룹+집행옵션+전환옵션+지면+키워드    고유 80,057   중복     80

전체 43컬럼 완전 동일 중복: 6건
```

차원 컬럼을 전부 묶어도 유일하지 않다. 그리고 겹치는 행들은 **내용이 다르다**:

```
── 차원 동일 · 내용 다름 (3행) ──
  노출수          1837  vs  0  vs  0
  클릭수             5  vs  0  vs  0
  광고비          1155  vs  0  vs  0
  총 주문수(1일)      0  vs  0  vs  1
  총 전환매출액(1일)   0  vs  0  vs  63900
```

한 행은 **노출·클릭·광고비**를, 다른 행은 **전환수·전환매출**을 담고 있다. 파일에 드러나지
않은 차원(거의 확실히 날짜 — 월간 리포트인데 날짜 컬럼이 없다)이 행을 가르고 있다.

**자연 복합키를 쓰면 이 행들이 서로를 UPSERT로 덮는다.** 광고비 1,155원과 전환매출
63,900원 중 하나가 사라진다. 헌장 A-5가 최악이라 부른 조용히 틀린 숫자다.

---

## 결정

**프로파일이 키 전략을 명시한다.** 자연 키가 있는 양식과 없는 양식을 같은 규칙으로
다루지 않는다.

```jsonc
"sourceKey": { "strategy": "natural",  "columns": ["주문번호", "주문순번"] }
"sourceKey": { "strategy": "content" }   // 자연 키 없음
```

### `content` 전략 — 내용 해시 + 동일 내용 순번

```
source_key = sha1(정규화된 전 컬럼 값) + ":" + n
             n = 그 파일 안에서 같은 해시가 나온 순번 (0부터)
```

두 성질을 동시에 만족한다.

| | |
|---|---|
| **서로 다른 행이 합쳐지지 않는다** | 내용이 다르면 해시가 다르다. 내용이 완전히 같은 6건은 순번으로 갈린다 |
| **같은 파일 재가져오기가 멱등이다** | 같은 내용 집합 → 같은 키 집합 → 깨끗한 UPSERT. **행 순서가 바뀌어도 유지된다** |

### 왜 행 번호(positional)가 아닌가

`source_key = 행 번호`도 유일성은 만족한다. 하지만 마켓이 정렬을 바꿔 내보내면 같은 행이
다른 키를 갖게 되고, 재가져오기가 엉뚱한 행끼리 UPSERT한다 — 광고비가 다른 캠페인에
붙는다. 내용 해시는 순서에 기대지 않는다.

### 대가

원본에서 **한 행의 값이 정정되면** 그 행은 새 키를 갖는다. 옛 행이 남고 새 행이 추가되어
이중 집계가 된다.

이건 `content` 전략의 구조적 한계이고, 감출 수 없다. 해소 경로는 헌장 B-2가 이미 제공한다 —
**이전 배치를 되돌리고 다시 가져온다.** 위저드가 이 사실을 알려야 하며, §18-E로 기록했다.

## ⚠ 구분자는 `U+0001`이다 — 소스에서 보이지 않는다

`mapping/index.ts`의 두 `join()`은 **빈 문자열이 아니라 제어문자 `U+0001`로 잇는다.**

```
contentKey  values.map(...).join("")        // 내용 해시의 canonical 문자열
natural     (sourceKey.columns).map(...).join("")
```

에디터·`grep`·코드 리뷰에서는 `.join("")`으로 보인다. 실제 바이트는 `0x01`이다
(`sed -n '147p' … | cat -A` → `join("^A")`로 확인된다).

**이걸 "빈 문자열"로 착각해 정리하면 모든 `source_key`가 바뀐다.** 키가 바뀌면 UPSERT
정체성이 바뀌므로, 재가져오기가 기존 행을 갱신하지 못하고 전부 새 행으로 쌓인다 —
이중 집계다. 조용히 틀린 숫자(헌장 A-5)의 전형이다.

구분자 자체는 **옳다.** 없으면 `["a","bc"]`와 `["ab","c"]`가 같은 canonical 문자열을
만들어 서로 다른 행이 같은 키를 받는다. 데이터에 나올 수 없는 바이트라 충돌도 없다.
문제는 의도가 소스에 안 보인다는 것뿐이다.

바꾸려면 **기존 DB의 키를 전부 재계산해야 한다.** 표현만 고치는(바이트 동일)
리팩터링이라도 `tools/harness/equivalence.ts --check`로 #13 매핑 해시
`b1187f70e5758592`가 유지되는지 반드시 확인한다.

> 2026-08-12: ADR-007 작업 중 발견. 이 문서에 기록되지 않은 채
> `70ab59c`에서 들어와 있었다.

## 재검토 트리거

1. 쿠팡이 날짜 컬럼을 포함하도록 리포트를 바꿈 → 그 양식은 `natural`로 승격
2. `content` 전략 양식의 재가져오기 이중 집계가 실사용에서 발생 → 배치 간 diff 기반
   자동 정리 검토
3. 다른 마켓 양식에서 같은 문제 발견 → 전략 목록에 추가 (예: 부분 키 + 순번)
