## ★ 품목 적재 — ④의 자물쇠 (2026-08-14) ★

**매출은 주문 헤더로 들어오고 원가는 SKU에 붙는다. 그 둘을 잇는 것이 품목이다.**
`fact_order_item`은 001부터 있었지만 0행이었고, 그래서 원가를 넣어도 순이익이
움직이지 않았다.

```
ESM #8        주문 146 · 클레임 9 · 품목 146      ← 클레임은 품목을 만들지 않는다
쿠팡 일반 #14  주문 141 · 품목 141
쿠팡 제트 #15  주문 147 · 품목 147   (그중 수량 0이 103행)
```

### 설계 결정 넷 — 각각이 함정을 하나씩 막는다

| 결정 | 막는 함정 |
|---|---|
| 품목 키 = **부모 주문 키 + 리스팅 키** | 새 식별자를 선언하면 리스팅 키와 언젠가 갈린다 |
| `sku_id`를 **비워 둔다**. SKU는 `listing_id` → 리스팅에서 조회 때 잇는다 | 적재 시점에 박으면 **나중에 연결한 리스팅의 과거 판매가 영원히 안 붙는다** |
| `listing_id`는 자연키에서 **계산**한다 (`lst-{conn}-{key}`) | 조회 왕복 0. 리스팅 upsert 순서만 지키면 된다 |
| `order_id`는 **조회해서** 채운다 | UPSERT가 id를 보존하므로 **재가져오기에서 계산한 id는 틀린다** (실측) |

두 번째가 이 작업에서 가장 중요한 결정이다. 사람이 상품 연결 화면에서 리스팅을
SKU에 잇는 순간 **과거 판매의 원가가 소급해서 붙고**, 잘못 연결한 것을 고치면 그
정정도 소급된다 — 연결은 기준 데이터이고, 기준 데이터의 정정이 이력을 바로잡는 것은
정상 동작이다. `tests/order-item.test.ts`가 «연결 전 0 → 연결 후 2,100»으로 못박는다.

### ★ 되돌리기가 깨져 있었다 — 품목이 생기는 순간 드러날 버그 ★

```
undoBatch가 FACT_TABLES 순서로 지운다 → 부모(fact_order)가 자식(fact_order_item)보다 먼저
PRAGMA foreign_keys = ON                → FOREIGN KEY constraint failed
```

되돌리기는 이미 실기기에서 한 바퀴 돌았지만 그 회차가 증명한 것은 **«품목이 없는
되돌리기»**였다. 게이트의 사각을 아는 것(작업 리듬 7)의 또 한 사례다.

`DELETE_ORDER`를 **따로 선언**했다 — `FACT_TABLES`를 재정렬하지 않는다. 그쪽은
«적재할 수 있는 테이블의 목록»이라 순서에 뜻이 없고, **뜻이 있는 순서를 이름 없는
배열 순서에 얹어 두면 다음 사람이 알파벳순으로 정렬하는 날 조용히 깨진다.**

### 곁들여 — 보이지 않는 구분자가 두 벌이었다

`KEY_SEP`(U+0001)이 `listing.ts`에 상수로 있는데 `mapping/index.ts`는 **리터럴을 두 곳에
직접 적고 있었다.** 품목 키가 그 구분자를 쓰기 시작하면서 «두 벌이 같다»에 정합성이
걸리게 됐으므로 상수로 합쳤다. 소스에서 보이지 않는 문자라 어긋나도 눈으로는 못 잡는다.

### «원가 0원»의 뜻이 이제 다섯이다 — 처방이 다르면 다른 단서다

| 상태 | 문구 | 처방 |
|---|---|---|
| 품목 0행 | 매입원가 · **적용 불가** | 없다 (파일을 다시 넣어야 한다) |
| 리스팅이 SKU에 안 이어짐 | **SKU에 연결되지 않은 판매** · 원가 못 붙음 | 상품 **연결** 화면 |
| 이어졌는데 원가 없음 (전부) | 매입원가 · 미입력 | 상품 화면 |
| 이어졌는데 원가 없음 (일부) | 매입원가 · **일부 미입력** (warn) | 상품 화면 |
| 기간 안에서 원가가 바뀜 | 기간 집계의 매입원가 · **근사** | 적용일을 기간 경계에 맞춘다 |

뭉뚱그려 «원가 미입력 N건»이라 말하면 **사용자가 원가를 다 넣고도 숫자가 안 맞는
이유를 영영 모른다.** 처방이 다르면 다른 단서다.

### 조건 2 — 기간 집계의 원가는 근사다, 그리고 **그렇다고 말한다**

`date_precision='period'` 행은 `ordered_at`이 기간 **시작일**이라 `costAt`도 그 날짜로
단가를 고른다. 기간 안에서 원가가 바뀌면 후반 판매분이 옛 단가로 잡힌다.

**기준일은 바꾸지 않는다** — 중간값·가중평균은 «파일이 말하지 않은 것»을 지어내는
일이고, 일별 수량을 모르는 이상 어느 쪽도 더 참이 아니다. 대신 **근사가 실재할
때만** 말한다: 그 기간 안에 실제로 `effective_from`이 있는 행을 세어
`cogs-period-approx`가 표면화한다. 0이면 화면은 아무 말도 하지 않는다.

조항은 [ADR-009 ①-보완 2](ADR-009-회계-정책.md)에 있다.

### 안 한 것 — 쿠팡 헤더의 grain은 **그대로 둔다**

실측: 쿠팡 일반은 주문번호 140/141 유일이고, 중복 1건은 한 주문에 «블루»·«핑크»
옵션 둘이 실린 것이다. 즉 `fact_order`가 지금 **옵션 단위**이고 실제 주문보다 하나 많다.

품목을 붙이면서 헤더를 주문 단위로 되돌리지 **않았다.** `source_key`가 바뀌는 일이라
기존 batch의 UPSERT 정체성과 되돌리기 의미(ADR-004)가 함께 흔들리고, `equivalence
--save` 기준선부터 떠야 하는 별건이다. **품목은 그것 없이도 «어느 SKU가 몇 개
팔렸나»를 온전히 답한다.**

### ★ 남은 것 — 판단이 필요하거나 별건이다 ★

> **★ A와 B는 해소됐다 (커밋 `ba7b9c5`) ★** 아래는 그때의 판정 기록이다.
> 남은 것은 C·D·E·F.

**★ A. ESM 클레임 이중 차감 → 해소. 판정: ②(이중 기록) ★**

```
revenue  = SUM(active_order.total_amount)      ← 클레임 9행은 fact_claim으로 갔으므로 애초에 없다
computePnl                                      ← 그런데 claims 388,700원을 여기서 **또** 뺀다
```

ESM의 `rowRouting`은 취소·반품·환불 행을 `fact_claim`**에만** 넣는다. 그 행들은
매출에 들어간 적이 없는데 손익이 한 번 더 뺀다 — 순이익이 388,700원 **과소**계상.

ADR-009 ①과 충돌하지 않는다는 점이 함정이다: 「클레임은 발생일 기준」은 **원거래가
다른 달에 있는** 클레임을 위한 규칙이고, ESM은 원거래 행 **자체**가 클레임으로
분류된 모양이다. 두 경우를 같은 식으로 다루면 후자가 두 번 빠진다.

**판정: ②** — `rowRouting.routes[].alsoDefault`. 결정적 근거는 ①이 ESM에서
**구조적으로 불능**이라는 점이다: 조인하려면 클레임 키(주문번호)와 주문 키
(주문번호+상품번호)를 근사 매칭해야 하는데 ADR-006이 금지한다. 전부 «짝 없음»으로
판정하면 월경계 클레임이 영영 안 빠지는 더 큰 사고가 된다. 표시 계층 땜질은
22-5(«매출은 order에서만») 위반이라 **저장 계층**이 정도다.

```
총매출  8,285,200  ✔ 정답지 · 클레임 388,700 ✔ · 순매출 7,896,500 ✔ (옛 7,507,800)
적재    fact_order 155 · fact_claim 9 · fact_order_item 146
표기    「판매 155건 · 취소 9건」 — 146의 소멸은 의도된 것이다
```

곁들여 잡힌 것 둘: «취소된 판매는 품목이 없다»가 *"다시 넣으면 생긴다"*는 **못 지킬
처방**을 만들 뻔했고(같은 `source_key`의 클레임 유무로 판정해 뺐다), 한 파일 행이
최대 **세** Fact 행이 되면서 `row_count`의 소유자를 `MappingResult.rowsLoaded`로
옮겼다 — 플래그로 예외를 두는 것보다 소유자를 옮기는 쪽이 맞다.

**B. 적재 경로가 다시 두 벌 → 해소.** `tools/harness/pnl.ts`의 루프를 통째로
`runImport` 호출로 바꿨다. 그 루프는 `runImport`가 생기기 전의 «완전한 쪽»이었고
그 뒤로도 두 번째 벌로 남아 `mapped.items`를 안 읽고 있었다 — 같은 파일이 CLI에서는
품목 0, 위저드에서는 146이 됐다.

**C. LOCK 6 계열 셋** — 리스팅 키가 빈 행은 품목이 조용히 안 생긴다(오류·제외 기록
0건) · 고아 품목 분기가 행을 버리며 아무 데도 안 남긴다 · `orderItem`을 엉뚱한
`targetTable`에 선언하면 raw FK 오류로 죽는다(프로파일 검증 없음).

**D. 음수 수량** — 반품이 음수로 오는 양식이 생기면 원가 환입이 0이 되고 모든
지표에서 사라진다. 오늘 픽스처에는 없다(제트 항등식 147/147 성립).

**E. `cogs-period-approx`가 기준 단가가 아예 없는 행에서도 뜬다** — 그 행은 근사가
아니라 **미상**이라, 문장이 틀린다. `cogs-missing`과 나란히 떠서 서로 다른 말을 한다.

**F. minor/nit 10건** — 화면 문구 낡음 · 조사 고정(«원가 44개이») · `gross_amount`를
읽는 코드가 하나도 없어 이중계상 함정이 놓인 것 · 청크 delta가 다른 모듈의
«갱신하지 않는다» 성질에 걸려 있는데 그 성질의 테스트가 없는 것 등.

> **다음 세션은 C부터** (A·B 해소됨). 남은 것은 전부 «말이 틀렸다» 계열이라
> 숫자를 움직이지 않는다 — 그래서 실기기 세션을 막지 않는다.

행 31 · 제외 0 · 매핑 오류 0 · source_key 유일 31/31
총비용 533,291원 · 구매금액 1,909,000원 · 노출 236,612 · 클릭 843

### 대행사 요약본(#4)에는 프로파일을 만들지 않는다 — §22-5-a

다시 묶은 것이다. 원본(#11)이 우리 손에 있으므로 §22-5-a에 따라 원본이 아니고,
넣으면 같은 533,291원이 시트 수만큼 쌓여 **광고비가 부풀고 순이익이 그만큼 깎인다.**

> 없는 채널이라면 그것이 원본이 된다 — 로켓그로스가 그랬듯이.

**부재를 단언으로 못박았다** — `tests/profile-registry.test.ts`가 #4의 **18시트를 전부
돌며** «어느 시트에도 프로파일이 붙지 않는다»를 검사한다. 「G_상품별」·「G_키워드별」은
«노출수·클릭수·총비용»을 갖고 있어 **걸릴 여지가 실제로 있다.**

### 단언이 또 스스로 뒤집혔다 (두 번째)

```
marketDict("esm").readable   ["order"]  →  ["ad", "order"]
마켓 × 성격 9칸 중 읽을 수 있는 칸    3 → 5
```

프로파일 JSON 하나를 더한 것 말고는 아무 파일도 안 건드렸는데 채널 화면 문장이 함께
움직였다. 쿠팡 때 «예언»했던 반복이 그대로 일어난 자리다 (22-3-a).

**충돌 검사도 함께 돌렸다** — #1·#2(11번가 기간별보고서)는 헤더가 겹치지만
`날짜·노출수·클릭수·클릭률·총비용`까지고 **«영역명»과 «구매수·구매금액»이 없다.**
컨테이너 포맷(CSV vs xlsx)에만 기대지 않고 셋을 다 필수 헤더에 넣었다 — 언젠가
11번가 보고서가 xlsx로 나오는 날 그 방어 하나가 사라지기 때문이다.

## ★ ③④ 원가 — 입력 화면과 손익 배선 (2026-08-14) ★

사슬이 여기서 닫혔다. **다만 마지막 칸이 «배선은 됐고 숫자는 아직»이다.**

```
① 프로파일 확장 → 리스팅 적재     ✅
② 리스팅 → SKU (연결 화면)        ✅
③ 원가 입력 UI (상품 화면)        ✅  ← 이번
④ costAt → computePnl             ✅ 배선 · ❌ 값 (품목 0행)
```

| 조각 | 자리 |
|---|---|
| 규칙 (`costAt`) | `core/cost/index.ts` — **판매일 이전 중 가장 늦은 이력. 없으면 `null`** |
| 같은 규칙의 SQL판 | 같은 파일 `costAtSql` — 집계는 SQL에 위임해야 해서(LOCK 5) 필요하다 |
| 조회 단일화 (여섯 번째) | `core/product/rows.ts` |
| 저장 | `Repository.addCost` / `costHistory` |
| 손익 | `core/profit/snapshot.ts` — `cogs`가 `base.cogs`에서 **DB 조회**로 |
| 화면 | `app/product.ts` · `data-s21="cost-input"` · `data-s21="cost-gauge"` |
| 시험 | `tests/cost.test.ts` 23개 · `tests/product-screen.test.ts` 15개 |

### ★ «미상»과 «0원»을 끝까지 가른다 — 이 작업의 전부다 ★

원가가 없는 SKU에 0을 넣으면 그 상품의 기여이익이 **매출 전액**이 되고, 화면은
«원가 미입력»이 아니라 **«엄청 남는 상품»**이라고 말한다. §22가 «부재를 0으로 바꾸지
않는다»고 한 것의 계산기판이다.

```sql
SUM(oi.quantity * <그날 원가>)   -- 원가가 NULL인 행은 0으로 세지 않고 **빠진다**
SUM(CASE WHEN <그날 원가> IS NULL THEN 1 ELSE 0 END)   -- 빠진 만큼을 따로 센다
```

### 규칙이 두 벌이 되지 않게 — TS와 SQL을 직접 대조한다

화면은 `costAt`(메모리), 손익은 `costAtSql`(80,138행에 붙는다). 둘이 갈리면 화면과
대시보드가 다른 원가를 말한다. 되돌리기 버튼 3상태에 쓴 처방을 그대로 썼다 —
**`ORDER BY effective_from DESC LIMIT 1`을 저장소에서 딱 한 번만 적고**, 테스트가
경계 6개(`2026-05-31` … `2026-08-01`)에서 두 답을 직접 맞춰 본다.

### ★ «원가 0원»의 뜻이 셋이라 갈라 말한다 ★

여기 있던 한 줄은 **곧 거짓말이 될 문장**이었다:

```
전:  pnl.cogs === 0  →  "원가 0 — cost_history가 비어 있다"
```

사용자가 상품 화면에서 원가를 넣는 **바로 그 순간** 거짓이 된다. 결함 47(«2026년 8월»)·
52(시드 3·7)와 같은 계열 — **화면이 데이터를 안 보고 하는 말은 데이터가 바뀌는 날
거짓이 된다.** 그래서 `cogsBasis`를 근거로 갈랐다:

| 상황 | 뭐라고 하나 | 톤 |
|---|---|---|
| 품목 0행 | «매입원가 · **적용 불가**» — 원가를 넣어도 이 숫자는 안 움직인다 | **warn** |
| 품목 있고 원가 전부 없음 | «미입력» | info |
| 품목 있고 **일부만** 원가 있음 | «일부 미입력 · N품목» | **warn** |

세 번째가 특히 무섭다 — 순이익이 «어중간하게» 틀려 있어서 알아채기 어렵다.

`warn`의 기준은 «사용자가 자기 몫을 다 했는데도 숫자가 틀린가»다. «아직 안 넣었을
뿐»(info)과 갈리는 자리이고, 적용 불가는 사용자가 할 수 있는 일이 **없다.**

### 실데이터 (2026-07)

```
cogs 0 · basis {items: 0, itemsWithoutCost: 0, hasOrderItems: false}
담지 못한 것 → [warn] 매입원가 · 적용 불가 · 0원
상품 화면    → SKU 61행 · 게이지 «원가 0/61 — 61개가 남았습니다»
              date 입력 61개 · 저장 버튼 61개
```

### 목업이 못 하던 셋 ([결함 57·58·59](목업-결함-발견분.md))

**58이 가장 무겁다.** 목업의 `costQuick`은 SKU당 숫자 하나라 «8월부터 원가가 올랐다»를
표현할 수 없고, 그대로 저장하면 **원가가 모든 과거 판매에 소급된다** — 8월에 원가를
고칠 때마다 **이미 마감한 7월 순이익이 바뀐다.** 001의 `cost_history`는 처음부터
`effective_from`을 갖고 있었으므로, 목업을 따라가면 스키마가 이미 아는 답을 화면이
되묻는 꼴이었다.

승인된 설계 그대로 넣었다 — SKU×kind×effective_from · 기본값 오늘 + **날짜 필드 상시
노출** · 같은 날짜 정정은 명시 확인 · `amount ≥ 0`(0은 받는다 — 증정품이 그렇다) ·
**SKU 단위** 게이지 · costAt «판매일 이전 이력 없으면 미상≠0».

### 원가는 조정이 아니다 (§15와 갈리는 자리)

조정은 **마켓이 준 사실을 우리가 고치는 것**이라 원본 위에 스택으로 쌓인다(LOCK 3).
원가는 마켓이 애초에 주지 않아 **고칠 원본이 없다** — 기준 데이터이고, 기준 데이터의
정상 경로가 «수동 편집 + 변경 이력»이다. 조정 레이어에 태우면 «원본 없는 조정»이
생겨 «대사는 원본끼리만 비교»의 전제가 무너진다.

Fact 인라인 편집 금지(LOCK 9)와도 충돌하지 않는다 — 원가는 Fact가 아니다.

### 정정은 묻고 나서 덮는다

같은 `(SKU · 종류 · 적용일)`이면 `addCost`가 **넣지 않고 지금 값을 돌려준다.** 화면이
그걸 받아 묻고, 답을 받아 `replace`로 다시 부른다. UPSERT로 만들었으면 코드는 짧아지지만
**오타 한 번이 이력 한 칸을 소리 없이 지운다** — 그 값은 Fact가 아니라 `row_shadow`가
없어 되찾을 수 없다.

가드는 화면과 **저장 경로 양쪽**에 있다. 화면만이면 하네스·CLI가 우회한다 —
파일명 캡처 가드를 `runImport`에 둔 것과 같은 판단이다.

### 임시물의 수명이 설계대로 관리됐다

`shell.ts`의 `UNBUILT`에서 «products»를 빼자 **`convert-gate`의 «배선 시 제거» 단언이
먼저 깨졌고**, 그것이 안내 마크업(`data-s21="unbuilt-products"`)과 구간 선언과
`DEVIATIONS` 항목을 함께 지우라는 신호였다. 적어두기만 했으면 아무도 안 지웠을 자리다.

## ★ 다음 손이 갈 곳 — 상품 화면 구조 (사용자 확정분 · 미착수) ★

**품목 적재가 이 블록의 선행 조건이었고 그건 닫혔다.** 아래 넷은 스코프가 커서
별도 블록으로 남긴다 — 특히 ④는 새 쓰기 연산이라 앞의 셋과 무게가 다르다.

### 실측이 먼저 말해 주는 것 (2026-08-14, `.tmp/pnl.sqlite`)

```
ESM   SKU 28 · 리스팅 35
11번가 SKU 27 · 리스팅 44
쿠팡  SKU  0 · 미연결 175          ← ②가 세워야 할 줄
두 채널에 걸친 SKU  0건            ← ★ 병합이 하나도 안 됐다 ★
제목 앞 12자가 같은 SKU 쌍  6건    ← ④의 후보. 실제 판정은 사람이 한다
```

**«두 채널에 걸친 SKU 0건»이 ④의 근거다.** 같은 실물 상품이 ESM에서 한 번, 11번가에서
한 번 SKU가 됐고 아무도 합치지 않았다 — 그래서 상품별 손익이 채널마다 쪼개져 보인다.

### 넷의 순서와 무게

| | 무엇 | 무게 |
|---|---|---|
| ① | 행 = SKU · 기본 전채널 합산 · **채널 칩으로 좁히기**(필터 + 통합 둘 다 — 대시보드와 같은 문법) | 조회 + 칩 마크업(§21 구간) |
| ② | **미연결 리스팅 묶음 행** — «미연결 175건 — 연결하면 상품별로 나뉩니다». 조용히 빼기 ❌ | 표에 합성 행 하나. ①과 같은 조회 |
| ③ | **배분 불가 광고비 별도 줄** — ESM 광고는 일별 총액이라 상품 귀속 불가. 임의 배분 ❌ | `기여이익 — 판정 계보`. 손익 3층의 «미배분 광고비»가 이미 그 자리다 |
| ④ | **SKU 병합** — 이력 보존 «이동»이다: `cost_history`·리스팅 재귀속, 삭제 ❌ | ★ 새 쓰기 연산 + 확인 다이얼로그 + 되돌리기 의미 판단 ★ |

### ④가 왜 별건인가

병합은 **삭제가 아니라 이동**이라는 요구가 이미 설계를 정한다:

```
리스팅        sku_id를 대상 SKU로 재귀속        (연결 저장소는 하나 · 헌장 B-5 ②)
cost_history  sku_id를 옮긴다 — 삭제 ❌
              그런데 UNIQUE(library, sku, kind, effective_from)가 있다
              → 같은 날짜에 양쪽 다 원가가 있으면 **충돌한다.** 사람에게 물어야 한다
상품(product) SKU가 빠져 비면 `purgeOrphanSkus`와 같은 판단이 필요하다
품목·주문     손대지 않는다 — 리스팅 경유라 재귀속만으로 소급 반영된다 ★
```

마지막 줄이 이번 품목 설계의 배당금이다. `fact_order_item.sku_id`를 비워 둔 덕에
**병합이 Fact를 한 줄도 건드리지 않는다** — 리스팅만 옮기면 과거 판매의 원가가
새 SKU 기준으로 다시 계산된다. 박아 넣었으면 8만 행 UPDATE + `row_shadow` 폭발이었다.

### ★ ④ SKU 병합 — 설계 지침 (사용자 확정, 2026-08-14) ★

미해결이던 질문 둘에 답이 왔다. **다음 블록은 이 다섯을 그대로 따른다.**

**1. 병합 = 리스팅 재귀속 + 원가 이력 이동 + 빈 SKU 처리. Fact 무접촉이 확정 배당금.**

그 성질을 **테스트로 단언한다** — 병합 전후 `fact_*` 전 테이블의 해시가 불변이어야
한다. 「안 건드리도록 짰다」와 「안 건드렸음을 잰다」는 다르고, 이 프로젝트는
`equivalence`에서 이미 후자를 택했다.

**2. 원가 충돌(같은 날짜에 양쪽 다 존재)은 자동 해소 ❌.**

충돌 목록을 보여주고 **사람이 남길 쪽을 고른다** — §20 확인 질문 문법(후보 + 근거)을
재사용한다. 안 골랐다고 병합을 막지 않는다: **«충돌 2건 보류»로 부분 병합을 허용**한다.
미응답이 진행을 막지 않는 것은 §20 레이아웃 절의 규율 그대로다 (안내지 검문이 아니다).

**3. 되돌림 — v1은 «다시 분리»로 충분한지부터 판단한다.**

이력 테이블 신설은 그 **판단 뒤에** 한다. 리스팅 재귀속의 역방향으로 되돌아가는지를
먼저 보고, 안 되는 경우(원가 이력이 합쳐져 원본을 잃는 자리)가 실재할 때만 새 저장을
연다. 저장을 먼저 짓고 필요를 나중에 찾지 않는다 — §21-5 «형식화 보류»와 같은 규율.

**4. 진입점 — 제목 앞 12자 동일 6쌍을 후보로 제시. 자동 병합 ❌.**

군집 엔진(`packs/…/listing-match.ts`, 상품부 완전 일치)을 재사용한다. 점수는
후보를 **줄 세우는 데만** 쓰고 확정에는 못 쓴다 — 리포지토리 쓰기 함수가 점수를
인자로 받지 않아 구조적으로 불가능한 그 성질을 병합에서도 유지한다.

**5. 존재 근거 — 「두 채널에 걸친 SKU 0건」이다.**

6쌍 처리가 끝나면 **채널 횡단 상품별 손익이 처음 성립한다.** 지금은 같은 실물 상품이
ESM과 11번가에서 각각 SKU라 상품별 손익이 채널마다 쪼개져 있다.

> ①②③은 한 묶음으로 갈 수 있다. ④는 위 지침대로, **3번의 판단부터** 하고 짓는다.

1. **`contribution`은 `ad`를 요구하지 않는다.** 요구하면 광고를 안 하는 셀러가

### 동반 규칙 둘 (§22-5)

- **grain 원칙** — 리스팅 생성 권한은 그 마켓의 **가장 가는 grain 문서에만**.

  «파일 역할» 필드는 신설하지 않는다

### 되돌리기 버튼 3상태 — 판정을 화면이 하지 않는다

화면이 «되돌릴 수 있다»를 스스로 계산하면 `assertUndoable`과 두 벌이 되고, 그 둘은

### 목업과 다르게 한 곳 셋

|---|---|---|---|

### 소요 시간은 «—»다

## ★ 화면 테스트가 데이터에 묶여 있었다 — 절대값을 걷어냈다 (2026-08-14) ★

사용자가 쿠팡 매출을 넣자 **테스트 7개가 빨개졌다.** 회귀가 아니라 **데이터가 는 것**이다:

```
expected 86909220 to be 7896500      ← 매출이 늘었다
expected 434 to be 146               ← 주문이 늘었다
'광고비'가 없다                        ← 사용자가 광고 batch를 되돌렸다
```

`dashboard-wiring`·`order-rows`가 **3b-0 CLI가 만든 DB 한 상태의 사진**을 정답지로
박아 두고 있었다. 위저드가 서기 전에는 그 DB가 변하지 않아 문제가 없었지만, 이제
**파일을 넣을 때마다 게이트가 빨개진다.** 그건 가드가 아니라 방해다.

**고친 방식** — 이 테스트들의 이름이 «화면 숫자 = 스냅샷 숫자»이므로 물어야 할 것도
그것이다:

| 전 | 후 |
|---|---|
| `toContain("7,896,500")` | `toContain(won(s.pnl.revenue))` — 화면이 쓰는 포맷터로 파생 |
| `toBe(146)` | `toBe(snap.orderCount)` — 목록과 스냅샷이 갈리지 않는가 |
| `toContain("광고비")` | 광고 데이터가 있을 때만. **0을 그리면 없는 비용을 있다고 말한다** |

**정답지는 버리지 않고 범위를 좁혔다** — 「ESM 주문 146건 = 7,896,500원 · 클레임 9건
388,700원」을 **연결 단위**로 단언한다. 손으로 검산한 값의 가치는 그대로 남고,
라이브러리 합계가 바뀌는 것은 정상이 된다.

> **교훈**: 기기 로컬 상태(`.tmp/pnl.sqlite`, gitignore됨)에 묶인 테스트는 그 상태가
> 변하지 않을 때만 절대값을 쓸 수 있다. 사용자가 앱을 쓰기 시작하면 그 전제가 깨진다 —
> **제품이 살아나는 순간 게이트가 먼저 부러진다.**

### ★ `npm run convert:gate`는 **늘 빨갛다** — 판정은 테스트가 한다 (2026-08-14 확인) ★

`/after-work`로 전 게이트를 돌리다 나왔다. **내가 깨뜨린 것이 아니다** — `af9ad85`
(이번 세션 시작 전) 워크트리에서 돌려 보니 **같은 6개 항목이 이미 빨갛다.**

```
af9ad85     6개 항목 불일치 · 동적 자리 991건 차이
05d37b3     6개 항목 불일치 · 동적 자리 997건 차이   ← 이번에 선언한 이탈만큼 늘었다
```

원인은 구조다. CLI(`tools/convert/gate.ts`)는 목업과 출력을 **그대로** 비교하고
**선언된 이탈을 모른다.** `DEVIATIONS`와 `S21_REGIONS`는 `tests/convert-gate.test.ts`
안에 있고, 그 테스트가 이탈을 반영해 대조한 뒤 **12개 전부 통과**한다.

> **§21 패치가 처음 올라간 날부터 CLI는 빨갰다.** gate.ts의 머리말이 그 사실을 이미
> 예고하고 있다 — *"§21 이탈은 별도 커밋에서 의도적으로 만들고, 그 커밋의 diff가 곧
> 목업과 다른 곳의 전체 목록이 된다."*

**왜 그냥 두면 안 되나**: 늘 빨간 게이트는 **사람을 훈련시켜 게이트를 무시하게
만든다.** 새 세션이 «전 게이트 확인»을 하다 이걸 만나면 없는 사고를 좇거나,
반대로 «원래 빨간 거»라며 진짜 회귀까지 넘기게 된다.

**처방(미착수)**: 이탈 선언(`DEVIATIONS`·`S21_REGIONS`)을 테스트에서 **모듈로 빼서
CLI와 공유**한다. 그러면 CLI가 테스트와 같은 답을 내고 둘 다 녹색이 된다.
지금 안 하는 이유는 이 세션의 범위 밖이고, 잘못 옮기면 **게이트의 보증 범위가
조용히 넓어지는** 변경이라 그 자체로 검토가 필요해서다.

**그동안의 규율**: 보존 게이트의 판정은 `npm test`가 한다. `convert:gate` CLI는
«선언되지 않은 이탈이 몇 건인지» 세는 참고 도구로만 읽는다.

### ★ 위저드 v1은 파이프라인을 **메인 스레드**에서 돌린다 — ADR-001 조건 2 위반 ★

조건 2는 «파싱은 Worker에서»다. 위저드 v1은 그러지 않는다. **조용한 위반과 기록된
부채는 다르므로** 여기 적는다.

```
실전 기준으로 순서를 정했다 — 8월 정산 파일은 수백 행이라 문제가 없다
그러나 쿠팡 광고(8만 행 · ~10MB)는 스모크 실측으로 9.5~10.4초 화면이 멈춘다
```

그동안의 방어는 **고지 하나**다 (`data-s21="import-big"` · 4MB 이상):

> *"큰 파일입니다. 가져오는 동안 화면이 잠시 멈출 수 있습니다 — 앱이 멈춘 것이
> 아니라 파일을 읽고 있는 중입니다. 창을 닫지 말고 기다려 주세요."*

**고지 없는 10초 프리즈는 강제 종료를 부른다.** 사용자의 자연스러운 반응이
"죽었나?"이기 때문이다. 미리 말하면 같은 10초가 "크니까 그렇구나"가 된다.
고칠 수 없는 것을 숨기지 않는 것이 지금 할 수 있는 정직이다.

**해소 조건**: Worker 이관. 그때 `import-big` 구간과 `BIG_FILE_BYTES` 상수를
함께 지운다 — 임시물의 수명을 §21-7과 같은 방식으로 묶어 둔다.

1단 스크린샷을 찍다가 "앱은 도는데 창이 안 보인다"를 만났고, 처음엔 제품 결함으로

**① `-16000 @ 157x25`의 정체 — 그냥 최소화된 창이다.**

```
+0s   2586x1656 @ (294,129)      vis=T  iconic=False   창 생성
+2s   2586x1656 @ (147,29)       vis=T  iconic=False   fit 적용 · 포커스
+4s   314x50    @ (-32000,-32000) iconic=True          ← 최소화
```

`-32000 @ 314x50`은 Windows가 **최소화된 창을 주차하는 표준 자리**다. 내 열거
스크립트가 DPI 비인식이라 200% 배율에서 절반으로 보여 `-16000 @ 157x25`가 됐다 —
**두 값은 같은 것이었다.** 도구가 만든 착시를 새 현상으로 읽은 것이다.

**② 최소화의 범인은 실행 방식이었다.**

```
에이전트 셸에서 Start-Process   →  +4s에 최소화된다
explorer.exe로 실행 (정상 실행)  →  90초 내내 정상. 상태 변화 0
```

우리 코드에 `minimize` 호출은 프론트·Rust 통틀어 **0건**이다(grep). 즉 앱이
아니라 **비대화형 셸에서 띄운 프로세스의 포커스 처리**가 만든 현상이었다.

> **교훈은 도구 쪽이다.** 앞으로 앱을 눈으로 확인할 때는 `explorer.exe <exe>`로
> 띄운다. `Start-Process`로 띄우고 "창이 안 뜬다"고 판정하면 없는 버그를 좇게 된다.
> 그리고 **측정 도구의 좌표계를 먼저 의심한다** — DPI 비인식 스크립트가 200%
> 기기에서 내놓는 숫자는 절반이다.

**다만 이 소동이 진짜 버그 하나를 잡았다** — `fit_to_work_area`. 아래 참조.

#### ★ 그런데 그 `fit_to_work_area`가 실제로는 맞추지 못하고 있었다 (2026-08-13 실측·수정) ★

`set_size`가 정하는 것은 **내부 크기**인데 목표를 `outer_size()` 기준으로 계산해
그대로 넘기고 있었다. 창은 **프레임만큼 더 커진다**:

```
setup    outer 2586x1671 · inner 2560x1600  →  프레임 26x71 물리 (13x35.5 논리)
         work_area 1704 물리 = 852 논리
호출     set_size(1293 x 828 논리)
결과     outer 1306 x 863.5 논리   ← 852를 여전히 넘는다
         center()가 그 큰 창을 가운데 두며 y = -3 — 제목 표시줄이 화면 위로
```

**작업영역에 맞추려고 만든 함수가 맞추지 못했다.** 게다가 이건 "높이가 조금 넘는다"가
아니라 **창을 잡을 수 없다**는 뜻이다(제목 표시줄이 화면 밖).

고친 뒤:

```
전   1306 x 863.5 논리 @ y = -3
후   1293 x 828   논리 @ y = +14.5      828 ≤ 852 · 전부 화면 안
```

같이 넣은 것:
- **`ensure_on_work_area`** — 크기를 안 줄인 경우에도 위치가 작업영역 밖이면
  중앙으로 되돌리고, `center()`가 작업표시줄을 모르므로 남는 어긋남은 직접 민다
- **`MIN_SIDE`(320)** — 계산이 어긋나 0에 가까운 값이 나오면 창이 있으나 마나가 된다

> **왜 8/13 반응형 검증에서 안 걸렸나**: 그때는 브라우저 뷰포트를 재는 검증이었고,
> **네이티브 창 기하는 그 게이트의 바깥**이었다. 게이트의 사각을 아는 것(작업 리듬 7)의
> 또 하나의 사례다. 창 기하는 모니터·배율·작업표시줄에 달려 테스트로 덮기 어려우므로,
> 개발 빌드에서 `[win] outer=… at …` 한 줄을 남겨 회귀가 눈에 띄게 했다.

### 막고 있던 것은 `dispCards`가 아니라 **`layout` 파생 값 한 가족**이었다

추적의 끝은 예상과 조금 달랐다. `dispCards`(목업 L276·L5558)는 표시 설정 메뉴의

```

`showHero`만 앞선 세션에서 손으로 되살려져 있었고 **나머지 가족이 통째로 빠져

함께 나오므로 하나가 빠졌으면 대개 전부 빠져 있다.

> 복원이 아니라 새 결함이다.

### 정직성이 화면으로 넘어왔다 — `pnlGaps`

CLI가 손익 5줄 밑에 늘 출력하던 **"이 숫자가 담지 못한 것"**을 화면도 그린다.
숫자만 옮기고 단서를 두고 오면 사용자는 −8,192,734를 완성된 순이익으로 읽는데,
지금 그것은 한 연결의 광고비를 다른 연결의 매출에서 뺀 미완성 합성이다 (A-5).

**판정은 `src/core/profit/gaps.ts` 하나뿐이다.** 원래 CLI 출력부 안에만 있어서
화면을 배선하면 조건이 두 벌이 될 자리였다. 단일 계산기 원칙이 계산기 →
조회 계층(`snapshot`) → **단서 계층**까지 확장된 것이다.

```
주문에 이어지지 않은 정산   수수료 빠짐    983,085원
발생일이 추정인 클레임      날짜 추정      9건
매입원가 · 고정비·운영비    미입력         0원
여러 연결이 섞인 기간       연결 3개
```

두 가지가 CLI보다 나아졌다:

- **마켓 이름을 지웠다** (LOCK 4). "11번가 정산인데 11번가 주문이 없다"가 아니라
  "정산 N건이 주문에 이어지지 않는다"로 쓴다. core는 마켓을 모른다
- **채널 혼재를 판정한다.** CLI는 픽스처를 알기에 이 문장을 무조건 출력했다.
  이제 `contributingConnections`(스냅샷 신규)를 세서 **연결이 하나로 정리되면
  단서가 스스로 사라진다**. 하드코딩된 경고문은 그러지 못한다

`joined.count`를 실측했더니 **0**이고 `all.count`는 128이 아니라 **106**이었다
(나머지는 `settled_on`이 7월 밖). 조건을 `count === 0`에서 `all − joined > 0`으로
넓혔지만 **오늘 출력은 달라지지 않았다** — 넓힌 이유는 절반만 조인될 때 나머지
수수료가 조용히 빠지는 것을 막기 위해서다.

### 보존 게이트에 **선언된 이탈**이 생겼다

목업 카피가 LOCK 10을 어기는 자리가 실재했다(§1-46). 게이트 규칙이 "diff 0"이라
선택지는 *게이트를 빨간 채로 두기* 아니면 *이탈을 선언하기*뿐이었고,
**빨간 게이트는 곧 꺼지므로** 후자를 만들었다 — `tests/convert-gate.test.ts`의
`DEVIATIONS`.

게이트는 무뎌지지 않고 오히려 강해졌다: 선언 밖의 차이는 여전히 실패하고,
**선언이 낡아도**(목업에 그 문구가 더는 없어도) 실패한다. 2단 §21 패치가 이
장치를 바로 쓴다.

`src/core`에 **마켓 이름 가드**를 세웠다(`core-env-neutral.test.ts`). 스키마

**고쳤다** — 헤더 부제가 상수 `"2026년 8월"`(shell.ts `TITLES.dash`, 목업 L3667)이라
**7월 데이터 위에 8월이 적혀** 있었다. 히어로는 "2026년 7월 순이익"이었으니 한 화면에

테스트가 지킨다. **빈 값이면 모르고 넘어가지만 틀린 값은 사용자가 믿는다.**

**아직 남았다 — 전부 `Template.tsx`의 정적 텍스트라 `DEVIATIONS` 선언이 필요하다:**

## 2단 — §21 패치 완료 (2026-08-13) · 워터폴만 3단 이행

| 항목 | 상태 |
|---|---|
| 도넛 → 가로 막대 | ✅ `0c78b94` |
| 스파크라인 제거 | ✅ `51035b8` |
| 비교 문장 조건부화 | ✅ `51035b8` |
| 워터폴 신설 | **3단 이행** — 사유: 검증층 부재 ([§21](§21-표면-근거-재배치.md)) |

**워터폴을 미룬 이유가 규율이다.** §21 패치의 진입 조건이 "실제 창을 띄워 눈으로
확인하며 친다"였는데, 워터폴은 "변화(전월 대비)"에 답하고 DB엔 7월 한 달치뿐이라
**오늘 지으면 렌더되지 않는다.** 가짜 이전 달을 넣는 것은 3a 게이트(시드 잔재 0건)를
§21 검증을 위해 어기는 순환이라 기각했다.

### 도넛 폐기가 실데이터로 소급 입증됐다

```
광고비 15,700,534 = 매출 7,896,500의 198.8%
```

**도넛은 이걸 그릴 수 없다** — 조각 합이 항상 원을 채우므로 "매출을 넘는 비용"이
비율 뒤로 사라진다. 가로 막대로 바꾸고서야 숫자로 떴다. 분모는 둘로 나눴다 —
**막대 길이는 최댓값 기준**(크기 비교), **옆의 %는 매출 대비**. §21에 각주로 남겼다.

### 게이트가 2층이 됐다

| 층 | 쓰는 자리 | 무엇을 보증하나 |
|---|---|---|
| **구간 선언** (`S21_REGIONS`) | 도넛처럼 통째로 갈아엎는 곳 | "같다"가 **아니다.** "바뀐다고 선언돼 있다"뿐 |
| **연속 구간 splice** (`DEVIATIONS`) | 스파크라인처럼 국소적인 곳 | 선언한 구간 밖은 여전히 1:1 |

보증 범위를 부풀리지 않는 것이 요점이다 (ADR-007 계열). 그리고 **가드의 가드**를
붙였다 — `indexOfRun` 유일성 강제(흔한 값을 선언하면 엉뚱한 자리를 갈아끼우고도
녹색이 된다) · `data-s21` 표식 개수 검사(오타로 큰 구간이 조용히 대조에서 빠지는 것을
막는다).

**첫 실전 수확**: LCS 차분으로 편집 8곳을 뽑아 검토했더니 **의도한 구간 밖 편집이
0건**이었다. 그게 이 검토의 값이다.

### 작업 리듬 9번이 설계대로 작동했다

`not.toContain("388,700원")`으로 박아둔 부재가 가로 막대와 함께 깨졌고,
**단언을 뒤집는 행위 자체가 완료 선언**이 됐다. 부재가 미결이 아니라 검증된
상태였기 때문에 가능했다.

| **프로파일 레지스트리** | 모든 호출부가 프로파일 하나를 **하드코딩**한다. `mapping_profile` 테이블은 읽지도 쓰지도 않는다 |

곳이 없다. 읽지 못한 것을 표시해야 한다는 **LOCK 6의 살아 있는 구멍**이다.

그리고 §18이 요구하는 시트 선택도 지금 형태로는 안 된다 — `listSheets()`는 **호출자가 0명**이고

> ★ **LOCK 6 구멍 — 그 뒤 메워졌다** ★ 이 문단을 쓸 때 ESM의 **매핑 오류 5건**은

#### 남은 판정 하나 — 파일 바이트를 어떻게 얻나

세 갈래이고, **ADR-003 재검토 트리거 2**가 이미 방향을 적어 뒀다:

> *"프론트엔드에서 임의 조회가 꼭 필요한 동선 발견 → 플러그인이 아니라 **커맨드 추가**로 푼다"*

| 길 | Rust 변경 | 새 IPC 표면 | 비고 |
|---|---|---|---|
| **`<input type="file">`** | 없음 | **0** | 웹 표준. 드래그드롭까지 하려면 `dragDropEnabled: false`가 필요하다 |
| plugin-dialog + 자체 바이트 커맨드 | 크레이트 1 + 커맨드 1 | 커맨드 1 | 네이티브 다이얼로그. ADR-003 트리거 2의 문자 그대로 |
| plugin-fs | 크레이트 1 | **넓다** (read/write/mkdir/remove/watch) | ADR-003이 `tauri-plugin-sql`을 기각한 논리에 정면으로 걸린다 |

> ⚠ **한때 「플러그인을 붙이면 ACL이 소급 적용돼 앱이 깨진다」고 적었는데 틀렸다.**
> `src-tauri/permissions/`가 없어서 지금 `db_*` 커맨드가 ACL 면제인 것은 맞지만,
> **플러그인 추가는 그 디렉터리를 만들지 않는다** — 플러그인 권한은
> `capabilities/default.json`(지금 `["core:default"]`)에 문자열 하나로 들어간다.
> 지뢰는 실재하되 **다른 행위**(앱 레벨 `permissions/` 신설)가 밟는다.

**연결 화면에서 그 규율이 쓰기까지 늘어났다** — `writeThenReload`(`app/data.ts`).
쓰기 뒤 화면 상태를 손으로 갱신하지 않고 **다시 조회한다.** 손으로 갱신하는 순간
화면이 DB와 다른 것을 믿기 시작하고, 그건 카운트를 한 곳에서만 세기로 한 것과
같은 이유로 막아야 한다.

MappingProfile.displayName   "11번가" · "ESM (G마켓·옥션)" · "쿠팡"
      ↓ 연결 생성 시
connection.display_name       ← 화면은 이것만 본다
```

LOCK 4와 충돌하지 않는다 — 이름이 사는 곳이 `core/`가 아니라 **팩의 프로파일**이다.
core는 문자열을 옮길 뿐 무엇인지 모른다. 연결 화면이 생기면 사용자가 덮어쓰는
값이 되고(§10-2), 여기 있는 것은 **기본값**이다.

`tests/order-rows.test.ts`의 "내부 키가 화면에 새지 않는다"가 두 화면을 한꺼번에
지킨다 — **다음 화면에서도 같은 실수가 나오기 때문**에 화면별이 아니라 공통으로 뒀다.

### 주문 화면에서 `—`로 남은 것 (unbuilt 기록)

§21-3의 *"빠진 기능은 미구현으로 기록한다"*에 따라 남긴다. 전부 **데이터가 없어서**이지
숨긴 것이 아니다:

| 열 | 왜 비었나 | 채워지려면 |
|---|---|---|
| 마켓 주문번호 | 전용 컬럼이 없다. `source_key`는 내부 키(주문번호+상품번호)라 노출 ❌ (C-4) | 마이그레이션 + 프로파일 매핑 + 재가져오기 |
| 상품 · 수량 | `fact_order_item`이 비어 있다 — ESM 프로파일이 품목까지 매핑하지 않는다 | 프로파일 확장 |
| 기여이익 | **주문 단위 배분이 없다.** 계산기가 기간 단위로만 계산한다 | 임의 배분을 넣으면 계산기가 둘이 된다 (단일 계산기 LOCK) — 배분 규칙이 정해질 때 |

### 클레임은 주문에 붙지 않는다 — 붙일 수 없다

```
주문   source_key        = 주문번호 + 상품번호   (자연키)
클레임 order_source_key  = 주문번호만
```

모양이 달라 조인이 성립하지 않는다. 접두 매칭하면 상품이 여럿인 주문에서 조용히
잘못 붙으므로, §14-1대로 **성격이 보이게 따로 세웠다.** 11번가 정산의 미연결과
같은 계열의 사실이고, 목록 155행이 적재 행 수와 정확히 같다는 것이 그 증거다.

## 상품 연결 (§21-6) — 2c 완료. **2d가 다음 손**

### 왜 이 화면이 먼저인가 — 실측이 순서를 정했다

"상품 화면(원가 입력)을 먼저"로 정했다가 **실측이 전제를 뒤집었다**:

```
product 0 · sku 0 · marketplace_listing 0 · fact_order_item 0 · cost_history 0
cost_history.sku_id 는 NOT NULL          → 원가는 SKU에만 붙는다
loadPnlSnapshot 의 base.cogs 는 기본 0    → cost_history 가 손익에 배선돼 있지도 않다
```

상품 화면만 지으면 **넣을 대상도 없고 넣어도 숫자가 안 변한다** — 워터폴을 미룬 것과
같은 검증층 부재다. 그래서 사슬을 세웠다:

```
① 프로파일 확장 → 리스팅 적재     ✅ 완료
② 리스팅 → SKU (연결 화면)        ← 지금 여기
③ 원가 입력 UI (상품 화면)
④ 원가 → 손익 (costAt · ADR-009 ①-보완 2)
```

④까지 닫히는 순간이 **순이익에 원가가 처음 반영되는 순간**이고, 그때 7월 원가가
문서 답변이 아니라 앱 사용 기록으로 남는다.

### ① 완료 — 리스팅 86개

```

ESM      42개  grain=product   (상품번호만 — 옵션 컬럼이 없다)

**입도가 채널마다 다르고 그것을 프로파일이 선언한다** (마이그레이션 004의 `grain`).
같은 실물 상품이 ESM에선 1개, 11번가에선 옵션 수만큼 N개다 — **결함이 아니라
비대칭의 정상 표현**이고 연결 화면에서 N:1로 나타난다.

### ★ 등급 예측이 틀린 게 아니라 **단위가 달랐다** ★

**새 숫자를 볼 때마다 "이건 무엇의 개수인가"를 먼저 묻는다.**

### ★ U+0001이 화면으로 샐 뻔했다 — 공용 안전 테스트가 이사한 이유 ★

`listing_key`는 컬럼 여럿을 **U+0001로 이어 붙인 합성 키**다 (ADR-006 · `KEY_SEP`).
목업이 `done` 탭에 그리던 `{r.key}`를 그대로 두면 **보이지 않는 제어문자**가 HTML에
섞여 나간다. `source_key`와 같은 계열의 내부 키인데 이름이 달라 눈에 안 띄었다.

막은 방법이 둘이다:

```
core        조회가 keyParts를 나눠 준다 — 화면은 구분자를 알 필요가 없다
테스트      LEAKS에 KEY_SEP 추가 (리터럴 ❌ — 상수를 import한다)
```

**리터럴로 적으면 안 된다는 것을 실수로 증명했다.** 처음에 손으로 적은 것은 U+0001이
아니라 **빈 문자열**이었고, `includes("")`는 늘 참이라 검사가 통째로 뒤집힐 뻔했다.
지금은 상수를 import하고 **그 상수가 정말 U+0001인지 먼저 확인**한다 (작업 리듬 8).

그래서 «내부 키가 화면에 새지 않는다»가 `order-rows.test.ts` →
**`tests/screen-safety.test.ts`**로 옮겼다. 내용은 한 곳 그대로이고 이름만 바꿨다 —
공용으로 둔 이유가 *"다음 화면에서도 같은 실수가 난다"*였는데 실제로 났고, 그때
파일 이름이 `order-rows`에 묶여 있는 것이 그 목적을 가렸다.
**새 화면은 그 파일의 `VIEWS`에 한 줄을 더한다. 새 파일을 만들지 않는다.**

### ★ 2d 완주 (2026-08-14) — 리스팅 86개 전부 연결 ★

```
리스팅        86 전부 linked (미연결 0)
sku/product   61 / 61        (고아 1개 정리 후)
cost_history  0              ← ③이 채울 자리

SKU당 리스팅  1개=43 · 2개=13 · 3개=4 · 5개=1     ← 군집이 작동했다
채널별        11번가 44리스팅 → 27 SKU
              ESM   42리스팅 → 34 SKU
```

**클릭이 86 → 61로 줄었다.** 5개짜리 묶음도 한 번에 들어갔다.

#### 결함 — 멱등성 부재 (고침)

같은 카드의 `[새 SKU로 등록]`을 두 번 누르자 **두 번째가 새 SKU를 하나 더 만들고
리스팅을 옮겨**, 첫 번째가 리스팅 0개짜리 고아로 남았다 (sku 62 · 리스팅 붙은 SKU 61).

첫 진단은 *"쓰기 도는 동안 버튼을 안 막았다"*였는데 **반쪽이었다.** 결함의 정확한
이름은 **멱등성 부재**다 — 같은 요청이 두 번 도착했을 때 두 번째가 거부되거나 같은
결과를 내야 하는데 그러지 않았다. 더블클릭 말고도 같은 요청이 두 번 갈 경로는
코드가 늘면 또 생긴다.

```
잠금(useRef)          UX      — 두 번째 클릭을 아예 안 받는다
createSkuForListings  정확성  — 이미 linked인 리스팅은 건너뛰고, 남는 게 없으면 만들지 않는다
purgeOrphanSkus       정리    — 리스팅 0 · 원가 0인 SKU를 치운다 (원가 있으면 남긴다)
```

정리는 **일회성 스크립트가 아니라 함수 + 테스트**다. 고아는 한 번 있었던 사고가
아니라 연결을 옮기면 언제든 생기는 상태이기 때문이다. 부르는 도구:
`npx tsx tools/harness/purge-orphans.ts [DB] [--yes]` (기본은 보여주기만).

#### ② 채널 간 SKU 중복 — ③의 설계 입력으로 기록

11번가 27 + ESM 34 = 61. **같은 실물 상품이 채널마다 따로 SKU가 됐다.** 접기는
채널을 넘지 않으므로(작업 리듬 12) 설계상 예상된 결과이고, 채널을 넘는 통합은
원래 *제안*(clear/contested)에서 일어나게 돼 있었다.

> **③(원가 입력)이 이걸 만나는 자리가 있다.** 「리스팅 1개짜리 SKU 43개」 중 상당수가
> 채널 쌍둥이일 것이고, **같은 원가를 두 번 치게 되는 순간이 사용자가 중복을 발견하는
> 자연 지점**이다. 그러므로 «SKU 병합»은 연결 화면이 아니라 **상품 화면의 기능**일 수
> 있다 — 지금 정하지 않는다. §20 피드백 + ③ 설계 때 함께 판정한다.

#### ★ §20 피드백 — 루프의 첫 회전 (2026-08-14) ★

| 물은 것 | 답 | 그래서 무엇을 했나 |
|---|---|---|
| 제안이 실제로 보였나 | **"이렇게 보였던 거 같아"** — 보였다 | 시각 위계가 아니라 **버튼 위계** 문제로 확정 → 아래 |
| 채널 쌍둥이를 인지했나 | **인지 못 했다** ("다 괜찮았다") | 중복은 지금 **보이지 않는다.** ③에서 원가를 두 번 치는 순간이 발견 지점 |
| 클릭 61번 체감 | **괜찮았다** | 군집·일괄이 충분했다. 클릭 수는 지금 병목이 아니다 |

**버튼 위계가 61번의 원인이었다.** 제안은 보였는데 파란 primary가 카드 머리에 늘
떠 있고 옳은 행동인 `[연결]`은 아래 24px 보조 버튼이었다. §21-6은 이미
*"후보가 없을 때의 기본값"*이라고 적어 뒀는데 「기본 액션」을 「항상 primary」로
읽은 것이 오독이었다 — **사양이 옳았고 구현이 틀렸다.**

```
none       [새 SKU로 등록] primary
clear      [연결] primary            후보 하나가 «미리 선택된» 것의 시각적 표현
contested  둘 다 보조                미리 고르지 않는다 — 사람이 고른다
```

> **두 번째 답(«인지 못 했다»)이 설계 판단을 확정했다.** 중복 SKU를 연결 화면에서
> 풀려고 하면 사용자가 문제를 못 보는 상태에서 해결을 강요하는 꼴이 된다.
> **«SKU 병합»은 상품 화면(③)의 기능**이고, 같은 원가를 두 번 치는 순간이 자연
> 발견 지점이다 — 그때 화면이 *"이 둘 같은 상품인가요?"*를 물으면 된다.

**미결**: [결함 51](목업-결함-발견분.md) — «1+1»이 토큰화에서 증발해 묶음과 단품이
100% 동점이 된다. 지금은 `contested`라 미리 골라지지 않아 피해가 막혀 있다(작업 리듬 12).
고치면 임계값 재측정이 따라오므로 ③의 «SKU 병합»과 함께 판정한다.

개별 번호를 보여준다. 보기 싫으면 그때 §21 개정으로 다룬다 — 지금 임의로 채우지 않는다.

### 2c에서 할 일 — 마크업

목업 `linking`은 **리스팅-평면**이라 §21-6 셋을 담지 못한다:

| 추가 | 방식 |
|---|---|
| 군집 카드 (`같은 상품으로 보이는 옵션 N개`) | 신규 요소 → `data-s21` 구간 선언 |
| `[새 SKU로 등록]` + 일괄형 | 신규 요소 → 구간 선언 |
| 후보 행에 **겹친 토큰** 한 줄 | 기존 행에 한 칸 → `DEVIATIONS` 값 치환 시도, diff 보고 판정 |
| done 탭 카피 수정 | 결함 대장 §1 등재 (아래) |

**카피 수정 (승인됨)** — 목업의 *"다음 가져오기부터 자동으로 붙습니다"*는 절반만
참이다. ADR-012가 보증하는 것은 같은 `listing_key`의 보존이지 새 리스팅의 자동
연결이 아니다. 새 옵션은 `unlinked`로 태어난다.

```
→ "같은 리스팅이 다시 오면 이 연결이 유지됩니다"
```

결함 46("동기화" 카피)과 같은 계열(§17-3)이라 **결함 대장 §1에 등재**하고 2c에서
함께 고친다. 자동 연결을 만들지 않는 이유는 작업 리듬 12다 — 새 옵션이 같은 SKU인지는
사실이 아니라 판단이고(옵션마다 원가가 다를 수 있다), 검토 전에 접으면 사람은 접힌
것만 본다. **정직함의 가격은 클릭 한 번**이다 — 새 옵션이 todo에 뜨면 기존 SKU가
`clear` 후보로 바로 잡힌다 (`tests/linking-view.test.ts`가 그 동작을 지킨다).

### ②의 완료 기준 (승인분)

```
a. 실데이터 렌더 — 엔진 분류와 화면 표시가 1:1        ✅ tests/linking-screen.test.ts
b. 쓰기 첫 관통 — [새 SKU로 등록] → sku 생성 + 4필드   ✅ tests/listing-write.test.ts
c. 되돌리기 무관 — 연결 후 배치 되돌리기 → 연결 생존    ✅ 같은 파일
d. done 탭 카피가 사실인가                            ✅ 수정 완료 (자리가 둘이었다)
e. 내부 키 부재 — U+0001이 이 화면 HTML에 0회         ✅ tests/screen-safety.test.ts
f. 사용자 실기기 클릭 동선 확인                        ← 2d. 남은 하나
```

**a는 두 상태로 판정했다** — 콜드스타트(SKU 0 · 카드 61 · 제안 전부 `none`)와 등록
후(11번가 27장을 SKU로 → 카드 34 · clear 4 · contested 13 · none 17). 두 번째 상태는
`VACUUM INTO`로 뜬 사본에서 돈다.

> **`copyFileSync`로 사본을 뜨다 한 번 깨졌다.** vitest가 테스트 파일을 병렬로 돌리므로
> 다른 파일이 `pnl.sqlite`를 열고 있는 순간의 파일 복사는 **SQLite 잠금을 통째로 무시**해
> 찢어진 스냅샷을 만든다 — 리스팅 86개 중 39개만 담겼고, 같은 순간 `settlement-rows`가
> 원본에서 SQLITE 오류를 봤다. `VACUUM INTO`는 SQLite 자신이 만드는 일관된 사본이라
> 동시 독자와 안전하게 공존한다.
>
> **39는 "조회가 틀렸다"가 아니라 "내가 만든 DB가 반쪽"이었다** — 값이 이상하면
> 도구부터 의심한다(작업 리듬 8). 실데이터를 쓰는 테스트가 늘면 또 만날 자리라
> 여기 남긴다.

## ~~다음 손이 갈 곳 — DC 템플릿 변환기 (승인됨)~~ → 완료 (2026-08-13)

변환기와 보존 게이트가 섰다. 아래는 그때의 설계 기록이다 — 조건 4개가 어떻게
지켜졌는지 확인할 때 본다.

**손으로 옮기지 않는다.** `FlowBase.dc.html`은 443KB이고 `renderVals()`가 1,900줄이라,
손 이식은 "조용히 어긋나도 아무도 모르는" 경로다. 기계로 옮기고 **보존 게이트**가
어긋남을 잡는다 — `equivalence` 하네스와 같은 발상이다 (ADR-007).

핸드오프 §4-1이 변환표를 이미 완성해서 줬다:

```
{{ path }}        →  {expr}          <sc-if value>  →  {cond && …}
<sc-for list as>  →  .map()          $index         →  .map((x, i) =>)
<x-import>        →  import          <x-dc>·hint-*  →  삭제
```

### 파이프라인은 3단으로 고정한다 (조건 2)

```
① 변환 (기계, 100% 충실)  →  ② 보존 게이트 통과  →  ③ §21 패치 (손, 커밋 분리)
```

**§21 이탈을 변환 도중에 끼워 넣지 않는다.** 도넛→가로막대·스파크라인 제거를
변환기가 하면 게이트가 "의도된 이탈"과 "사고"를 구분하지 못한다.
§21 패치는 **별도 커밋**이고, 그 커밋의 diff가 곧 *"목업과 의도적으로 다른 곳의
전체 목록"*이 된다 — 나중에 "이거 왜 목업이랑 달라?"의 답이 git log에 산다.

### 보존 게이트가 비교하는 것 (조건 1)

정적 구조 수준에서 본다. **JSX를 렌더한 DOM이 아니다** — `{{ path }}` → `{expr}`는
값이 아니라 **자리**의 치환이기 때문이다.

| 대상 | 왜 |
|---|---|
| 텍스트 노드 | 카피가 바뀌면 안 된다 |
| 클래스 | Vector DS 클래스가 살아 있어야 한다 |
| 토큰 | `var(--…)` 참조 보존 |
| **인라인 `style` 속성값** | ★ 이 목업은 **토큰이 인라인 style에 박힌 코드**다 (드롭존 L313~331이 그렇다). 클래스만 비교하면 style 드리프트가 샌다 |
| **동적 자리의 개수·경로** | 1:1 대응을 봐야 표현식 누락까지 잡힌다 |

요약: **구조와 정적 속성의 완전 보존 + 동적 자리의 1:1 대응.**

### 손 이식한 드롭존은 첫 시험이다 (조건 3)

`src/app/App.tsx`의 온보딩은 내가 **손으로** 옮긴 것이다. 변환기가 나오면 그 출력과
대조한다. 다르면 —

> **변환기가 기준이 아니라 목업이 기준이다.**
> 둘 다 목업 원문(L313~331 · L5696~5704)과 대조해서 어긋난 쪽을 고친다.
> 손 이식이 맞고 변환기가 틀렸을 수도 있다. **시험의 정답은 항상 원본이다.**

### `renderVals` 1,900줄 분해 — 변환기 스코프 **밖**이다 (조건 4)

여기가 이식 전체에서 "조용히 어긋나기" 제일 좋은 자리다 — 계산 로직을 옮기다
살짝 다르게 쓰는 것. 방어선은 이미 있다: **`computePnl`이 유일한 계산기**다
(단일 계산기 LOCK).

```
분해 규칙
  데이터 접근  →  리포지토리로
  계산        →  computePnl **호출로 대체**한다 (옮기지 않는다)
  남는 것     →  표시용 포맷팅뿐
```

### ★ 배선 규율 — 화면은 스냅샷의 소비자다 ★

**화면 코드에서 리포지토리를 직접 조회하지 않는다.**

조회는 `src/core/profit/snapshot.ts`의 `loadPnlSnapshot` 같은 **공용 함수 하나**를
거친다. 화면은 그 결과를 포맷할 뿐이다.

왜 이게 규율이어야 하는가 — 조건 3("화면 숫자 = CLI 숫자")을 **검사 항목에서
구조적 보장으로** 올리기 때문이다. 검사는 어긋난 뒤에 잡지만, 구조는 어긋날
경로 자체를 없앤다. 단일 계산기 원칙(C-3)이 계산기를 넘어 **조회 계층까지**
확장된 것이다.

> 이 규율이 없으면 두 번째 화면(정산)을 배선하는 세션이 **"간단한 조회니까"**
> 하고 직접 쿼리를 박는 순간 구조가 샌다. 조인 조건 하나가 어긋나도 두 화면이
> 다른 답을 내고, 그 차이는 아무도 모르게 쌓인다.

새 화면이 새 집계를 필요로 하면 **스냅샷을 넓힌다** — 화면에 쿼리를 두지 않는다.

### 경계 테스트는 양방향으로 건다

ADR-011의 `tests/core-env-neutral.test.ts`가 그 본보기다:

```
src/core/*        node:를 쓰면      실패
어댑터 2개        node:를 안 쓰면   실패   ← 이쪽이 빠지기 쉽다
```

어댑터인데 아무것도 안 쓰면 **그 파일의 존재 이유가 없다**. 경계를 한쪽에서만
지키면 반대쪽이 무의미해지고, 언젠가 "이 어댑터 뭐하는 거지" 하고 지워진다.

**renderVals 안의 산수가 JSX 쪽으로 한 줄이라도 복사되면 두 번째 진실이 생긴다.**

**기기를 바꿀 때는 `/after-work`로 닫고 옮긴다.** 닫지 않고 옮기면 다음 기기에서
`/before-work`가 "원격이 뒤처져 있다"거나 갈라진 상태를 보고하게 되고, 그때는
합치는 방법을 물어본다 — 자동으로 rebase하지 않는다.

## 이 프로젝트의 작업 리듬

세션 1·2에서 반복해 효과를 본 것들이다. 계속 이렇게 간다.

1. **지시서의 전제도 실측으로 확인한다.** 세 번 틀렸다 — xlsx CVE 주석 위치,
   대조표의 ragged/헤더행/TOTAL 3건, B-2가 전제한 자연 키의 존재.
   정정은 환영받는다
2. **가설은 세우고 실측으로 기각한다.** "파생 시트는 수식으로 만들어진다"는 그럴듯했지만
   실측에서 깨졌다 (ADR-002 §4)
3. **가드는 부러뜨려 확인한다.** 안 잡는 가드는 없느니만 못하다 (G-1).
   **그리고 "안 깨졌다"도 해석해야 한다** — 가드가 무른 것일 수도, 그 코드 경로가
   애초에 안 쓰이는 것일 수도 있다. 둘은 전혀 다른 결론이다 (ADR-007)
4. **결정은 ADR로.** 조건·정정·측정 결과·재검토 트리거까지 한 문서에
5. **추정으로 넘어간 자리는 나중에 그대로 버그가 된다.** 실제 사례:
   97,600원 차이를 처음엔 "7월 밖 3행"이라고 **추정하고 넘어갔다.** 그때 실측했으면
   거기서 잡혔을 것이 며칠 뒤 "모든 기간 조회가 매달 말일을 잃는다"는 구조적 결함으로
   드러났다. 이 원칙은 지시서의 전제(1번)뿐 아니라 **자기 작업 이력에도** 적용된다
6. **교차 검증은 양방향이다.** 사용자의 헌장 대비 diff가 U-1을, 우리 테스트가 대조표
   오류 3건을 잡았다
7. **게이트는 선언된 질문만 답한다.** 마크업 게이트 녹색 ≠ 동작함. 화면은 실제
   뷰포트(375·M·폴드·배율)로 띄워 눌러봐야 잡히는 결함 층이 따로 있다 —
   결함 5건(44·45·배선 3건)이 전부 **전 게이트 녹색**에서 나왔다.
   교훈은 "게이트가 무르다"가 아니라 **각 게이트의 사각을 아는 것**이다.
   보존 게이트는 "마크업이 목업과 같은가"를 물었고 그 질문에는 완벽히 답했다 —
   빈 배선·빈 탭바·안 열리는 더보기는 그 질문의 **바깥**이라 통과가 정상이었다.
   3번의 "안 깨짐에도 해석이 필요하다"(ADR-007)와 같은 계열이다

   **사례가 셋이 되면서 패턴이 됐다:**

   | 못 잡은 게이트 | 놓친 것 | 왜 바깥이었나 |
   |---|---|---|
   | 보존 게이트 (마크업) | 빈 배선·빈 탭바·안 열리는 더보기 | "목업과 같은가"만 물었다 |
   | 전 테스트 녹색 | `node:` 의존으로 웹뷰에서 죽는 파이프라인 | Node에서만 돌려봤다 (ADR-011) |
   | 반응형 검증 (375·M·폴드) | 창이 작업영역을 넘어 제목줄이 화면 밖 | **브라우저 뷰포트**를 쟀다. 네이티브 창 기하는 그 바깥 |

   한 줄로: **검증층은 겹겹이고, 각 층은 자기 아래층을 보지 못한다.**
   그러므로 "어느 게이트가 녹색인가"가 아니라 **"이 결함이 어느 층에 사는가"**를 묻는다

   ### ★ 7-a. 시간 축 — **검증은 검증 시점의 세계만 증명한다** (2026-08-14 승격) ★

   7번은 «게이트가 무엇을 안 보는가»를 공간으로 물었다. 같은 원리에 **시간 축**이 있다.

   되돌리기는 실기기에서 한 바퀴를 돌았고 통과했다. 그런데 그 회차가 증명한 것은
   **«품목이 없는 되돌리기»**였다 — `fact_order_item`이 0행이던 세계의 되돌리기다.
   품목이 생기는 순간 `undoBatch`는 부모를 자식보다 먼저 지우고 FK가 통째로 막는다.
   테스트도 실기기도 거짓말을 하지 않았다. **세계가 자란 것이다.**

   > **스키마가 자라면 그 스키마 위에서 통과한 모든 게이트를 다시 읽어야 한다.**
   > 「테이블을 더하면 `row_shadow` 트리거도 더한다」(대기목록)가 이미 그 계보이고,
   > 이번에 **삭제 순서**가 같은 목록에 합류했다.

   실전 적용: 새 Fact 테이블·새 FK·새 라우팅을 더할 때 **«이걸 전제로 통과했던
   게이트가 무엇인가»**를 먼저 센다. 늘 답이 있고, 보통 되돌리기가 그중 하나다.

   ### ★ 7-b. **우연히 맞는 순서는 선언된 순서가 아니다** (2026-08-14 승격) ★

   `undoBatch`가 쓰던 순서는 «`FACT_TABLES` 배열에 적힌 대로»였다. 그 배열의 순서에는
   **뜻이 없다** — 「적재할 수 있는 테이블의 목록」일 뿐이다. 지금까지 맞아 보였던 것은
   품목이 0행이라 순서가 관측되지 않았기 때문이다.

   그래서 뜻이 있는 순서는 **이름을 갖는다**(`DELETE_ORDER`). 이름 없는 배열 순서에
   불변식을 얹으면 다음 사람이 알파벳순으로 정렬하는 날 조용히 깨지고, 그때 깨진
   자리에는 «왜 이 순서였나»가 적혀 있지 않다.

   > **우연히 맞는 것은 틀린 것의 특수형이다.** 지금 맞는지가 아니라 **왜 맞는지가
   > 코드에 적혀 있는지**를 묻는다.

   ### ★ 7-c. **적대적 검토는 커밋 전이 정위치다** (2026-08-14 승격) ★

   품목 적재를 «typecheck 통과 · 619/619 · 게이트 녹색»으로 보고하고 커밋한 **뒤에**
   적대적 검토를 돌렸다. 반증을 거쳐 **17건이 살아남았다** — 그중 넷은 사용자의
   바로 다음 동작 위에 있던 blocker였다. 순서가 뒤집혔던 것이다.

   > **게이트 녹색은 커밋 «자격»이지 검증 «완료»가 아니다.**

   7번이 «게이트는 선언된 질문만 답한다»였다면 이것은 그 실무 귀결이다: 선언되지
   않은 질문을 **누가 언제 하는가**. 답은 «적대적 검토가, 커밋 전에»다.

   실무 순서로 고정한다:

   ```
   구현 → 게이트 녹색 → **적대적 검토** → 살아남은 것 처리 → 커밋
                          ↑ 여기가 빠져 있었다
   ```

   비용이 크므로 **모든 커밋에 붙이지 않는다.** 붙이는 조건은 셋 중 하나다 —
   ① 스키마·적재 경로를 건드렸다 ② 손익 숫자가 움직인다 ③ 사용자가 다음 동작으로
   그 코드를 바로 밟는다. 이번 작업은 셋 다였다.
8. **측정 도구의 좌표계를 먼저 의심한다.** 실측이 원칙인 만큼, **틀린 실측은
   틀린 추정보다 위험하다** — 숫자가 붙어 있어서 믿게 된다. 사례 둘:

   | 도구가 보여준 것 | 실제 | 원인 |
   |---|---|---|
   | 프로세스 열거에 잡힌 무관한 항목들 | 앱 트리는 그중 일부 | 이름만으로 걸렀다 → `app.exe` **자식 트리만** 세도록 고침 |
   | 창이 `-16000 @ 157x25`에 있다 | `-32000 @ 314x50` (최소화 표준 주차 자리) | 스크립트가 **DPI 비인식** → 200% 기기에서 모든 좌표가 절반 |
   | 리스팅이 86개가 아니라 **39개** | 86개 맞다 | 테스트가 `copyFileSync`로 뜬 사본이 **반쪽**이었다 |
   | `git status`가 «다 담겼다»고 말한다 | §22 판정 모듈 2개가 **통째로 빠져 있었다** | `.gitignore`의 `coverage/`가 **모든 깊이**에 적용 → `src/core/coverage/` 삼킴 |

   후자는 **없는 버그를 하루치 좇게 만들 뻔했다.** 새 도구로 이상한 숫자를 보면
   현상을 설명하기 전에 **도구가 그 숫자를 어떤 단위로 말하는지**부터 확인한다

   > ★ **디렉터리 이름이 도구 예약어와 겹치면 ignore 패턴의 적용 깊이를 확인한다** ★
   >
   > `coverage/`는 테스트 커버리지 산출물의 **관용 이름**이라 어느 리포에나 있다.
   > 앞에 `/`가 없으면 gitignore는 **모든 깊이**에 적용하므로, 도메인 모듈이 우연히
   > 같은 이름을 가지면 조용히 사라진다.
   >
   > **이 저장소에 아직 남아 있는 같은 모양의 규칙**(실측 2026-08-14) —
   > `dist/` · `build/` · `out/` · `.cache/` · `.turbo/` 등 깊이 무한 적용 12건.
   > 전수 조사에서 **지금 걸리는 소스 파일은 0건**이지만, `src/**/build/` 같은
   > 디렉터리를 만드는 날 같은 일이 난다. (`node_modules/`·`fixtures/raw/`·`.tmp/`는
   > 중첩까지 무시하는 것이 **의도**라 그대로 둔다.)
   >
   > 전수 확인은 이렇게 한다:
   >
   > ```bash
   > find src tools tests docs -type f \( -name '*.ts' -o -name '*.tsx' -o -name '*.json' \) -exec git check-ignore -q {} \; -print
   > ```
   >
   > 위험한 이유는 **이 기기에서는 전부 통과한다**는 것이다. 파일이 디스크에 있으니
   > 테스트도 타입체크도 녹색이다. 깨지는 것은 **다음 기기가 clone한 다음**이고,
   > 그때는 원인이 며칠 전 커밋에 있다.
   >
   > 그래서 새 디렉터리를 `src/` 아래 만들면 **`git check-ignore -v <파일>`을 한 번
   > 돌린다.** 커밋 전에 잡으면 한 줄이고, 놓치면 다음 세션의 첫 30분이다.

   > ★ **살아있는 DB의 파일 복사는 사본이 아니다 — 스냅샷은 DB 엔진에게 시킨다** ★
   >
   > `copyFileSync`는 **SQLite의 잠금을 통째로 무시한다.** vitest가 테스트 파일을
   > 병렬로 돌리므로 다른 파일이 `pnl.sqlite`를 열고 있는 순간의 복사는 찢어진
   > 스냅샷을 만든다. 같은 순간 원본 쪽 `settlement-rows`도 SQLITE 오류를 봤다 —
   > **복사가 읽기까지 방해한 것**이다.
   >
   > ```
   > copyFileSync   OS가 바이트를 옮긴다      트랜잭션 경계를 모른다
   > VACUUM INTO    SQLite가 사본을 만든다    동시 독자와 안전하게 공존
   > ```
   >
   > 원인 귀속이 핵심이다: **39는 "조회가 틀렸다"가 아니라 "내가 만든 DB가
   > 반쪽"이었다.** 조회를 의심했다면 멀쩡한 코드를 하루 뒤졌을 것이다.
   > 실데이터를 쓰는 테스트가 늘수록 다시 만날 자리다
9. **현재의 한계는 단언으로 박는다 — 미래의 변경이 그 테스트를 뒤집게.**
   기대한 값이 화면에 없을 때 길은 셋이고, 앞의 둘은 함정이다:

   ```
   ① 마크업에 몰래 넣는다        →  승인 없는 발명 (헌장 E-1)
   ② 테스트를 조용히 완화한다     →  게이트 후퇴. 사라진 이유는 아무도 모른다
   ③ 부재를 사실로 단언한다       →  ★
   ```

   실제 사례: 비용 구성의 원 단위 금액(`388,700원`)은 호버 툴팁 안에만 있어
   서버 렌더 HTML에 없다. 이걸 `not.toContain`으로 박아뒀다 —
   **§21 가로 막대가 들어오는 순간 그 테스트가 정확히 뒤집힌다.**

   요점은 *부재가 미결이 아니라 **검증된 상태**가 된다*는 것이다. 미결은 잊히지만
   단언은 깨진다. 그리고 깨질 때 "왜 이게 없었는지"의 설명이 테스트 주석에 붙어 있다.
10. **미분화의 단언 — 아직 갈리지 않은 두 개념을 갈리기 전에 각자 자리에 앉힌다.**

    같은 값을 내지만 **묻는 것이 다른** 두 개념이 있다. 오늘 값이 같으면 사람은
    같은 것이라고 믿고 하나로 합치거나, 합치지 않더라도 왜 둘인지 잊는다. 그러다
    데이터가 늘어 값이 갈리는 날 **두 화면이 그냥 모순으로 보인다** — 그때는
    어느 쪽이 맞는지 아무도 모른다.

    실제 사례:

    ```
    손익  settlement.joined   "이 **기간의 주문**에 이어졌나"  (수수료는 주문 귀속)
    정산  row.linked          "**어떤 주문에든** 이어지나"      (정산 행의 성질)
    오늘  둘 다 0             ← 갈리지 않았다
    ```

    갈리기 전에 **둘 다 0임을 테스트로 못박았다.** 갈리는 날 그 테스트가 먼저
    깨지고, 그때가 두 숫자의 관계를 설명할 기회다. 9번이 *부재*를 단언한다면
    10번은 *미분화*를 단언한다 — 둘 다 **미래의 변경이 테스트를 깨우게** 하는 장치다.
11. **우연히 맞는 것은 틀린 것의 특수형이다.**

    값이 맞는지만 보면 통과하지만, **왜 맞는지**를 보면 안 맞을 조건이 이미
    존재하는 경우가 있다. 그건 "지금은 맞다"가 아니라 **"아직 안 틀렸다"**이다.

    실제 사례 — 주문 화면의 `주문 146건`:

    ```
    fact_order 의 grain 은 order-line 이다 (source_key = 주문번호 + 상품번호)
    실측: 행 146 · 주문번호 146종      → 주문당 상품이 하나라서 두 수가 같다
    ```

    라벨이 맞은 것은 **이 파일이 우연히 1:1이라서**다. 상품이 여럿인 주문이 하나라도
    들어오면 `146`은 주문 수가 아니라 줄 수가 되고, 라벨은 조용히 거짓이 된다.
    값을 확인하는 데서 멈추지 않고 **그 값이 성립하는 조건**까지 봐야 잡힌다.

    같은 계열의 앞선 사례: 도넛이 "매출 대비 198.8%"를 그릴 수 있어 보였던 것 —
    조각 합이 항상 원을 채우도록 정규화되니 **어떤 값을 넣어도 그림이 그럴듯했다.**
    3번("안 깨짐도 해석이 필요하다")의 값 버전이다.
12. **사람 검토를 거치는 제안은 확률적이어도 되지만, 검토 전에 구조를 접는 묶음은
    결정론적이어야 한다.**

    같은 화면 안에서도 확신의 기준이 층마다 다르다:

    ```
    제안 (유사도)        사람이 하나씩 본다        → 확률적이어도 된다
    군집 (상품부 일치)   보기 전에 여럿을 하나로 접는다 → 결정론적이어야 한다
    ```

    제안이 틀리면 사람이 고르지 않으면 그만이다. 그러나 **묶음이 틀리면 사람은
    이미 하나로 접힌 것을 본다** — 서로 다른 상품이 한 SKU가 된 것을 알아채려면
    접기 전 상태를 상상해야 하고, 그건 사람이 가장 못하는 일이다.

    그래서 리스팅 군집은 유사도가 아니라 **상품부 완전 일치**로 묶었다.
    일반화하면: **되돌리기 쉬운 자리에는 추측을 허용하고, 되돌리기 어려운 자리는
    확실한 것만 한다.**
13. **세는 단위를 먼저 선언한다 — 숫자를 볼 때 "이건 무엇의 개수인가"부터 묻는다.**

    같은 대상을 세는데 **단위가 다른** 두 숫자가 계속 나온다. 리스팅-평면으로 그려진
    목업을 카드-단위로 옮기는 동안 이 구분이 **세 번** 걸렸다:

    ```
    탭 배지    todo가 리스팅 수인가 카드 수인가        → 카드 (일의 단위)
    제안 등급  예측 clear 6 · 실측 clear 4             → 리스팅 42 vs 카드 34
    군집 머리  "옵션 N개"의 N                          → 리스팅 (접힌 원자료)
    ```

    셋 다 **둘 다 맞고 묻는 단위가 다른** 경우였다. 틀린 답이 아니라 다른 질문의
    답이므로, "왜 안 맞지"로 시작하면 없는 버그를 좇는다. 문서의 숫자를 인용할
    때도 **그 숫자를 만든 스크립트가 무엇을 순회했는지**까지 본다 — `listing-match-dist.ts`는
    리스팅을 돌고 화면은 카드를 돈다.
14. **보이지 않는 값을 검사할 때는 검사 대상부터 검사한다.**

    `KEY_SEP`은 U+0001이라 소스에서 **보이지 않는다.** 화면 누출 검사에 그 문자를
    손으로 적었는데 실제로 적힌 것은 **빈 문자열**이었고, `includes("")`는 늘 참이라
    검사가 통째로 뒤집힐 뻔했다. 지금은 상수를 import하고 **그 상수가 정말
    U+0001인지 먼저 단언**한다.

    ```
    리터럴로 적는다        →  보이지 않으니 검토가 불가능하다
    상수를 import한다      →  한 곳에서 정의되고 한 곳에서 검증된다
    ```

    8번(측정 도구의 좌표계를 의심한다)의 **검사 도구 버전**이다. 눈으로 확인할 수
    없는 것을 다룰 때는 "검사가 통과했다"가 "검사가 실행됐다"를 뜻하지 않는다.
