# ADR-003 — SQLite 바인딩 선택

- **상태**: 채택
- **일자**: 2026-08-12
- **범위**: 세션 2 저장 계층, 세션 3 Tauri 접합
- **전제 조건 해소**: Rust 툴체인(1.97.1 stable-msvc) + MSVC Build Tools 설치 완료. 실측 가능

---

## 결정

**`rusqlite`를 Tauri 커맨드 뒤에 둔다. `tauri-plugin-sql`은 쓰지 않는다.**

```
TS 파이프라인 (webview)  →  IPC (좁은 커맨드)  →  Rust + rusqlite  →  SQLite
```

프론트엔드는 SQL을 만들지 않는다. `loadChunk`·`undoBatch`·`countInRange` 같은
**이름 있는 커맨드**만 부른다.

---

## 왜 — 성능이 아니라 커맨드 표면 때문이다

`tauri-plugin-sql`은 프론트엔드가 임의 SQL을 실행하게 한다:

```ts
await db.execute("SELECT * FROM fact_order")   // 막을 방법이 없다
```

세션 2 합격 기준 4는 "전체 테이블 적재 경로가 **없음**"을 요구했고, 우리는 그것을
`Repository`에 `selectAll`·`raw`·`exec`가 **존재하지 않는 것**으로 증명했다
(`tests/driver-boundary.test.ts`). 조회는 기간을 필수 인자로 받고 `active_*` 뷰만
허용한다.

플러그인을 쓰면 **그 증명이 통째로 무의미해진다.** 아무 코드나 전체 테이블을 끌어올 수
있으면 "경로가 없다"는 문장이 거짓이 된다. 헌장 B-2(전체 메모리 적재 금지)를 지키는
장치가 규율이 아니라 구조여야 하는 이유다.

부수적으로, 로컬퍼스트 앱이 사용자의 정산 데이터를 들고 있다. 프론트엔드에 임의 SQL
권한을 주는 것은 그 자체로 넓은 표면이다.

---

## 실측

### 적재 처리량 — 80,137행 × 17컬럼, 청크 1,000행, 청크당 트랜잭션 1개

| | 적재 시간 | 비고 |
|---|---|---|
| `node:sqlite` | **1,700~1,950ms** | 종단 게이트에서 (매핑+적재) − (매핑만)로 분리 |
| `rusqlite` (bundled 3.46.0) | **545~692ms** | 동일 스키마·청크·PRAGMA로 재현 |

약 **3배**. 벤치 코드는 `dev/sqlite-bench`에 있고 세션 2의 스키마·PRAGMA·청크 크기를
그대로 쓴다.

### 메모리 — 직접 비교가 안 된다는 점을 밝혀둔다

| | |
|---|---|
| `node:sqlite` 증가분 | **+18MB** (종단 게이트에서 적재 유무로 분리) |
| `rusqlite` 프로세스 전체 | **53.7MB** (행 생성용 `Vec<Row>` 약 20MB 포함) |

두 숫자는 성격이 다르다 — 앞은 245MB짜리 프로세스에 얹힌 **증가분**이고 뒤는 **전체**다.
SQLite 자체의 절대 발자국은 어느 쪽이든 30MB 안팎으로 보이며, 이 차이는 결정을 가르지
않는다.

### `tauri-plugin-sql`은 벤치하지 않았다

제대로 재려면 Tauri 앱과 IPC 왕복이 필요하다. **그런데 이 결정은 처리량으로 갈리지
않는다** — 커맨드 표면에서 이미 갈린다. 재지 않은 것을 잰 척하지 않는다.

---

## ★ 이 측정이 세션 3 개시 조건을 바꾼다 ★

세션 2 조건 3은 이렇게 걸려 있었다.

> 종단 게이트는 node:sqlite 기준으로 1차 판정하되, **"드라이버 교체 후 재측정"을
> 세션 3 개시 조건에 넣는다** — 적재 성능은 드라이버에 따라 달라질 수 있으므로.

그 전제를 실측했더니 **드라이버는 레버가 아니다.**

```
파싱 + 정규화              ~232MB
+ 매핑                     ~245MB   (+13MB)
+ SQLite 적재              ~263MB   (+18MB)
                            ────────
예산                        256MB
```

**적재를 0으로 만들어도 245MB로 이미 예산의 96%다.** rusqlite로 바꿔 18MB를 전부
webview 밖으로 내보내도 245MB가 남고, 기준 2는 통과하지 못한다.

부수 관찰 하나 — **편차도 적재가 만든다.** 적재를 빼면 편차가 ±3.5MB에서 **±0.5MB**로
떨어진다(244.9·244.4·245.3). 앞서 "4회 중 1회 초과"의 흔들림은 SQLite 쪽 GC였다.

**따라서 기준 2의 실제 레버는 JS 파이프라인의 232MB다.** 드라이버 교체는 그 뒤에 오는
일이지 선행 조건이 아니다. 세션 3 개시 조건을 이렇게 고쳐 제안한다:

> ~~드라이버 교체 후 종단 재측정~~
> → **JS 파이프라인 메모리 축소 후 종단 재측정.** 드라이버 교체는 별도로 진행하되
> 기준 2의 전제 조건에서 뺀다

---

## 따름 조건

1. **드라이버 계약은 그대로다.** `src/core/store/driver.ts`의 `Driver` 인터페이스를
   rusqlite 커맨드 뒤에 구현한다. 리포지토리와 그 위쪽은 손대지 않는다 —
   `tests/driver-boundary.test.ts`가 그 경계를 지킨다
2. **PRAGMA는 SQL 수준 그대로 옮긴다.** `PRAGMAS` 상수를 Rust 쪽에서도 같은 순서로
   적용한다. 벤치가 이미 그렇게 했다
3. **커맨드는 좁게.** 새 커맨드를 추가할 때 "이걸로 전체 테이블을 끌어올 수 있나"를
   먼저 묻는다. 답이 예면 다시 설계한다
4. **청크는 1,000행.** 실측으로 정한 값이며(ADR-001), 교체 후 재측정해 유지 여부를 본다

---

## 재검토 트리거

1. 적재가 실사용에서 병목 → 청크 크기·`prepare_cached` 재조정
2. 프론트엔드에서 임의 조회가 꼭 필요한 동선 발견 → 플러그인이 아니라 **커맨드 추가**로 푼다
3. Tauri가 `rusqlite` 통합 방식을 바꿈 → 드라이버 구현 파일 하나만 영향받는다
4. JS 파이프라인 축소 후 종단 재측정에서 여전히 초과 → 파이프라인 일부의 Rust 이관 재검토
   (ADR-001 조건 1의 단계별 교체 조항)
