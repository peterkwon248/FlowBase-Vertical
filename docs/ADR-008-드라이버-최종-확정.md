# ADR-008 — SQLite 드라이버 최종 확정: 어디서 도는가

날짜: 2026-08-12 · 상태: **결정 대기 (사용자 확인 필요)** · 관련: [ADR-003](ADR-003-sqlite-바인딩.md) · [ADR-001](ADR-001-파이프라인-스택.md)

[ADR-003](ADR-003-sqlite-바인딩.md)이 `rusqlite`를 골랐고, 판정 기준은 성능이 아니라
**커맨드 표면**이었다. 이 문서는 그 결정을 Tauri 통합 시점에 확정한다. 기준은
사용자가 지정한 대로 **통합 단순성 · 유지보수 비용**이다.

그런데 확정하려고 보니 ADR-003이 세운 따름 조건 하나가 성립하지 않는다.

---

## ★ 정정 — "드라이버 교체는 구현 파일 하나 교체"가 아니다 ★

ADR-003 따름 조건 1은 이렇게 적혀 있다.

> **드라이버 계약은 그대로다.** `src/core/store/driver.ts`의 `Driver` 인터페이스를
> rusqlite 커맨드 뒤에 구현한다. 리포지토리와 그 위쪽은 손대지 않는다.

**성립하지 않는다. `Driver` 계약이 전부 동기이기 때문이다.**

```ts
run(...params): RunResult        // Promise가 아니다
get(...params): Row | undefined
all(...params): Row[]
transaction<T>(fn: () => T): T   // 동기 함수를 받아 값을 돌려준다
```

실측 확인: `driver.ts`·`driver-node.ts`에 `Promise`·`async`가 **한 번도 나오지 않는다.**
`repository.ts`는 `return this.db.transaction(() => …)`로 트랜잭션의 반환값을 그대로 쓴다
(2곳).

**Tauri IPC(`invoke`)는 비동기다.** 웹뷰에서 도는 코드가 Rust의 SQLite를 부르면 반드시
`Promise`가 된다. 동기 계약을 비동기 백엔드로 구현하는 방법은 없다.

두 번째 문제도 같은 자리에서 나온다. `loadChunk`는 **행마다** `stmt.run()`을 부른다
(`repository.ts:124`). 이게 IPC가 되면 #13에서 **80,137번의 왕복**이다. 청크당 한 번이
아니라 행당 한 번이다.

즉 드라이버 교체는 파일 하나가 아니라 **저장 계층의 동기/비동기 성격**과
**적재 경로의 입도(粒度)**를 건드리는 일이다. 이걸 모르고 3a를 진행하면 b·c 작업을
전부 다시 해야 한다.

## 선택지

| | 무엇 | 통합 단순성 | 유지보수 비용 |
|---|---|---|---|
| **A. 리포지토리를 비동기화** | `Driver`·`Repository`를 `async`로. Rust는 SQL을 받아 실행만. 대량 적재만 `load_chunk` 벌크 커맨드로 분리 | 중 — 기계적 리팩터 1회 | **낮음. 구현이 하나다** |
| **B. 리포지토리를 Rust로 이관** | 도메인 커맨드(`import_chunk`·`undo_batch`·`query_*`)로 좁게 노출 | 낮음 — 재작성 | **높음. TS/Rust 두 벌** |
| **C. Node 사이드카** | 로컬 Node 프로세스가 `node:sqlite`를 그대로 씀 | 낮음 — 패키징·프로세스 관리 | 중. 런타임 의존 추가 |
| **D. WASM SQLite** | 웹뷰 안에서 동기 실행. 계약 무변경 | 높음 — 코드는 그대로 | 높음. DB가 OPFS에 갇히고 파일 백업·Rust 벤치가 무의미해짐 |

### 권고: A

- **구현이 하나다.** 리포지토리 로직·되돌리기 의미론(ADR-004)·`row_shadow` 트리거를
  TS 한 벌로 유지한다. B는 같은 규칙을 두 언어로 쓰게 만들고, 그게 정확히
  "조용히 어긋나는" 자리다
- **비동기화는 기계적이고, 경계가 이미 테스트로 잠겨 있다.**
  `tests/driver-boundary.test.ts`가 가짜 드라이버로 리포지토리를 검증하므로
  리팩터가 샜는지 바로 드러난다
- **행당 IPC 문제는 벌크 커맨드로 푼다.** 적재는 이미 columnar 청크(ADR-007)라
  청크 하나를 통째로 넘기기에 알맞다 — **청크당 1회 IPC**다. 나머지(조회·되돌리기·
  메타데이터)는 호출 빈도가 낮아 비동기 왕복이 문제되지 않는다
- **`node:sqlite`는 남는다.** 테스트와 하네스는 계속 그걸 쓴다(비동기 계약을 만족하는
  얇은 래퍼). 게이트 2 실측이 무효화되지 않는다

### 기준 4(전체 테이블 적재 경로 부재)는 어떻게 되는가

ADR-003이 `tauri-plugin-sql`을 버린 이유는 **프론트엔드 기능 코드가 임의 SQL을
실행**할 수 있어서였다. A에서도 웹뷰가 SQL을 보내지만, **보내는 주체가 리포지토리
하나**이고 화면 코드는 리포지토리 메서드만 본다.

정직하게 말하면 기준 4의 증명은 원래도 드라이버가 아니라 **리포지토리 API 표면**이
지고 있었다 — `node:sqlite`에서도 누군가 `db.prepare("SELECT * FROM fact_order")`를
쓸 수는 있었다. A는 그 상태를 유지한다. 강화하려면 커맨드에서 SQL을 허용 목록으로
제한하는 방법이 있고, 그건 별도 결정으로 미룬다.

## 미결 — 사용자 확인이 필요하다

권고는 A지만, **저장 계층 전체를 비동기로 바꾸는 것은 되돌리기 어려운 결정**이고
3a의 b·c 작업이 전부 그 위에 얹힌다. 확인 없이 진행하지 않는다.

확인이 필요한 것은 하나다: **A로 간다 — 리포지토리를 비동기화하고 적재는 청크 벌크
커맨드로 좁힌다.** 맞나?

## 재검토 트리거

1. 비동기 리팩터 중 `transaction()` 계약이 깨지는 자리 발견 → 트랜잭션을 Rust 쪽
   단일 커맨드로 올리는 방안 재검토
2. 청크 벌크 커맨드의 IPC 직렬화가 새 병목으로 측정됨 → 청크를 전송 가능
   (transferable) 버퍼로 넘긴다. `kinds`가 이미 `Uint8Array`다 (ADR-007)
3. 조회 지연이 체감됨 → 화면별 집계를 도메인 커맨드로 내리는 부분 이관 (B의 일부)
