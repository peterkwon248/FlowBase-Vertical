# ADR-020 — 조정 레이어의 쓰기 경로 (정산 조정 팝오버)

- 날짜: 2026-08-20
- 상태: 채택
- 사건: 사용자가 세션 직후 물었다 — *"원본 파일의 테이블을 직관적으로 수정하는
  공간은 없는 느낌인데."* 코드로 확인한 답은 「값을 고치는 자리 = 조정 레이어이고,
  저장·계산은 서 있는데 **화면만 없다**」였다. `adjustment` 표는 001부터 있고
  `addAdjustment`/`adjustmentsFor`/`applyAdjustments`도 있는데 **앱 소비처가 0**이다.
  배선의 남은 일 6건(`adjDraft`·`adjWhy`·`setAdjDraft`·`setAdjWhy`·`adjPosLeft`·
  `adjPosTop`)이 전부 이 팝오버다.
- 관련: [ADR-004](ADR-004-되돌리기-의미론.md)(되돌리기 × 조정) ·
  [ADR-005](ADR-005-기준데이터-이력-범위.md)(이력 범위) ·
  헌장 B-3(원본 불변) · E-2(=LOCK 9, Fact 인라인 편집 금지) · B-5③(조정 저장소는 하나)

## 문제 — 실측

**이것은 조정 레이어의 쓰기 경로를 처음 여는 일이다.** 그래서 LOCK 3(원본 불변)과
LOCK 9(Fact 인라인 편집 UI 금지)에 동시에 닿는다. 아무 칸이나 열면 그게 곧 인라인
편집이고, 그 순간 LOCK 9는 글자만 남는다.

그리고 **목업과 스키마가 세 축에서 정면으로 어긋나 있다.** 배선하려면 어느 쪽이
이기는지를 먼저 정해야 한다.

| 축 | 스키마(001) | 목업(FlowBase.dc.html) |
|---|---|---|
| 단위 | 개별 Fact 행 × 필드의 **절대값 대체**(`previous_value`→`new_value`) | 정산일×채널 **집계행**의 금액 **delta 스택** (`rowKey = d + ":" + c.id`, `payout + stackSum`) |
| 사유 | `reason TEXT NOT NULL` | placeholder 「사유 (선택)」 · 없으면 「사유 없음」 |
| 취소 | `revoked_at` — 주석: 「조정을 되돌리는 것도 조정이다 — 삭제하지 않고 무효화 표시만 한다」 | trash 버튼 = `stack.filter` **물리 삭제** · 「원본으로 복원」 = 스택 전체 비우기 |

추가 실측 셋:

- **화면 행은 Fact 행이 아니다.** `loadSettlementRows`는
  `GROUP BY s.settled_on, s.connection_id`의 결과를 돌려준다
  ([rows.ts:78](../src/core/settlement/rows.ts:78)). 목업 표의 한 줄도 같은 단위다.
- **`applyAdjustments`는 절대값 대체다** — `value[a.field] = castToColumn(a.new_value, …)`
  ([effective-value.ts:65](../src/core/store/effective-value.ts:65)). 스택이 여럿이면
  **마지막 것이 이긴다.**
- **`SettlementRow`는 `connection_id`를 안 들고 있다** — 헌장 C-4를 근거로 일부러
  뺐다([rows.ts:26](../src/core/settlement/rows.ts:26)). 조정을 쓰려면 대상 키가 필요하다.

## 결정

### A1: 조정 대상은 **집계행**이다 — (정산일, 연결)

`target_table = "settlement_daily"` · `target_connection_id = connection_id` ·
`target_source_key = settled_on`.

- **왜 Fact 행이 아닌가**: 화면에 행 선택 UI가 없다. 집계행 하나에 얹은 delta를
  N개 Fact 행에 나눠 붙이는 배분 규칙은 **임의값을 만들어내는 일**이고, 그렇게 만든
  숫자는 어느 원본과도 대조되지 않는다. 행 선택 UI를 새로 그리는 쪽은 목업 이탈
  + §21 신설 구간이 필요한데, 사용자가 요구한 것은 그것이 아니다.
- **`settlement_daily`는 실재하지 않는 테이블 이름이다.** 합성 키를 만들지 않고
  기존 컬럼 둘을 그대로 쓴다 — `settled_on`이 곧 행 키이고 연결은 별도 컬럼이므로
  **기존 인덱스 `idx_adjustment_target(target_connection_id, target_table,
  target_source_key)`가 그대로 맞는다.** 마이그레이션 0건.
- **001의 규율은 유지된다** — 「배치가 아니라 행에 붙으므로 되돌리기로 행이 사라져도
  조정은 남고, 같은 `source_key`가 다시 들어오면 다시 적용된다」. (정산일, 연결)은
  재가져오기·되돌리기에 무관하게 안정된 키라 이 성질이 그대로 성립한다.

### A2: 값 의미론은 **delta**다 — 절대값 대체가 아니다

`new_value` = 부호 있는 delta(문자열) · `previous_value` = 조정 시점의 원본 합계
**스냅샷(감사용, 계산에 쓰지 않는다)** · 유효 지급액 = `SUM(net_amount) + SUM(활성 delta)`.

두 가지가 delta를 강제한다:

1. **재가져오기.** 헌장 B-3은 「재가져오기 시 원본만 갱신, 조정 유지」다. 절대값
   대체에서 이 문장은 **「갱신된 원본을 무시한다」**가 된다 — 마켓이 정산서를
   고쳐 보내도 옛 `new_value`가 스택 위에서 이긴다. delta는 새 원본 위에 그대로
   얹혀서 문장이 뜻대로 성립한다.
2. **스택의 개별 취소.** 목업은 항목마다 trash 버튼을 준다. 절대값에서 **중간
   항목을 빼는 것은 정의되지 않는다**(마지막 것만 의미가 있다). delta는 어느 것을
   빼도 나머지 합이 답이다. 즉 목업의 UI 자체가 delta를 전제하고 있다.

### A3: 두 의미론은 **`target_table`로 갈린다** — 섞이지 않는다

| `target_table` | 의미론 | 계산 주체 | v1 소비처 |
|---|---|---|---|
| `settlement_daily` | delta 합산 | `loadSettlementRows`의 SQL | 정산 화면 |
| `fact_*` | 절대값 대체 | `applyAdjustments` | **없음** |

`applyAdjustments`는 손대지 않는다. 「스키마에 없는 필드는 유효값에 얹지 않는다」는
기존 가드가 있어 섞여 들어와도 조용히 틀리지 않는다. **두 의미론이 한 표에 사는
것이 이 결정의 비용이고**, 그 대가로 마이그레이션 0건과 「조정 저장소는 하나」
(헌장 B-5③)를 지킨다. 시험이 이 경계를 지킨다.

### A4: 여는 필드는 `net_amount` **하나뿐이다**

`fact_settlement`의 본문 컬럼은 `gross`·`fee`·`vat`·`shipping`·`net` 5종이지만
**v1은 지급액(`net_amount`)만 연다.** 나머지 4종과 키·날짜·공통 6컬럼은 잠근다.

- 목업 팝오버가 얹는 곳이 지급액 하나다(`payout + stackSum`).
- **이것이 LOCK 9와의 경계선이다.** 「고칠 수 있는 칸」이 늘어날수록 조정은
  인라인 편집에 수렴한다. 여는 칸마다 *왜 이 칸인가*를 답할 수 있어야 하고,
  지급액의 답은 「마켓이 준 지급액이 실제 입금과 다를 때 그 차이를 남기는 자리」다.
  다른 4종에는 아직 그 답이 없다.

### A5: 사유는 **필수**다 — 목업의 「(선택)」이 진다

빈 문자열·공백만은 거부한다. `reason TEXT NOT NULL`은 빈 문자열을 통과시키므로
**가드가 화면 쪽에 있어야 실효가 있다.**

- 조정 레이어를 복제 시트 대신 고른 근거 ③이 「`reason`이 NOT NULL이라 왜 고쳤는지가
  반드시 남는다」였다. 사유를 선택으로 열면 그 근거가 무너지고 NOT NULL은 장식이 된다.
- 이건 시각 취향이 아니라 **장부의 무결성**이다. 사유 없는 조정은 나중에 오타와
  구별되지 않는다.
- **목업 이탈이다** — placeholder 「사유 (선택)」→「사유 (필수)」 + 「조정 추가」
  버튼에 비활성 표현. [목업-결함-발견분 66번](목업-결함-발견분.md) 등재.

### A6: 취소는 **무효화**다 — 물리 삭제하지 않는다

trash = `revokeAdjustment`(`revoked_at` 마킹) · 「원본으로 복원」 = 그 행의 활성
조정 **전부 무효화**(한 트랜잭션).

- 001의 주석이 이미 그렇게 정해 뒀고, ADR-004가 「이 앱은 이력 덮어쓰기를 전부
  금지해 왔다」고 못박았다.
- **목업 이탈이 아니다.** `adjustmentsFor`가 `revoked_at IS NULL`로 거르므로
  사용자가 보는 것은 목업과 같다 — 항목이 스택에서 사라지고 지급액이 다시 계산된다.
  달라지는 것은 DB에 흔적이 남는다는 사실뿐이고 화면에 나타나지 않는다. 그래서
  결함 대장 등재 대상이 아니다.

### A7: `SettlementRow`가 `connectionId`를 **들되 그리지 않는다**

C-4는 「`batch_id`·`connection_id` **사용자 화면 노출** 제거」다 — 화면이 그리지
말라는 것이지 뷰 타입이 몰라야 한다는 뜻이 아니다. `LinkingListing.listingKey`가
같은 선례다(내부 키를 경고 주석과 함께 운반하고, 화면은 `keyParts`를 쓴다).
조정의 대상 키이므로 운반은 불가피하고, 같은 모양의 경고 주석을 단다.

### A8: 유효값을 소비하는 곳은 **정산 화면뿐이다** (v1)

조정 컬럼 · 지급액 컬럼 · 요약 줄(「지급액 N원」). 이 셋이 같은 수를 말한다.

- **대사는 그대로 원본끼리다.** `linked` 판정은 건수 비교라 조정과 무관하게 성립한다
  — 헌장 B-3의 「조정으로 불일치를 일치로 만들 수 없다」가 코드 구조로 지켜진다.
  목업 팝오버 하단의 안내문 「…대사 결과에는 영향을 주지 않습니다」가 참이 된다.
- **손익 3층·대시보드에는 반영하지 않는다** — 아래 범위 밖 참조.

## 범위 밖 (명시)

- **손익 3층·대시보드 전파.** 정산 지급액과 손익은 원래 다른 것을 센다(지급액 =
  마켓이 주는 돈, 손익 = 매출−비용). 전파하려면 `snapshot.ts`의 집계에 조정을
  조인하는 별도 설계가 필요하고, 그건 첫 쓰기 경로에서 같이 열 크기가 아니다.
  **화면 간 수가 갈리는 자리이므로 작업-상태에 남긴다.**
- **마켓이 싣고 온 조정금액.** 목업 시드의 `item.adj`는 「마켓이 정산서에 실어 준
  조정액」인데 `fact_settlement`에 대응 컬럼이 없다(시드가 전부 0이라 티가 안 났다).
  v1은 마이그레이션을 만들지 않는다 — 대신 팝오버 머리말 「원본 A → B」를
  **지급액의 전후**로 읽는다. 목업대로 「조정액의 전후」로 두면 그 값이 늘 0이라
  「원본 0 → −9,400」이 되는데, 0은 아무것도 알려주지 않고 사용자가 보려는 수는
  지급액이 얼마에서 얼마가 됐나다. 문구·자리는 그대로이므로 목업 이탈이 아니라
  **같은 자리에 실재하는 수를 넣은 것**이다.
- **대사 「확인함으로」(`canAck`·`ack`).** `recon_ack` 표는 있으나 조정과 별개
  기능이다. 지금처럼 어포던스를 그리지 않는다(§21-1).
- **Fact 행 단위 조정.** `applyAdjustments`의 절대값 경로는 소비처 0으로 남는다.
  주문 화면 등에서 요구가 실물로 나오면 그때 A1·A2를 다시 본다.
- **조정의 수정(edit).** 고치려면 무효화하고 다시 넣는다. 스택이 곧 이력이다.

## 실측 (2026-08-20)

실 DB(`.tmp/pnl.sqlite` 사본)의 첫 묶음 **2026-07-31 · 11번가 · 원본 512,721원**에
조정 두 건(−12,400 「실입금과 차액」 · +3,000 「누락 배송비 가산」)을 얹고
`render-screen settlement <db> adj`로 렌더해 브라우저에서 읽었다.

- [x] **조정 −9,400 · 지급액 503,321 · 요약 3,267,515원** — 셋이 같은 수로 움직였다
      (요약은 조정 전 3,276,915에서 정확히 9,400 내려갔다). 팝오버 머리말은
      「원본 512,721 → 503,321」, 스택은 「−12,400원 / 08-20 09:12 · 실입금과 차액」
      「3,000원 / 08-20 09:15 · 누락 배송비 가산」, 조정 칸에 accent 점이 붙었다
- [x] **재가져오기 후 delta가 새 원본 위에 얹힌다** — 30,000 → 32,000으로 갱신된 뒤
      유효 지급액 **30,800**. 절대값 대체였다면 28,800(갱신된 원본을 무시한 값)이
      나왔을 자리다. A2를 고른 이유가 수치로 갈린다
- [x] batch 되돌리기 후에도 조정이 남고, 같은 행이 다시 들어오면 다시 적용된다 (ADR-004)
- [x] 무효화하면 합·스택에서 빠지되 `adjustment` 행은 남는다(2건 유지). 이미 거둔 것을
      다시 거둬도 거둔 시각이 덮이지 않는다
- [x] **대사가 조정에 흔들리지 않는다** — 지급액 전액(−30,000)을 조정해도 `linked` 0/2 불변
- [x] `npm run wiring` **남은 일 6 → 0** (합계 428 중 배선 187 · 컷 241 · **100%**)
- [x] 게이트 — typecheck ✅ · `npm test` **1000 passed** ✅ · build ✅ ·
      perf 2.6초 / +201.9MB ✅ · e2e 5.1초 / +248.4MB ✅ · 보존 게이트 12/12 ✅

신규 마이그레이션 **0건** — 001의 `adjustment` 표를 그대로 쓴다.

## 되돌아볼 트리거

- 손익·대시보드가 조정을 반영해야 한다는 요구가 실물로 나오면 → A8 재검토
  (SQL 조인 설계 + 「상품별 합 ≠ 회사 순이익」 문구와의 관계)
- 마켓 정산서에 조정금액 컬럼이 실제로 나타나면 → 범위 밖 ②(마이그레이션 012)
- 지급액 외의 칸을 고쳐야 하는 실물 사례가 나오면 → A4의 「왜 이 칸인가」를
  그 칸에 대해 답할 수 있는지부터
- Fact 행 단위 조정의 소비처가 생기면 → A3의 이중 의미론을 계속 둘지, 한쪽으로
  통일할지
