# ADR-021 — 묶음: 무엇을 합쳐 볼 것인가

날짜: 2026-08-21 · 상태: **결정 · 미구현** (다음 세션이 구현)
관련: [ADR-004](ADR-004-되돌리기-의미론.md) · [§22](§22-커버리지-부재의-일급-취급.md) · LOCK 2·6·8

---

## 문제 — 사용자가 물었다

> *"여러 파일들의 데이터를 합쳐서 대시보드로 보여줘야 되는데, 이 합치기를 앱이 그냥
> 무비판적으로 모든 파일들을 받아들여서 하는 것 같다. 합쳐야 될 파일들을 유저가 직접
> 선택해야 제대로 된 정보를 확인할 수 있는 거 아니냐."*

실측 결과 **맞다.** 집계의 관문은 딱 한 줄이다:

```sql
CREATE VIEW active_order AS … WHERE b.status = 'committed';
                                    ↑ 이게 전부다
```

커밋된 batch는 조건 없이 전부 들어간다. 사용자가 고를 자리가 없다.

### 앱이 «완전히» 무비판적이지는 않다 — 있는 것을 먼저 세어 둔다

| 장치 | 무엇을 막나 |
|---|---|
| 프로파일 판정 | 양식이 안 맞으면 아예 안 들어간다 |
| `source_key` UPSERT | 같은 연결·같은 키면 갱신 — 재가져오기가 안 쌓인다 |
| `findPriorImports(hash)` | 같은 **바이트**면 고지 (막지는 않는다) |
| §18-A 수식 가드 | 파생 시트로 자동 이동 금지 |
| 되돌리기 | batch 단위 제거 (단, **삭제**다) |

### 없는 것 셋

1. **서로 다른 파일이 같은 매출을 담았을 때 감지가 0.** UPSERT는 `(connection_id,
   source_key)`로만 본다. 키 체계가 다른 두 파일이면 매출이 두 배가 된다.
2. **「계산에서 빼되 데이터는 남기는」 장치가 없다.** 되돌리기는 삭제다.
3. **「이 숫자가 어느 파일들로 만들어졌나」를 보는 자리가 없다.**

## ★ 배관은 이미 깔려 있다 ★

```
읽기 경로에서 fact_* 직접 참조 :  0건  (smoke 하네스 하나 제외)
active_* 뷰 사용             : 51곳 · 8파일
active_* 뷰 정의             :  5개
```

집계가 **전부 뷰 5개를 지난다.** 「이 batch를 계산에 넣나」를 뷰 5개의 `WHERE`에
한 줄씩 더하면 손익·정산·주문·채널·상품별·커버리지가 **동시에** 따라온다.
**이것은 배관 공사가 아니라 화면 문제다.**

## 조사 — 남들은 어떻게 하나

새 은유를 발명하기 전에 이미 풀린 문제를 봤다.

| 모델 | 어떻게 담나 | 새 항목이 오면 | 예 |
|---|---|---|---|
| **규칙형** | 조건을 저장 | **자동으로 들어옴** | [Linear 뷰](https://linear.app/docs/custom-views) · Notion/Airtable · Gmail 필터 |
| **수동형** | 손으로 고름 | 안 들어옴 | [Lightroom Collection](https://helpx.adobe.com/lightroom-classic/help/photo-collections.html) · Photos 앨범 · 재생목록 |
| **혼합형** | 규칙 + 손 | 규칙에 맞으면 자동, 손으로도 추가 | [Gmail 라벨](https://zapier.com/blog/gmail-labels/) |

### ★ Adobe가 둘 다 두고 하나로 못 줄인 이유가 답이다 ★

> *"Albums는 이미지를 직접 골라 넣고, Smart Albums는 조건을 정하면 자동으로 채워진다."*

두 일이 다르기 때문이다:

- **「5성 사진 전부」** = 규칙 (사람이 매번 고를 수 없다)
- **「이번 전시에 낼 12장」** = 수동 (규칙으로 표현이 **불가능**하다)

우리 앱에 그대로 대입된다:

- **「11번가 것 전부」** = 규칙
- **「7월 결산에 쓸 이 3개」** = 수동 ← **사용자가 원한 것이 이쪽이다**

### 버린 접근 — 「제외 목록」 (2026-08-21 · 사용자가 기각)

초안은 반대였다: 전부 담고 **뺀 것만** 목록으로 든다. 근거는 ① 파일 100개면 포함
목록이 100줄 ② 포함 목록이면 새 파일이 조용히 빠진다 였다.

**둘 다 죽었다.** ①은 **검색창**을 달면 근거가 사라지고, ②는 사용자가 **명시적으로
만든 묶음**이면 «안 들어온 것»이 사고가 아니라 정의다. 그리고 애초에 논의의 출발이
«쌓인 것 중에서 골라 묶는다»였는데 제외 모델은 그 질문을 바꿔치기한 것이었다.

### 버린 접근 — 「라이브러리로 가르기」

목업에 「라이브러리」가 나와 이 개념인가 물었으나, 실측하면 **아니다**:

```
mockup/FlowBase.dc.html:4807   // 필드 매핑 — 양식 라이브러리   ← 「양식 목록」이라는 뜻. 전체에서 이 한 번뿐
001-initial.sql:28             -- v1은 라이브러리가 하나다      ← 소유(테넌시) 단위
```

**`library_id`는 Fact 행에 박혀 있어 배타적이다**(LOCK 1 공통 6컬럼). 행 하나는
라이브러리 하나에만 속한다. 그런데 묶음은 **중첩**돼야 한다 — 「7월 전체」와
「7월 광고 제외」가 같은 매출 파일을 공유한다. 라이브러리로 만들면 **같은 파일을
두 번 넣어야** 하고 비교가 불가능해진다.

### 세 층위는 서로 다른 문제다 — 섞지 않는다

| | 무엇을 가르나 | 지금 상태 | 언제 |
|---|---|---|---|
| **연결(connection)** | 같은 마켓의 **계정 둘** (11번가 A/B) | `conn-${marketplaceKey}` 하드코딩 | 이것도 급하다 (별건) |
| **묶음** | 어느 **파일들**을 합칠까 | **없음** | 이 ADR |
| **라이브러리** | **사업체** 자체 | 컬럼만 있음 · `lib-1` 고정 | 나중 |

> «모든 파일을 뭉뚱그린다»의 진범 절반은 **연결**이다. 라이브러리로 가르면 계정별로
> 데이터가 통째로 갈려 **합산 손익을 못 본다.** 연결은 연결에서 고친다 — 가져올 때
> 어느 연결로 넣을지 고르거나 새로 만들게. `ensureConnection` 주석이 이미 예고해 뒀다:
> *"연결 화면이 생기면 사용자가 덮어쓸 수 있는 값이 된다."*

## 결정

### v1 — 수동 묶음 + 「전체」

```
전체         기본 · 못 지움 · 모든 파일 · 새 파일 자동 포함
7월 결산      사용자가 고른 파일 3개
광고 제외본    사용자가 고른 파일 2개
```

- **만들기**: 파일 목록(검색 가능)에서 골라 → 「묶음으로 만들기」 → **사용자가 이름을 붙인다**
- **편집**: 담기·빼기 둘 다 언제든
- **전환**: Linear의 뷰 전환과 같은 자리

「전체」의 자리는 **Linear식**을 따른다 — 뷰 목록 안의 기본 항목이고 지울 수 없다.
(Lightroom/Photos는 `All Photographs`를 아예 다른 층에 두지만, 배울 것이 하나 는다.)

### v2 — 스마트 묶음 (규칙형)

「11번가 것 전부」처럼 조건을 저장하면 다음 파일도 자동. Lightroom도 Collection이
먼저였고 Smart가 나중에 붙었다.

### v3 — 혼합 (Gmail 라벨형)

규칙으로 담되 손으로 예외를 더하고 뺀다.

### 함께 정한 것

| 쟁점 | 결정 | 한 줄 이유 |
|---|---|---|
| **이력** | 남긴다 — 묶음의 **변경**에 | 기준 데이터다(헌장). 이력 없이 바꾸면 **지난달 순이익이 오늘 바뀐다** |
| **기간** | 데이터의 **실제 날짜 범위**에서 뽑아 사용자가 고른다 | 앱이 정하지 않는다. 범용성 |
| **내보내기** | 원본 / 이 묶음 **둘 다 선택 가능** | LOCK 8(데이터 인질 금지). 「내보낸 수와 화면 수가 다르다」도 사라진다 |
| **앱의 제안** | **우선한다** — 「이 파일들이 한 묶음 같습니다」 | ADR-017 계보 — 앱이 짚고 사람이 확정 |
| **경고** | 막지 않는다. **크기를 말한다** | 「뺀 것이 얼마인지」가 보이면 사람이 판단한다. §22와 같은 방향 |

> ★ **막지 않는다**는 것이 이 ADR의 태도다 ★ 초안은 «틀리게 고를 수 있다 · 숫자를
> 예쁘게 만들 수 있다»를 이유로 선택권을 좁히려 했고, 사용자가 기각했다. 옳은 기각이다 —
> 사용자의 데이터고 사용자의 사업이다. 앱이 할 일은 **경고하고 결과를 보이는 것**까지고
> 결정은 사용자 몫이다. 그래서 「뺀 것의 금액」을 반드시 보인다.

### 되돌리기와 반드시 가른다

```
되돌리기(undo)   batch 행을 **지운다**    데이터가 없어진다   ADR-004 · LOCK 2
묶음에서 빼기     계산에서만 뺀다          데이터는 남는다     이 ADR
```

두 버튼이 가까이 있으므로 문구가 확실히 갈려야 한다. 안 그러면 «뺐는데 왜 아직
있지»와 «지웠는데 왜 안 없어지지»가 동시에 생긴다.

## ⚠ 함정 — 새 파일이 조용히 빠진다

「7월 결산」을 보는 중에 8월 파일을 가져오면 그 파일은 묶음에 없다. 맞는 동작이지만
아무 말이 없으면 **«넣었는데 안 보인다»**가 된다.

> **가져오기 결과가 말한다**: *"이 파일은 「7월 결산」에 없습니다 [담기] [새 묶음 만들기]"*

Lightroom은 이걸 안 한다 — 임포트와 앨범이 무관한 일이기 때문이다. **우리는 다르다.**
가져오기는 «손익을 보려고» 하는 일이라 넣었는데 화면이 안 변하면 목적이 깨진다.
남들보다 잘 해야 하는 자리다.

## 아직 안 정한 것

- **묶음의 저장 모양** — 새 표(`collection` + `collection_batch`)인가, `batch`에 컬럼인가.
  중첩이 필요하므로 **표 둘**이 유력하다(한 batch가 여러 묶음에).
- **이력의 범위** — ADR-005가 「v1 이력 = 원가만」으로 명시적 축소를 한 선례가 있다.
  같은 판단이 가능한지.
- **겹침 탐지의 첫 신호** — 「같은 연결·같은 날짜·같은 대상표에 batch 2개 이상」이
  1순위 후보. `order_source_key` 교차가 더 강한 신호.
- **파일 목록 화면의 자리** — 「가져오기 기록」을 키울지 새 화면일지.
