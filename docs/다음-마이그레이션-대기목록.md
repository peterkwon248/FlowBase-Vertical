## 1. 광고 배분 룰 — 캠페인 → SKU

**목업**: 비용 화면의 `adRules`, 핸드오프 §6-8의 `AD_RULES` 4종
(`revenue` 매출 비례 · `qty` 판매량 비례 · `single` 단일 SKU · `company` 배분 안 함).

**없으면**: 사용자가 배분 규칙을 바꿔도 새로고침하면 되돌아간다. 손익 3층의
"직접 광고비 vs 미배분 광고비" 경계가 매번 기본값으로 리셋된다.

`company`로 지정한 캠페인은 `AD_UNALLOC`으로 가고 **상품 기여이익이 아니라 채널
기여이익에서** 빠진다 (인계 문서 §4). 즉 이 규칙은 표시 설정이 아니라 계산의 입력이다.

## 2. 운영비 · 고정비

**목업**: `OPS_SEED`(포장·부자재·피킹) · `FIXED_SEED`(임대·인건·창고),
비용 화면의 `opsEdit`/`fixedEdit`.

**없으면**: 손익 3층의 아래 두 층이 통째로 없다 — 운영비 없이는 상품 기여이익이,
고정비 없이는 회사 순이익이 나오지 않는다.

주의: **고정비는 상품에 배분하지 않는다** (인계 문서 §5). 그리고 조회 기간 기준으로
안분해야 한다 — 목업의 `PERIOD_DAYS = 8 / MONTH_DAYS = 31` 고정이 헌장 C-3의
must-fix 이슈 20이다.

## 3. 진단 할 일 결정 기록 — 채택 / 기각 + 사유

**목업**: 진단 화면의 `actState` (핸드오프 §6-7 — `accepted` · `done` · `reject:사유` 4종).

**없으면 거짓말이 되는 것**: "기각한 제안은 다시 올라오지 않습니다."
영속 없이 이 문장을 화면에 쓰면 새로고침마다 같은 제안이 되살아난다. 제품이 사용자의
판단을 기억한다고 말해놓고 기억하지 않는 것 — 헌장 A-5가 금지한 조용한 거짓이다.

기각 사유 4종도 함께 저장해야 "왜 안 하기로 했더라"에 답할 수 있다.

스키마를 지금 굳히지 말고 JSON 스냅샷으로 두는 편이 안전하다.

## 5. 라이선스 · 설정

**목업**: 설정 화면의 `licSt`(none/active/expired), `gen`(일반 설정), 테마.

**없으면**: 라이선스 키를 매번 다시 입력해야 한다. 헌장 B-10의 "다운그레이드 시 기존

자격증명은 여기 두지 않는다 — 로컬 암호화 저장소 참조만 (헌장 B-11).

## 6. URL 소스 — "이 주소 기억"

**목업**: 가져오기의 `impSrc = "url"` 경로 (지시서 §11-4).

**없으면**: 매달 같은 주소를 다시 붙여넣어야 한다.

주의: 헌장 E-7 — **"동기화"라고 부르지 않는다.** 주소를 기억하는 것과 자동으로
가져오는 것은 다르다. 저장하는 것은 주소와 마지막 가져오기 시각뿐이다.

## 7. 금액 컬럼의 `CHECK (… >= 0)` — 부호 규약을 스키마로 내린다

**정책**: [ADR-009 ②](ADR-009-회계-정책.md) — 모든 fact 금액은 양수로 저장하고
차감 여부는 타입 컬럼이 정한다.

**지금**: `src/core/accounting/sign.ts`의 `assertStoredPositive()`가 저장 직전에 막는다.
스키마 LOCK(헌장 규칙 1) 때문에 `001-initial.sql`을 고치지 않았다.

**넣을 것**: `fact_claim.amount` · `fact_order.total_amount` · `fact_order_item.gross_amount`
· `fact_settlement.*_amount` · `fact_ad_spend.spend_amount` 등에 `CHECK (col >= 0)`.

**왜 미뤘나**: 기존 DB에 이미 음수가 들어 있으면 마이그레이션이 실패한다. 넣기 전에
`SELECT`로 위반 행을 먼저 세고, 있으면 그게 어디서 들어왔는지부터 밝힌다 —
제약을 통과시키려고 데이터를 조용히 고치면 안 된다 (헌장 A-5).

## 8. 파일 접수 장부 — **넣은 파일은 전부 한 줄**

> ⚠ **이 항목은 열흘 늦게 등록됐다 (2026-08-20).** [ADR-019](ADR-019-시트-자동-선택과-다중-시트-기준-적재.md):144가
> 「기준 가져오기의 기록 화면 표출 … **대기 목록으로 남긴다**」고 약속했는데
> **이 목록에 안 적혔다.** 미뤘는데 미뤄둔 자리에 안 적혀서 두 번 잊혔다.
> `/after-work` 6-②가 이 사고에서 나온 규칙이다.

**사용자가 겪은 것**: 13MB 단가표를 넣었는데 「가져오기 기록」에 한 줄도 없었다.
넣은 사람은 실패로 읽는다.

**지금 코드**: 「가져오기 기록」은 `batch` 한 테이블만 읽는다
(`repository.ts:2515 FROM batch b LEFT JOIN connection c`). 그런데 원가는 batch를
안 만든다 — `runReferenceImport`가 `App.tsx:1218`에서 반환해 `openBatch`에 닿지 않고,
`batch.connection_id`가 `NOT NULL`이라 채널 없는 파일은 애초에 못 들어간다.

**없으면 거짓말이 되는 것**: 「가져오기는 덮어쓰기가 아니라 쌓기입니다. 각 실행에
`batch_id`가 붙어서, 잘못 올린 파일 하나만 골라 되돌릴 수 있습니다」 — 기록 화면이
스스로 하는 말이다. 원가 파일에는 해당되지 않는데 화면은 구분해서 말하지 않는다.

### ★ batch를 척추로 삼지 않는다 ★

가장 쉬운 길은 「원가도 batch 행을 쓰게 한다」인데 **그 길로 가지 않는다.**
채널 없는 파일마다 유령 연결을 만들어야 하고(`App.tsx:1183-1189`가 이미 그 이유를
적어 뒀다), 그러면 아래 「통」을 나중에 얹기가 더 어려워진다.

batch는 **사실 적재 장부**다. append-only이고 되돌리기 단위이며 연결에 매달린다
(LOCK 2). 제 일을 하고 있다. **문제는 「가져오기 기록」 화면이 batch를 장부로 착각한 것이다.**

장부는 파일이어야 한다:

```
파일 접수 장부(통)  ← 척추. 넣은 파일은 전부 한 줄
  ├ 얕게: 파일 메타 + 무엇이 됐나 (batch / cost_history / pending_cost)
  └ 깊게: 파싱된 표까지 보관 → 아무 파일이나 표로 다시 본다   ← 「원본 보관층」
그 위에 묶음 — 지금 `collection_batch`는 batch를 묶는다. 파일을 묶어야 맞다 (013 확장)
```

**받을 값은 이미 있다.** `runReferenceImport`가 `inserted`·`skipped`·`replaced`·
`unmatched`·`stashed`·`bridged`·`createdSkus`·`badRows`를 돌려주는데 저장할 자리가 없다.

**선행**: 이건 스키마가 느는 일이라 [작업 리듬 4](작업-리듬.md)에 따라 **ADR이 먼저다.**
지금 이 항목에는 ADR이 없다 — 그게 이 건이 열흘 떠 있던 이유다.

**끝나면 지울 자리 4곳**: `tests/user-invariants.test.ts:203`(`toBe(false)`가 붉어진다)
· `docs/사용자-불변식.md:116`(U-1 ⚠ 부분) · `docs/문서-감사-2026-08-20.md:77`(A-4-4)
· `docs/작업-상태.md`의 「다음 손 ①」.
