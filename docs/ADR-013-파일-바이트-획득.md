# ADR-013 — 사용자가 고른 파일의 바이트를 어떻게 얻나

상태: **확정** (2026-08-14) · 결정: **웹 표준 `<input type="file">`**

---

## 문제

파이프라인은 완성돼 있고 e2e·Tauri 스모크로 증명됐다. 그런데 **앱에는 사용자가 파일을
고르는 경로가 없다.** 지금 앱이 읽는 데이터는 CLI(`tools/harness/pnl.ts`)가 만든 DB뿐이다.

스모크가 쓰던 `fetch("/@fs/…")`는 **vite dev 전용 트릭**이다(`__PROJECT_ROOT__`는 빌드
시점 define). 릴리스 빌드에서는 죽는다.

8월 정산 파일이 며칠 안에 나온다. 그날이 위저드의 첫 실전이자 `hasPriorPeriod`가 처음
참이 되는 날인데, 지금 상태로는 그 파일이 **CLI로만** 들어간다 — *"정산서 던지면 손익
나온다"*는 제품 약속에서 **'던지면'이 없다.**

## 실측 — 오늘 있는 것

```
package.json deps    @tauri-apps/api · fflate · lucide-react · pretendard · react · react-dom · xlsx
                     → plugin-dialog 없음 · plugin-fs 없음
Rust 커맨드          db_open · db_close · db_exec · db_run · db_get · db_all · db_run_many  (7개뿐)
capabilities         default.json = ["core:default"]
src-tauri/permissions/  없음
Template             <input type="file"> 없음 · 드래그드롭 핸들러 없음
```

## 세 갈래

| 길 | Rust 변경 | 새 IPC 표면 | 비고 |
|---|---|---|---|
| **① `<input type="file">`** | **없음** | **0** | 웹 표준. `File.arrayBuffer()` |
| ② plugin-dialog + 자체 바이트 커맨드 | 크레이트 1 + 커맨드 1 | 커맨드 1 | 네이티브 다이얼로그 |
| ③ plugin-fs | 크레이트 1 | **넓다** — read/write/mkdir/remove/rename/watch | — |

**③은 먼저 빠진다.** ADR-003이 `tauri-plugin-sql`을 기각한 논리에 정면으로 걸린다 —
그때 이유는 성능이 아니라 **커맨드 표면**이었다. 보증이 구조가 아니라 설정(capability JSON)이
되는 순간, 합격 기준 4("전체 테이블 적재 경로 없음")를 구조로 증명한 것이 무의미해진다.

## 결정과 근거 — ①

### 1. ADR-003 재검토 트리거 2의 **적용 범위**

그 조항은 이렇게 적혀 있다:

> *"프론트엔드에서 **임의 조회**가 꼭 필요한 동선 발견 → 플러그인이 아니라 커맨드 추가로 푼다"*

문자만 보면 ②가 맞아 보인다. **그런데 조항의 주어를 봐야 한다** — "임의 조회가 필요한
동선"이다. DB를 읽고 싶은 동선이 생기면 넓은 표면(플러그인) 대신 좁은 표면(커맨드)으로
풀라는 규칙이다.

지금 동선은 조회가 아니라 **사용자가 고른 파일의 바이트를 얻는 것**이고, 그 일은 웹뷰가
표준 API로 이미 완벽하게 한다. 즉 트리거 2는 *"IPC 표면이 필요해질 때의 규칙"*인데,
**표면이 아예 필요 없는 길이 있으면 규칙 적용 전에 그 길이 이긴다.**

```
② "가장 좁은 IPC"   커맨드 1개
① "IPC 없음"        0개        ← 0은 1보다 작다
```

조항의 **취지**(표면 최소화)가 조항의 **문자**보다 상류에 있다. 이 해석을 여기 남기는
이유는, 다음에 트리거 2를 인용하는 사람이 같은 판단을 다시 할 수 있어야 하기 때문이다.

### 2. 파이프라인 입력이 이미 바이트다

Recognition이 **매직 바이트 스니핑**부터 시작한다(`sniff(bytes, fileName)`). 그래서
`File → ArrayBuffer → 파이프라인`이 **접합면 0**으로 붙는다.

②는 `경로 문자열 → Rust가 읽어서 bytes 반환`이라 **같은 결과를 IPC 왕복 하나 얹어서**
얻는다. 게다가 경로에서 파일명을 다시 뽑아야 하는데(프로파일의 파일명 캡처가 그걸 본다)
Windows 경로 구분자 정규화라는 사소하지만 틀리기 쉬운 일이 하나 더 붙는다.

### 3. 대용량도 문제없다

8만 행 xlsx가 ~10MB대다. `ArrayBuffer`로 받아 Worker에 **transferable**로 넘기면 복사도
없다. Tauri 스모크가 이미 그 크기를 웹뷰에서 소화했다(#13 · 9.5~10.4초 · JS 힙 74~86MB).

## 같이 넣은 설정

```json
"dragDropEnabled": false
```

Tauri v2는 기본적으로 **파일 드롭을 네이티브에서 가로채** 웹뷰에 HTML 드래그 이벤트가
가지 않는다. 목업의 드롭존이 살려면 꺼야 한다. 클릭으로 고르는 경로는 이 설정과 무관하게
동작하지만, **두 경로가 같은 코드로 붙도록** 지금 명시해 둔다.

## 증축 조건 — 언제 ②로 가나

①을 고른 것이 ②를 영영 안 한다는 뜻이 아니다. **①에서 ②로 가는 것은 쉽고 그 반대가
어렵다** — 바이트를 얻는 지점만 갈아끼우면 되고 파이프라인 아래는 그대로다.

다음 중 하나가 실제로 관측되면 재검토한다:

1. **경로 기억이 필요해질 때** — "지난번 그 폴더"를 열어주는 동선. HTML input은
   마지막 디렉터리를 기억하지 못한다
2. **폴더 단위 가져오기** — 파일 여러 개를 한 번에, 또는 폴더를 지정해 그 안을 훑는 동선
3. **자동 재가져오기** — 정해둔 경로의 파일이 바뀌면 다시 읽는 동선. 이건 경로를 **저장**해야
   하므로 ①로는 불가능하다 (브라우저 보안 모델상 경로가 노출되지 않는다)
4. 사용자가 "파일 선택 창이 앱 같지 않다"고 말할 때 — 미감은 실제 불만이면 근거가 된다

②로 갈 때 필요한 것은 실측해 뒀다: `tauri-plugin-dialog` 크레이트 + npm 패키지,
`capabilities/default.json`에 권한 문자열, 그리고 바이트를 읽는 **자체 커맨드 하나**
(plugin-fs가 아니라 — 그건 ③이고 이미 기각됐다).

## ⚠ 정정 기록 — 한때 잘못 적은 근거

이 결정의 첫 판에서 *"플러그인을 붙이면 `src-tauri/permissions/`가 생겨 기존 `db_*`
커맨드가 소급 ACL 대상이 되어 앱이 깨진다"*고 적었다. **인과가 틀렸다.**

```
src-tauri/permissions/ 가 없어서 로컬 커맨드가 ACL 면제인 것    맞다
플러그인 추가가 그 디렉터리를 만드나                          아니다
```

플러그인 권한은 `capabilities/default.json`에 **문자열 하나**로 들어간다. 지뢰는 실재하되
**다른 행위**(앱 레벨 `permissions/` 신설)가 밟는다. 언젠가 그 디렉터리를 만들 일이 생기면
`db_*` 7개를 전부 명시적으로 허용해야 한다는 사실은 **여전히 유효한 경고**다.

> **왜 이 정정을 결정문에 남기나** — 결론(①)은 유지됐지만 **근거 하나가 죽었다.**
> 근거가 죽었는데 결론만 살아남으면, 다음 사람이 이 문서를 읽고 "ACL 때문에 ①"이라고
> 잘못 배운다. 결론이 같아도 근거가 바뀌면 재판정한다 — 그게 이 저장소의 규율이다.

## 재검토 트리거

1. 위 «증축 조건» 넷 중 하나가 관측됨 → ②로 증축
2. Tauri가 웹뷰의 `File` API 동작을 바꿈 → ①의 전제 재확인
3. 100MB 이상 파일이 정기 입력이 됨 → `ArrayBuffer` 전량 적재가 아니라 스트리밍 검토
   (지금 파이프라인도 바이트 전량을 받으므로 이건 ADR-001·007과 함께 본다)
