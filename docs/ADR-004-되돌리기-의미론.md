# ADR-004 — UPSERT × 되돌리기 의미론

- **상태**: 채택
- **일자**: 2026-08-12
- **범위**: 헌장 B-2 (append-only · 되돌리기), 세션 2 합격 기준 1·2
- **발견**: 헌장 B부 대비 diff 검수 (U-1). 세션 2의 자체 테스트 10개는 이 구멍을 지나가지 않았다

---

## 문제

헌장 B-2는 이렇게 적었다.

> append-only. 가져오기는 덮어쓰기가 아니라 batch 추가다. **되돌리기 = 해당 batch 행 제거.** `source_key` 기준 중복은 UPSERT.

두 문장이 함께 서지 않는다. UPSERT가 있으면 **한 행이 여러 배치를 거치기** 때문이다.

```
배치 A가 주문 X를 넣는다        → X.batch_id = A
배치 B가 같은 X를 다시 가져온다  → X.batch_id = B   (UPSERT)
배치 B를 되돌린다               → DELETE WHERE batch_id = B
                               → X가 통째로 사라진다
```

X는 A가 정당하게 들여온 행이다. **B의 되돌리기가 A의 데이터를 파괴했다.**

"해당 batch 행 제거"는 한 행이 한 배치에만 속할 때만 참인 문장이었다. 재현 테스트가
`tests/multi-batch-undo.test.ts`에 있고, 고치기 전에는 5개 전부 실패했다.

---

## 결정

**되돌리기는 두 갈래로 나뉜다.**

| 그 배치가 한 일 | 되돌릴 때 |
|---|---|
| 신규 삽입 | 삭제 |
| 기존 행 갱신 | **이전 판으로 복원** |

복원하려면 덮어쓰기 직전의 행을 보존해야 한다. `version` 컬럼은 몇 번째 판인지만 알려줄 뿐
이전 판의 **내용**을 갖고 있지 않다.

### `row_shadow`

```sql
CREATE TABLE row_shadow (
  id, batch_id, target_table, connection_id, source_key,
  prev_batch_id,      -- 덮이기 전 행의 소유 배치
  prev_row_json,      -- 덮이기 전 행 전체
  created_at,
  UNIQUE (batch_id, target_table, connection_id, source_key)
)
```

이름에 `fact_` 접두를 쓰지 않는다. 그 접두는 "헌장 B-1의 공통 6컬럼을 갖는 사실 테이블"을
뜻하고, B-1 준수 테스트가 `fact_%`로 대상을 열거한다. 그림자는 사실 행이 아니므로 접두를
달면 그 테스트가 거짓으로 실패한다 — 실제로 `fact_shadow`로 지었다가 그 테스트가 잡았다.

### 스냅샷은 트리거가 만든다

애플리케이션이 행마다 "이미 있나?"를 묻지 않도록 DB 안에서 처리한다. 80,138행 적재에서
행당 왕복이 하나 늘면 그게 바로 병목이 된다 (같은 이유로 삽입/갱신 집계도 청크 앞뒤
카운트 2회로 낸다).

```sql
CREATE TRIGGER shadow_fact_order BEFORE UPDATE ON fact_order FOR EACH ROW
WHEN OLD.batch_id <> NEW.batch_id
BEGIN INSERT OR IGNORE INTO row_shadow ... json_object(...) ... END;
```

- `WHEN OLD.batch_id <> NEW.batch_id` — 같은 배치가 같은 행을 두 번 건드리는 경우
  (한 파일에 `source_key` 중복)에는 스냅샷을 만들지 않는다. 그 배치가 손대기 전 상태는
  이미 첫 스냅샷에 있다.
- `INSERT OR IGNORE` + `UNIQUE` — **첫 스냅샷만 남는다.**

### 되돌리기 절차

1. `assertUndoable` — 되돌릴 수 있는지 확인
2. 복원 — `row_shadow`의 이전 판을 행에 되쓴다 (`batch_id`가 이전 배치로 돌아간다)
3. 삭제 — 아직 `batch_id`가 이 배치인 행 = 이 배치가 신규 삽입한 것
4. 그림자 정리 — `batch_id = ? OR prev_batch_id = ?`

4번의 `prev_batch_id` 조건이 필요한 이유: **복원 UPDATE 자체가 그림자 트리거를 다시
발화시킨다.** `batch_id`가 B에서 A로 바뀌므로 `(batch_id=A, prev_batch_id=B)`인 거울상
항목이 생긴다. 1번에서 `prev_batch_id = B`가 없음을 이미 확인했으므로, 지금 남은 그것은
전부 복원이 만든 것이다.

### 되돌리기는 행 단위 LIFO다 — 아니면 거부한다

```
A가 X를 넣는다 → B가 덮는다 → C가 덮는다
```

이 상태에서 **B만** 되돌리려 하면, 복원했을 때 C의 데이터를 덮어쓰게 된다. 순서가
꼬인 되돌리기는 의미가 모호하다.

조용히 덮는 대신 **거부한다** (헌장 A-5):

> 되돌릴 수 없다: 배치 C가 이 배치의 행을 덮어썼다. 그쪽을 먼저 되돌려야 한다

판정은 `row_shadow.prev_batch_id`로 한다 — 어떤 그림자가 이 배치를 가리키고 있으면 그 뒤에
다른 배치가 얹혀 있다는 뜻이다.

## 비용

| | |
|---|---|
| 저장 | 갱신되는 행 하나당 JSON 스냅샷 하나. 신규 삽입만 있는 첫 가져오기에는 0 |
| 쓰기 | 트리거 한 번. UPSERT가 실제로 갱신일 때만 |
| 정리 | 배치를 되돌리면 그 그림자도 사라진다. 되돌리지 않은 배치의 그림자는 남는다 |

**미해결:** 되돌리지 않은 오래된 그림자의 보존 기간을 정하지 않았다. 12개월치를 매달
재가져오기하면 그림자가 누적된다. 세션 3에서 실사용 데이터로 증가율을 보고 정한다.

## 재검토 트리거

1. 그림자 누적이 실사용에서 문제 → 보존 정책 도입
2. 순서 꼬인 되돌리기를 실제로 요구하는 동선 발견 → 거부 대신 다른 해법 검토
3. Fact 테이블 추가 → **트리거도 함께 추가해야 한다.** 빠뜨리면 그 테이블만 조용히 옛 동작으로 돌아간다

## 실측 (2026-08-14) — 거부 경로가 처음으로 실재했고, 처음으로 시험됐다

7월 리허설이 상황을 만들었다. 위저드로 11번가 파일을 다시 넣자 128행이 새 batch로
이관돼 `batch-11st`이 **행을 0개 소유한 배치**가 됐다. 그때까지 이 저장소에는
거부 경로를 밟는 테스트가 **0건**이었다 (`multi-batch-undo.test.ts`의 5개는 전부
순서를 지킨 성공 경로만 걷는다).

`tests/undo-refusal.test.ts` 9개가 그 구멍을 메운다. 확정된 성질:

| 성질 | 실측 |
|---|---|
| 판정 조건 | **`row_shadow.prev_batch_id` 하나뿐이다.** 배치의 시각·순번·status를 보지 않는다 |
| 행 0개 배치 | **이관 때문이면 거부**된다. 이관이 남긴 그림자가 신호다. 적재가 아예 없던 빈 배치는 조용히 성공(0 반환) |
| 거부 범위 | **배치 통째다.** 한 줄만 이관돼도 나머지 행을 되돌릴 방법이 없다 |
| 테이블 교차 | `fact_order` 한 줄이 이관되면 같은 배치의 `fact_settlement` 행까지 잠긴다 — `assertUndoable`이 `target_table`을 보지 않는다 |
| 롤백 | 거부 시 아무것도 남지 않는다. **다만 그 안전은 «검사가 앞에 있어서»가 아니라 트랜잭션 래핑 때문**이다 — 두 번째 거부(`되돌릴 수 없는 배치`)는 DELETE들 **뒤에** 난다 |

**실데이터 상태** (`.tmp/pnl.sqlite`, 2026-08-14):

```
prev_batch_id = batch-11st  →  그림자 128        batch-11st 잠김
prev_batch_id = batch-esm   →  그림자 155        batch-esm  잠김
batch-coupang               →  그림자 0          되돌리기 가능
```

### status 가드 — 판정 완료 (2026-08-14)

발견 당시는 이랬다:

```sql
commitBatch   UPDATE batch ... WHERE id = ? AND status = 'open'
undoBatch     UPDATE batch ... WHERE id = ?              ← 상태 조건 없음
```

독립 검증 2건이 확인했고, **두 갈래로 갈라 판정했다.**

**① `undone` → `undone` 재실행은 결함이다. 막는다.**

이미 되돌린 배치를 또 되돌리는 것은 **하는 일이 없으면서 `undone_at`만 파괴한다.**
최초로 되돌린 시각은 감사 이력이고, 이 앱은 이력 덮어쓰기를 전부 금지해 왔다 —
조정도 삭제도 기록으로 남기는 판에 되돌리기 시각만 예외일 이유가 없다.
`commitBatch`와의 비대칭도 근거다. → `assertUndoable`에 상태 조건 추가.

**② `open` 배치 되돌리기는 허용을 유지하되 의미를 명시한다.**

```
open      상태의 undo = 취소(abort)     — 적재하다 만 것을 치운다
committed 상태의 undo = 되돌리기(undo)  — 이미 손익에 반영된 것을 물린다
```

같은 함수가 두 의미를 갖는다. **v1은 스키마를 나누지 않는다** — `aborted_at`을
따로 두는 것은 둘을 구분해 보여줄 필요가 실사용에서 생긴 뒤에 한다. 지금은
`assertUndoable`의 주석과 `tests/undo-refusal.test.ts`가 의미를 진다.

**곁들여 고친 것**: 배치 존재 검사를 **맨 앞으로** 옮겼다. 전에는 맨 끝(UPDATE의
`changes === 0`)에서 걸려 거부되기 전에 DELETE 10여 개가 먼저 돌았다. 트랜잭션이
롤백해 주긴 했지만 **안전이 «검사가 앞에 있어서»가 아니라 래핑에 걸려 있었다.**
이제 둘 다다.

> 단언을 뒤집는 장치가 설계대로 작동했다. 「현재 동작 고정 (미판정)」이라 적어 둔
> 절이 가드 커밋에서 깨졌고, 그 깨짐이 곧 판정 완료의 신호였다 (작업 리듬 9).

### 반환값의 모호함

`undoBatch`는 **삭제된 행 수만** 돌려준다(복원된 행은 세지 않는다). 그래서 `0`이
«아무 일도 없었다»(빈 배치)와 «전부 복원됐다»(전량 UPSERT 갱신)를 구분하지 못한다.

**화면은 이 모호함을 우회한다** — `batchHistory`가 `ownedRows`(사라질 수)와
`restoresRows`(복원될 수)를 따로 세어 주고, 확인 다이얼로그가 **누르기 전에**
그 둘을 말한다. 반환값을 쪼개는 것은 소비자가 더 생기면 그때 본다.

> **정정 (2026-08-16)** — 이 절이 **두 벌 있었고 처방이 서로 어긋났다.** 뒤쪽 사본은
> *"지금은 소비자가 테스트뿐이라 무해하고, 되돌리기 UI가 생기면 그때 갈라야 한다"*
> 였는데 **되돌리기 UI는 이미 배선됐다** — 낡은 사본이 살아 있는 결정처럼 읽히고
