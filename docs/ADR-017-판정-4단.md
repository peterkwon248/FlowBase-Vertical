# ADR-017 — 열 판정 4단: 파일이 아니라 열 단위로 안다

날짜: 2026-08-19 · 상태: 확정 · 관련: [§20](§20-보강-확인-질문.md) · [ADR-010](ADR-010-프로파일-라우팅-규약.md) · [ADR-016](ADR-016-원가-대기-스테이징.md)

## 문제

판정이 파일 단위로 전부 아니면 전무였다 — 프로파일이 맞으면 통째로 들어오고,
아니면 목격(009)만 남고 끝난다. 전용 필드 7개 중 1개만 가진 파일도 **그 1개만큼은
아는데** 아는 만큼을 쓸 길이 없었다.

## 결정 — 열마다 4단

```
alias      별칭이 안다 + 값 신호가 어긋나지 않는다   → 자동 사용 가능
identity   항등식이 증명한다 (C 세션)                → 자동 사용 가능
candidate  신호는 있는데 확정할 수 없다              → 반드시 사람에게 묻는다
unknown    아무 신호도 없다                          → 세어서 말한다 (LOCK 6)
```

§20 결정론 5층과의 대응: 별칭→`alias` · 값 신호→**게이트**(확정의 조건) ·
문서 맥락→색인 키(아래 한계 참조) · 항등식→`identity` · 개인 프로파일→B2에서
별칭 색인으로 합류한다.

### ★ 자동 사용은 확정+증명뿐이다 ★

`candidate`는 어떤 경로로도 자동으로 쓰이지 않는다. 이 실패는 **다른 실패와
질이 다르다** — 못 읽는 실패는 사용자가 보지만, 틀리게 확정한 필드는 숫자가
나오고 화면이 초록이고 손익이 통째로 틀리며 아무도 못 본다.

### ★ 부분 적재의 이행 경로는 즉석 적재가 아니라 즉석 프로파일이다 ★

판정이 열 몇 개를 확정해도 곧장 적재하지 않는다:

- 행 식별 키 없는 적재는 재가져오기가 중복을 쌓는다 (ADR-006)
- 키의 유일성을 «증명»할 항등식은 없다 — 유일성은 값 신호일 뿐이라 후보이고,
  후보는 사람을 지난다

그래서 부분 적재는 언제나 **최소 한 번의 사람 확정(행 식별 키)**을 지나고, 그
산물이 개인 프로파일(`mapping_profile` · `source='user'` — B2)이며, 적재는 기존
`runImport`가 그 프로파일로 한다. 적재기를 새로 만들지 않는다 — 두 벌이 되는
순간 «같은 파일, 다른 해석»이 생긴다.

## 구현 판단

### 전용 필드 등록부 (`core/import/mapping/targets.ts`)

canonical target 26종의 유일한 명부 — 이름·기대 kind·뜻풀이·사는 표.
`validateProfiles`가 «명부에 없는 target = 오타»로 지킨다(ADR-010 계보). 오타 난
target은 지금까지 조용히 그 필드를 잃었다 — 매핑은 돌고 적재도 되는데 그 컬럼만
어느 표에도 안 실렸다.

`IDENTITY_TEMPLATES`는 증명이 대상을 지목하는 유일한 길이다. 항이 하나뿐인
«항등»(a=b)은 넣지 않는다 — 값이 같은 두 열은 흔해서(금액 복사 열) 우연이 확정이
된다.

### 별칭 색인 — 저장하지 않고 유도한다 (`core/import/judge.ts`)

`buildAliasIndex(profiles)`는 순수 함수다. 씨앗이 곧 프로파일이라 별도 표를
만들면 썩는 사본이 생길 뿐이고, 개인 프로파일(B2)도 프로파일로 저장되므로
사용자의 답이 자동으로 색인에 흘러든다 — **출처가 하나다.**

- **계획은 팩에 두자고 했는데 core에 뒀다**: 유도는 `MappingProfile`의 구조를
  걷는 일이고(columnRoles가 판례) 코드에 마켓 문자열이 0이다. core에 있으면
  `analyzeImport`가 이미 받는 profiles로 색인을 만들 수 있어 새 매개변수가 없다.
- **`columnRoles`를 재사용하지 않는다** (실측): 그 함수는 역할을 병합해 한 헤더의
  두 번째 target을 잃는다. 실측 「구매금액」은 **네 뜻**이다 — esm 주문의
  `total_amount` · 같은 파일 품목의 `gross_amount` · 클레임 경로의 `amount` ·
  esm 광고의 `conversion_amount`. 이 넷이 곧 «전역 사전 금지»의 증거이고, 색인은
  선언을 직접 걸어 넷 다 든다.

### 판정 규칙 (`judgeColumns`)

- 이름의 뜻이 **하나뿐일 때만** 확정 후보가 되고, **값이 확정한다** (§20 2층):
  kind가 등록부의 기대와 어긋나면 후보로 강등, 표본이 없어도 후보다.
- 뜻이 여럿이면 후보 — 전부 들고 사람에게 간다.
- 근거는 %가 아니라 문장이다 (§20 규칙 2): *"esm/ad 양식이 spent_on(광고비가
  나간 날)로 쓴다 · 값도 date로 맞다"*.

### 한계 (정직하게)

- **문서 맥락(§20 3층)이 아직 없다**: 「날짜」는 esm 광고에서만 쓰여 유일이라
  확정되는데, 광고가 아닌 미지 파일의 「날짜」에도 `spent_on`을 제안하게 된다.
  문장이 출처(esm/ad)를 들고 다니고 v1이 주석 전용이라 사고는 안 나지만, 파일의
  docType 추정이 생기면 색인 조회를 그 범위로 좁혀야 한다.
- v1의 판정은 `analyzeImport` 결과의 주석일 뿐 **적재를 바꾸지 않는다.**

## 실측 (2026-08-19)

프로파일이 하나도 안 맞는 11번가 광고 픽스처(#2 · 27열):

```
4단: alias 4 · candidate 0 · unknown 23
확정: 날짜→spent_on · 노출수→impressions · 클릭수→clicks · 총비용→spend_amount
```

**「전부 아니면 전무」였던 파일이 열 4개만큼 알려진 파일이 됐다.** 나머지 23은
정직하게 unknown으로 세어진다.

## C — 항등식 증명기 (같은 날 · `validation/identity.ts`)

`proveIdentities` — 숫자 열들 사이의 합 `A = B + C`를 8행 선별 후 전량 검사.
뺄셈은 합 형태 하나로 전부 잡힌다(`net = gross − fee` ⇔ `gross = net + fee`).
표본은 **고른 시트에서만** `proofRows`(기본 200)행 — 전 시트 훑기에 물리지 않는다.

### 실측 — §20의 그 문장이 실물이 됐다

11번가 정산(#6 · 59열 · 128행):

```
「판매금액합계」 = 「정산금액」 + 「공제금액합계」 — 128행 중 128행 일치   ← 템플릿의 그 관계
「판매금액합계」 = 「판매가」 + 「옵션가」 — 128행 전부                      ← 진짜지만 템플릿 밖
「할인쿠폰이용료」 = 「판매자기본할인」 + 「판매자추가할인」 — 128행 전부
```

### ★ 우연 항등의 실물 — 실질성 가드 ★

11번가 광고 리포트(#2)에서 **거짓 항등 10건**이 나왔다 — 「총 전환수」=「클릭률」+
「직접 전환수」 따위. 클릭률(≤1)이 허용오차 ±1 안에 통째로 들어가 아무 합에나
붙은 것이다. 가드: 각 항과 결과가 검사 행 어딘가에서 **|값| > 허용오차**여야
한다. 가드 후 거짓 10 → 0, 진짜 3건은 그대로.

### 증명 → 이름: 세 모서리 규칙

템플릿(`net = gross − fee`)과 항등이 맞물릴 때, **세 모서리 중 둘이 별칭으로
확정돼 있고 하나가 미확정이면** 그 하나가 남은 자리의 target을 `identity`로
얻는다. 하나만 확정이면 못 올린다 — 합은 교환법칙이 있어 남은 두 자리를 항등이
못 가른다. 템플릿 밖 항등(위 판매가+옵션가)은 tier를 못 올린다 — 발견 원문은
`ImportAnalysis.identities`에 실려 화면 근거 칸의 재료가 된다.
