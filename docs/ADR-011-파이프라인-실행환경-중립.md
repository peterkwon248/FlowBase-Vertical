# ADR-011 — 파이프라인은 실행 환경에 중립이어야 한다

**상태**: 채택 (2026-08-13)
**관련**: [ADR-001](ADR-001-파이프라인-스택.md) · [ADR-008](ADR-008-드라이버-최종-확정.md) · 헌장 B-5

---

## 무엇이 드러났나

Tauri 셸이 뜬 뒤 **#13을 앱에서 처음 돌리자 파이프라인이 모듈 로드 단계에서 죽었다.**

```
Uncaught Error: Module "node:crypto" has been externalized for browser compatibility
  at /src/core/import/mapping/index.ts
```

전수 조사 결과 앱의 필수 경로를 막는 것이 둘이었다:

| 막는 것 | 어디 | 왜 필수 |
|---|---|---|
| `node:crypto` `createHash("sha1")` | `mapping/index.ts` — `contentKey()` | `source_key` 생성. 매핑 없이는 가져오기 자체가 불가 |
| `node:fs` `readdirSync`/`readFileSync` | `store/migrate.ts` | 마이그레이션 SQL 로딩. DB 초기화 불가 |

ADR-001은 "구현은 전부 TypeScript"라고 정했다. **그 문장이 "어디서든 돈다"를 뜻하지 않는다는 것이 이번에 드러났다.** TypeScript로 쓰였어도 `node:` 모듈에 손을 대는 순간 그 코드는 Node에 묶인다.

드러나지 않은 이유는 단순하다 — **테스트도 하네스도 전부 Node에서 돌았다.** 세션 1의 픽스처 하네스, 세션 2의 종단 게이트, 3b-0의 손익 CLI까지 전부. 앱이 없었으므로 앱에서만 나는 문제를 만날 자리가 없었다.

> 작업 리듬 7번("게이트는 선언된 질문만 답한다")의 두 번째 사례다. 273개 테스트와
> 성능·종단 게이트가 전부 녹색인 상태에서, **실제 앱에서 한 번 돌리자** 나왔다.

---

## 결정

**`src/core/`는 실행 환경에 중립이다. `node:` 모듈을 import하지 않는다.**

환경에 묶이는 것은 **어댑터로 분리**한다 — `driver.ts` / `driver-node.ts`가 이미 쓰던 모양 그대로다.

```
migrate.ts        계약 + 적용 로직 (멱등 판정 · 트랜잭션 경계 · 번호 중복 검사)
migrate-node.ts   디스크에서 읽기   ← 테스트 · 하네스
migrate-web.ts    번들에서 읽기     ← 앱
```

읽는 방법은 환경마다 다르되 **적용 규칙은 한 곳**이다. SQL 파일은 여전히 유일한 진실이고, 웹 쪽은 `import.meta.glob(…, { query: "?raw", eager: true })`로 **같은 파일을 같은 바이트로** 끌어온다.

해시는 어댑터로 가르지 않고 **순수 TypeScript 구현 하나로 통일**했다 (`mapping/sha1.ts`).

---

## 조건

### 조건 1 — `source_key` 값이 한 비트도 바뀌지 않는다

`contentKey()`가 만드는 값이 `source_key`가 되고, 그 값으로 UPSERT 멱등성이 성립한다 (헌장 2). 해시를 바꾸면 **같은 파일을 다시 가져올 때 다른 키가 생겨 중복 적재된다.**

그래서 표준 SHA-1을 그대로 구현했고, `tests/sha1.test.ts`가 `node:crypto`와 대조한다 — 빈 문자열·표준 벡터·패딩 경계 5종(55·56·63·64·65·119·120바이트)·한글·이모지·**무작위 200개**. 비교 대상이 다른 구현이라는 점이 요점이다 (ADR-007의 `equivalence`와 같은 발상).

### 조건 2 — 동기여야 한다

`crypto.subtle.digest`는 비동기다. `contentKey`는 청크 안에서 **행마다** 불리는 자리라 비동기로 바꾸면 매핑 루프 전체가 `await`로 물든다. 8만 행 × await는 구조도 성능도 손해다.

### 조건 3 — 회귀 없음

`npm test` 273개 전부 통과. 호출부 9곳(테스트 7 · 하네스 2)은 import 경로만 `migrate-node.js`로 바꿨고 시그니처는 그대로다.

## 기각한 대안

| 대안 | 왜 기각했나 |
|---|---|
| Web Crypto (`crypto.subtle`) | 비동기 — 조건 2 위반 |
| 다른 해시로 교체 (FNV·xxhash) | `source_key` 값이 바뀐다 — 조건 1 위반 |
| Node 폴리필 번들 (`crypto-browserify` 등) | 번들이 무거워지고, 근본은 "core가 Node에 묶여 있다"는 것이라 해결이 아니라 은폐다 |
| `migrate` SQL을 TS 문자열로 생성 | SQL 파일과 생성물 **두 벌**이 생긴다. 어긋나면 앱과 테스트가 다른 스키마를 쓴다 |

## 측정 — Tauri 스모크 (#13, 80,137행)

같은 픽스처를 두 경로로 돌렸다. **파싱·정규화·매핑은 같은 코드**이고 적재만 IPC를 탄다.

| | node:sqlite (`npm run e2e`) | Tauri IPC (스모크) |
|---|---|---|
| 적재 행 | 80,137 | 80,137 |
| SQL 되세기 | 80,137 | 80,137 (앱 안 · **밖에서도** 확인) |
| 광고비 합계 | 15,700,534원 | **15,700,534원** |
| 매핑 오류 | 0 | 0 |
| 파싱+정규화 | 190ms | 171ms |
| 매핑+적재 | 4,953ms | 9,332ms · 10,188ms (2회) |
| 합계 | **5.5초** | **9.5초 · 10.4초** |

**IPC 배율 ≈ 1.9배** (적재 구간). 30초 예산의 32~35%라 여유가 크다. 청크당 1회 왕복(`db_run_many`)이 없었다면 8만 번의 왕복이었을 것이고, 그 설계가 이 숫자를 만든다 (ADR-008).

광고비 합계가 원 단위까지 같다는 것이 두 경로가 **같은 답을 낸다**는 증거다.

### 메모리 — 서프라이즈 없음

|  | node:sqlite | Tauri IPC |
|---|---|---|
| 측정 대상 | Node 프로세스 RSS | app.exe **프로세스 트리 7개** 합계 |
| 베이스라인 | — | 443.2MB (WebView2 엔진 자체) |
| **증가분** | **+227.7MB** | **+193.7MB** |
| JS 힙 피크 | — | 74~86MB |

**IPC로 넘겨도 메모리가 늘지 않았다.** 오히려 증가분이 적은데, SQLite 페이지 캐시(32MB)와 적재 버퍼가 Rust 쪽에 있어 JS 힙이 가볍기 때문이다. 청크를 JSON으로 굴리는 비용이 피크를 밀어올릴 것이라는 게 이 측정의 가설이었고, **기각됐다.**

> **256MB 기준을 웹뷰에 그대로 들이대지 않는다.** 그 숫자는 "Worker 피크 RSS"
> 기준이었고(ADR-001 조건 4-a), 웹뷰는 실행 모델이 다르다 — 443MB 베이스라인은
> Chromium 엔진의 고정 비용이지 파이프라인이 쓴 것이 아니다. 비교 가능한 것은
> **증가분**이고, 그것이 Node보다 작다는 것이 이번 판정이다.
>
> 측정 방법도 한 번 틀렸다. 처음에 `msedgewebview2.exe`를 이름으로 잡았는데
> 그건 **다른 앱들도 쓰는 전역 프로세스명**이라 베이스라인이 952MB로 나왔다.
> `app.exe`의 자식 트리만 골라야 우리 것이 된다.
>
> dev 모드 측정이라 HMR·소스맵이 포함돼 있다. 릴리스 빌드에서 다시 재는 것은
> 3b 이후의 일이다.

## 재검토 트리거

1. **`src/core/`에 `node:` import가 다시 생기면** — `tests/sha1.test.ts`가 매핑 경로를 지키지만 core 전체를 훑지는 않는다. 범위를 넓히는 것을 검토한다
2. **파일이 #13보다 크게 늘면** — IPC 배율은 행 수에 비례한다. 30초 예산에서 여유가 얇아지면 청크 크기(현재 1,000)를 재본다
3. **`crypto.subtle`이 동기 API를 얻으면** — 그럴 일은 없어 보이지만, 그때는 표준 구현으로 돌아가는 것이 유지보수에 낫다
4. **마이그레이션이 수십 개로 늘면** — 번들에 전부 싣는 지금 방식의 크기를 다시 본다 (현재 3개 · 36KB)
