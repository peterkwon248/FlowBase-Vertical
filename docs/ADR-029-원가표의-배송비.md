# ADR-029 — 원가표의 «배송비»를 어디에 넣나

날짜: 2026-08-21 · 상태: **결정** — 사용자 확인 받음 (2026-08-21)
관련: [ADR-005](ADR-005-기준데이터-이력-범위.md) · [ADR-009](ADR-009-회계-정책.md) · [ADR-016](ADR-016-원가-대기-스테이징.md) · [ADR-023](ADR-023-통-묶음-자격-입구순서.md) · [코드-남은일 3.10](코드-남은일-2026-08-20.md) · LOCK 6 · CLAUDE.md 「손익 3층」

## 문제 — 018이 이것을 화면에 띄웠다

[ADR-028](ADR-028-장부의-출처-칸과-표-뷰어-자리.md)의 표 뷰어가 원가 파일의 원본 표를
열어 주면서, 사용자가 **자기가 넣은 열을 눈으로 보게 됐다**:

```
상품번호 · 상품명 · 모델명 · 원가 · 배송비 · 카테고리 · Model
                              ↑ 받는다   ↑ 버린다
```

`cost-master@1.json`의 `unmappedColumns`가 「`배송비`는 … 아직 자리가 없다」고 적어
뒀는데, 이제 그 «자리 없음»이 **화면에서 보인다.** 넣은 사람 입장에서는 파일에 있는
숫자를 앱이 못 본 척하는 것이다.

## 실측 (2026-08-21 · `public/demo.sqlite` · 017 `sheet_block`에서 꺼냄)

★ **표 보관층(016·017)이 없었으면 이 실측을 못 했다** ★ 원본 표를 안 들고 있으면
「배송비 열에 무슨 값이 있나」를 다시 파싱해야 알 수 있다.

```
① 정산이 말하는 배송비 — 손익이 «지금» 빼는 값
   conn-11st  128행 · shipping_amount 합 = 0 · 수수료합 1,130,702 · 판매금액합 4,969,100
     ↑ 0이다. 2.13이 이미 찾은 사실과 같다 — 11번가 정산 파일은 배송비를 안 준다

② 원가표가 들고 온 「배송비」
   2026-01 통합 매출 대시보드.xlsx · 253행
   값 있는 행 223 · 합 446,000 · **서로 다른 값이 «2000» 하나뿐**
   배송비 0인 행 30 · (대조) 원가 있는 행 206 · 원가합 4,480,200
```

**두 숫자는 다른 사건이다:**

| | 무엇 | 출처 | 오늘 값 |
|---|---|---|---|
| `fact_settlement.shipping_amount` | **마켓이 정산에서 공제한** 배송비 | 정산 파일 | 0 |
| 원가표의 `배송비` | **내가 택배사에 낸** SKU당 출고비 | 사람이 정리한 표 | 2,000/SKU |

## 결정

### 결정 1 — 「배송」 줄에 **합산**한다. 3층 정의를 안 건드린다

`CLAUDE.md`의 3층 정의가 이미 그 자리를 갖고 있다:

```
매출 − 할인·수수료·VAT·배송 − 매입원가 − 직접 광고비 − 운영비 = 상품 기여이익
                        ↑ 여기
```

**새 줄을 만들지 않는다.** 「물류비」를 3층의 독립 항목으로 올리면 정의·화면·시험·
문서가 함께 움직이는데, 얻는 것은 이름 하나다. 두 값은 **같은 성격의 지출**(상품을
사는 값이 아니라 **보내는 값**)이라 한 줄에 앉는 것이 맞다.

★ **이중 계상이 아니다** ★ 마켓이 공제한 배송비와 내가 택배사에 낸 배송비는 **다른
돈**이다. 둘 다 나가는 돈이므로 합이 맞다. 오늘 실측에서 전자가 0이라 겹칠 여지조차
없지만, **0이라서 안전한 것이 아니라 사건이 달라서 안전하다** — 전자가 0이 아닌 날에도
같은 판단이 선다.

### 결정 2 — 화면은 **출처 둘을 갈라 보인다** (LOCK 6)

합쳐서 빼되 **합쳐서 말하지 않는다.** 「배송비 446,000원」만 뜨면 사용자는 그것이
정산에서 온 것인지 자기 원가표에서 온 것인지 모르고, 틀렸을 때 어느 파일을 고쳐야
할지도 모른다.

```
배송      446,000원
          정산 공제 0원 · 원가표 446,000원
```

### 결정 3 — 프로파일이 금액 열을 **여럿** 선언할 수 있다

`reference`가 `amountColumn` + `kind` **한 쌍**만 받는다. 두 번째 쌍을 **선택 항목**으로
더한다 — 기존 프로파일은 한 글자도 안 고쳐도 그대로 돈다.

```jsonc
"reference": {
  "amountColumn": "원가",  "kind": "COGS",
  "extraAmounts": [ { "column": "배송비", "kind": "LOGISTICS" } ]   // ← 신설
}
```

★ **`amounts: [...]`로 통일하지 않는다** ★ 더 깔끔해 보이지만 **기존 프로파일 전부와
그것을 읽는 코드·시험이 함께 움직인다.** 얻는 것은 대칭성 하나다. 「한 파일에서 한
종류만 넣는다」를 「한 종류 + 곁가지」로 여는 것이 지금 필요한 전부다.

### 결정 4 — 스키마는 **안 바꾼다**

`cost_history.kind`가 001부터 `CHECK (kind IN ('COGS','PACKAGING','LOGISTICS','OTHER'))`
이고 UNIQUE가 `(library_id, sku_id, kind, effective_from)`다. **한 SKU가 같은 날짜에
COGS와 LOGISTICS를 동시에 가질 수 있다.** 마이그레이션이 필요 없다.

> 첫 스키마가 이미 이 모양이었다는 것이 요점이다 — 3.10은 «스키마에 자리가 없다»가
> 아니라 **«가져오기가 한 종류만 넣는다»**였다. 남은일 문서의 표현이 그 점에서 낡았다.

## 버린 길

### ✗ 매입원가(COGS)에 합산한다

가장 짧다 — 수량 × 단가 계산이 똑같아서 코드 한 줄이면 된다. 버린다: **「매입」이
아닌 것이 매입원가에 섞인다.** 상품별 손익에서 「매입원가 16,500원」을 보고 매입처에
따지러 가면 2,000원은 거기 없다. `kind`를 넷으로 가른 001의 설계도 그걸 막으려던 것이다.

### ✗ 담기만 하고 손익은 나중에

적재만 하면 **화면에 아무 변화가 없다.** 손익 3층은 `kind = 'COGS'`만 소비하므로
(`snapshot.ts:540` · `rows.ts:42` · `product/rows.ts:170` 전부 리터럴) LOGISTICS 행은
쌓이기만 하고 한 푼도 안 움직인다. 「다음 손은 보이는 것부터」(작업 리듬 ④)에 어긋나고,
더 나쁘게는 **기능이 된 것처럼 보이는 무동작**이 된다.

## 따름 조건

1. **정산 배송비를 대체하지 않는다** — 더한다. 둘 중 하나를 고르는 코드가 나오면 위반
2. **화면은 출처를 가른다** (결정 2). 합계만 그리면 LOCK 6 위반
3. **`kind`별 단가는 `costAt`을 그대로 쓴다** — 원가와 같은 이력 규칙(ADR-005)이다.
   적용일이 다르면 새 이력이고, 과거는 남는다
4. **배송비가 없는 원가표가 정상이다** — `extraAmounts`가 없거나 열이 비면 조용히
   COGS만 넣는다. 없는 것을 결핍으로 부르지 않는다 (§22)
