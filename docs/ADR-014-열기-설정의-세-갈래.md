# ADR-014 — 열기 설정의 세 갈래: 파일에 남는 것 · 연결에만 사는 것 · 안 거는 것

상태: **확정** (2026-08-16)
관련: [ADR-003](ADR-003-sqlite-바인딩.md) (PRAGMA 목록의 출처) · [ADR-008](ADR-008-드라이버-최종-확정.md) (드라이버 계약) · [ADR-004](ADR-004-되돌리기-의미론.md) (FK 전제)

## 맥락 — 목록 하나가 성질이 다른 셋을 섞고 있었다

`PRAGMAS` 배열 하나에 다섯 줄이 있었고, 드라이버는 `pragmas: true/false`로 **전부
걸거나 하나도 안 걸거나** 둘 중 하나였다. 그 안에 성질이 전혀 다른 것들이 있었다:

| 줄 | 성질 |
|---|---|
| `journal_mode = WAL` | **DB 파일에 남는다.** 연결을 닫아도 안 돌아온다 |
| `synchronous = NORMAL` | 연결 설정이지만 **근거가 WAL을 전제한다** |
| `foreign_keys` · `temp_store` · `cache_size` | 연결에만 산다. 닫으면 사라진다 |

## 이 결정을 부른 사고 (2026-08-16)

재가져오기 도구가 개발용 DB를 **기본 옵션으로 열었을 뿐인데** `journal_mode = WAL`이
`.tmp/pnl.sqlite`를 `delete` → `wal`로 영구히 바꿨다. 앱은 늘 `pragmas: false`로
열어 왔으므로 그 DB는 계속 롤백 모드였다. 그리고 이 저장소는 **OneDrive 폴더**
안이라 WAL이 요구하는 `-shm`이 열리지 않는다 — 앱의 조회가 전부 실패했고,
사용자에게는 **「방금 연결한 것이 다 사라졌다」**로 보였다.

> **읽으러 간 도구가 쓰고 온다.** 기본값이 남의 세계를 바꾸면, 그건 옵션이 아니라 함정이다.

## 결정

### 1. 목록을 둘로 가른다

```
FILE_PRAGMAS     journal_mode = WAL · synchronous = NORMAL
SESSION_PRAGMAS  busy_timeout · foreign_keys · temp_store · cache_size
```

### 2. 기본값은 **세션만**이다. 파일 성질은 이름을 불러야 걸린다

```ts
openNodeDriver(path)                    // 세션만 — 남의 파일을 안 바꾼다
openNodeDriver(path, { journal: true }) // 파일 성질까지 — 내가 만든 DB에만
```

오늘 `journal: true`를 쓰는 곳은 **`tools/harness/e2e-worker.ts` 하나**다. 그 DB는
그 게이트가 만들고 그 게이트만 쓴다.

### 3. `synchronous = NORMAL`은 WAL과 한 묶음이다 — **정정**

원래 근거가 *"WAL에서 NORMAL은 프로세스 크래시에 안전하고 OS 크래시에서만 마지막
트랜잭션을 잃는다"*였다. **그 문장은 WAL을 전제한다.** 롤백 저널 모드에서 NORMAL은
저널이 동기화되기 전에 본체를 고칠 수 있어 전원이 끊기면 **파일이 깨질 수 있다** —
잃는 것의 크기가 다르다.

앱은 롤백 모드로 도므로 이 완화를 걸지 않는다. 대량 적재가 느려지는 대가가 있지만
지금까지도 그 상태였고(앱이 PRAGMA를 아예 안 걸었다), **속도는 나중에 살 수 있어도
깨진 파일은 못 산다.**

### 4. `busy_timeout = 5000`을 세션에 넣는다 (신규)

기본값은 **0** — 다른 연결이 잠그고 있으면 기다리지 않고 즉시 `database is locked`다.
근거는 추정이 아니라 실측이다: 하네스가 그것으로 한 번 빨개졌고(세 워커가 같은
파일, 5회 중 1회), 앱도 같은 노출을 갖고 있었다(사용자가 앱을 켜 둔 채 CLI를 돌리는
경우). 5초를 넘으면 **여전히 실패하고**, 그 실패는 이제 화면이 말한다.

### 5. 앱이 세션 PRAGMA를 건다 — `foreign_keys`가 꺼진 채 돌고 있었다

`data.ts`의 네 호출부가 전부 `pragmas: false`였고 **왜 껐는지 기록이 없다**(git 이력
확인). 그 상태에서 앱은 외래키 강제가 **꺼진 채** 돌았다. 이것이 왜 중한가 —

> 되돌리기의 삭제 순서 방어(`DELETE_ORDER`)는 「FK가 켜져 있으면 부모를 자식보다
> 먼저 못 지운다」를 전제로 잡은 것이다. **앱에서는 그 전제가 서 있지 않았다.**
> 테스트 세계(FK 켜짐)와 앱 세계(꺼짐)의 비대칭이 DB 설정 층에서 재발한 것이고,
> 이 계보(하네스 세계 ≠ 사용자 세계)의 **가장 낮은 층**이다.

**켜기 전에 쟀다** — `PRAGMA foreign_key_check`:

```
.tmp/pnl.sqlite                  FK 위반 0건
.tmp/pnl-backup-2026-08-16.sqlite FK 위반 0건
```

기존 데이터가 터지지 않으므로 켠다. `journal_mode`는 여전히 안 건다.

## 실측 (결정 뒤)

```
npm test   670/670 통과
npm run e2e  6.3초 / 30초 · 249.4MB / 256MB   (관측 폭 195.2~254.3 안)
```

e2e가 변하지 않은 이유는 그 워커만 `journal: true`라 WAL+NORMAL을 그대로 쓰기
때문이다 — **바뀐 것은 «누가 무엇을 거는가»이지 «무엇이 걸리는가»가 아니다.**

## 재검토 트리거

1. **앱에서 FK 위반이 실제로 터진다** → 데이터를 고칠지 제약을 고칠지 판정한다.
   끄는 것으로 돌아가지 않는다 — 껐다는 사실이 기록되지 않은 것이 이번 사고의 절반이다
2. 개발용 DB가 OneDrive 밖으로 나간다 → 앱에서 WAL을 켤 수 있는지 다시 잰다
   (켜면 적재 중 조회가 살아나고 `synchronous = NORMAL`도 함께 온다)
3. `busy_timeout` 5초를 넘는 실패가 관측된다 → 값이 아니라 **누가 그렇게 오래
   잠그는지**를 먼저 본다
4. 세션 PRAGMA가 늘어난다 → 그 줄이 정말 연결에만 사는지 확인하고 넣는다.
   판단이 안 서면 파일 쪽으로 분류한다 (틀렸을 때 손해가 작은 쪽)
