# ADR-007 — 정규화된 청크의 표현: columnar

날짜: 2026-08-12 · 상태: 확정 · 관련: [ADR-001](ADR-001-파이프라인-스택.md) · [ADR-003](ADR-003-sqlite-바인딩.md)

## 결정

`NormalizedChunk`를 **행 배열이 아니라 columnar 평면 배열**로 만든다.

```
이전   rows: (readonly NormalizedValue[])[]      // 행마다 배열, 셀마다 {kind, value, raw}
이후   kinds:  Uint8Array                        // KIND_* 코드
       values: (string | number | null)[]        // 인덱스는 r * width + c
       raws:   RawCell[]
```

청크당 할당이 **셀 수와 무관하게 3개**가 된다. #13(80,137행 × 43열)에서 셀당 객체
하나는 344만 개였다. 동시 생존은 청크 하나뿐이지만 RSS는 **할당 총량**을 따라간다.

## 왜 columnar인가 — 절충안을 고르지 않은 이유

"더 작은 객체"로 바꾸는 절충(예: `raw`를 빼서 2필드로)은 할당 **수**를 그대로 둔다.
344만 개가 344만 개로 남는다. 줄어드는 것은 개당 크기뿐이고, 그 폭은 측정 노이즈
안에서 판정 불능이 된다. 이왕 표현을 바꿀 거면 노이즈 밖으로 확실히 나가는 폭이어야
한다 — 그게 `행×컬럼 → 3`이다.

## 왜 여전히 평범한 데이터인가

메서드를 달지 않았다. `NormalizedChunk`는 `RowChunk`와 같은 **직렬화 경계**이고
(ADR-001: 단계 간에는 직렬화 가능한 값만), 메서드가 붙으면 구조화 복제가 깨져
Rust 포팅 시 IPC를 못 탄다. 접근은 `normalization/chunk.ts`의 자유 함수로 한다.

columnar는 오히려 그 경계에 **더 맞는다** — `Uint8Array`는 전송 가능(transferable)이고,
컬럼별 배열은 Rust 쪽에서 그대로 슬라이스로 받는 모양이다.

## `raw` 보존 — 소비자를 먼저 목록화했다

평탄화 중 `raw`를 버리고 싶은 유혹이 있어서, **먼저 누가 읽는지 세었다.**

| 소비자 | 위치 | 상태 |
|---|---|---|
| `coerce()` — number/percent 재해석 | `mapping/index.ts` | **유일한 프로덕션 소비자.** 살아 있다 |
| `raw` 보존 테스트 | `tests/normalization.test.ts` | 통과 |

### 전제 정정 세 건

작업 지시는 `batch_exclusion`의 detail · 오류 행 내려받기 · §18-4가 `raw`에
의존한다고 봤다. 실측에서 **셋 다 아니었다**:

1. **`batch_exclusion.detail`은 `NormalizedValue`를 거치지 않는다.** detail 문자열은
   `pipeline.ts`가 **정규화 이전**, `RawRow` 수준에서 조립한다("헤더(3행) 위의
   제목·설명 행", "합계 행", "빈 행"). 저장되는 것은
   `(batch_id, row_index, reason, detail)`뿐이고 `raw`는 DB에 아예 안 들어간다
2. **오류 행 내려받기는 아직 없다.** 매핑 오류는 `{rowIndex, field, reason}`이고
   `raw`를 담지 않는다
3. **§18-D(되돌리기 불가 사유)는 `row_shadow.prev_batch_id` 기반**이다. `raw`와 무관하다

그래도 `raw`는 **평면 배열로 그대로 보존한다.** 이유는 셋:
`coerce()`가 지금 쓰고 있고, 조정 레이어(헌장 B-3)가 "원본 + 조정"을 계산하려면
필요하며, 파서가 이미 만들어 둔 값을 **참조만** 하므로 포인터 한 칸 값이 전부다.
지연 로드로 미룰 만큼 비싸지 않다.

## 정합성이 먼저다 — 속도는 그다음에 취했다

표현이 바뀌는 리팩터링에서 1번 증명 대상은 "같은 답"이다.
`tools/harness/equivalence.ts`를 **먼저** 만들고 기준선을 뜬 뒤에 코드를 고쳤다.

해시 대상 3종:

- **cells** — 15개 픽스처 · 전 시트 · 전 셀의 `(kind, value, raw)` 3튜플 (452만 셀)
- **summary** — 헤더·컬럼 종류·데이터 행 수·제외 행(사유·detail 문자열까지)
- **mapped** — #13을 쿠팡 프로파일로 매핑한 결과. **실제로 적재되는 행 그 자체**

결과: 전부 동일. #13 매핑 해시 `b1187f70e5758592` 불변.

**가드를 부러뜨려 확인했다** (헌장 G-1). `hint === "text"` 분기의 kind를 하나 바꾸니
픽스처 6개의 cells 해시가 전부 깨졌고, 매핑 행 인덱스를 1칸 밀자 #13 mapped 해시가
깨졌다. 잡지 못하는 가드가 아니다.

### 원칙 — 파괴 시험의 "안 깨짐"도 해석해야 한다

처음 시도한 파괴(마지막 text 폴백)는 **아무것도 깨뜨리지 못했다.** 컬럼 추론이
힌트를 주므로 그 폴백에 닿는 셀이 픽스처에 없었기 때문이다.

> **가드를 부러뜨렸는데 안 깨지면 결론은 둘 중 하나다 — 가드가 무르거나, 그 코드
> 경로가 애초에 안 쓰이거나. 어느 쪽인지 가리기 전에는 둘 다 모르는 것이다.**

전자면 가드를 고치고, 후자면 그 경로가 죽은 코드인지 픽스처가 부족한 건지 묻는다.
"안 깨졌으니 괜찮다"로 넘기면 두 경우 모두 놓친다.

#### ★ 재림 — 테스트가 «깨끗한 세계»를 세우면 그 안에서는 두 답이 같다 (2026-08-14) ★

같은 함정이 정확히 반대 방향으로 다시 나왔다. 품목 적재의 `qtyWithoutCost`가
미연결 품목까지 세어 **최대 2,041배** 부풀었는데, 그 자리를 겨냥한 테스트가 있었는데도
녹색이었다:

```js
expect(snap.cogsBasis.itemsWithoutLink).toBe(0)   // ← 이 줄이 결함을 가렸다
expect(snap.cogsBasis.qtyWithoutCost).toBe(3)
```

**미연결이 0인 세계에서는 두 SQL이 같은 답을 낸다.** 테스트가 세운 픽스처가 너무
깨끗해서, 두 식이 갈리는 유일한 축(미연결 존재 여부)이 상수로 눌려 있었다.

> 위 원칙의 짝이다. 저기서는 «부러뜨렸는데 안 깨진 것»을 해석하라고 했고,
> 여기서는 **«세운 세계가 그 질문을 물을 수 있는 세계인가»**를 묻는다.
> 둘 다 «녹색의 뜻»을 해석하라는 같은 요구다.

**적용 규칙**: 두 값이 «같아야 한다»가 아니라 «다를 수 있다»를 시험하려면, 그 둘을
**가르는 축이 픽스처 안에서 실제로 변해야** 한다. 축을 0으로 고정한 단언이 같은
테스트에 있으면 그 테스트는 자기가 묻는 질문을 스스로 지운다.

#### ★ 처방 — 픽스처가 도달 못 하는 세계는 **테스트가 합성으로 만든다** (2026-08-15) ★

위 두 절은 함정을 진단할 뿐 처방이 없었고, 그 공백의 기본값은 **«더 좋은 픽스처를
기다린다»**였다. 기다림은 처방이 아니다 — 실파일이 그 세계를 영영 안 줄 수도 있다.

> **픽스처가 도달 못 하는 세계는 테스트가 합성으로 만든다 —
> 단 합성임을 테스트 이름에 명시한다.**

주문 화면 통합에서 처음 적용했다. 통합 행의 금액 열은 **판매액**을 찍으므로 전액
취소가 아니면 클레임 금액이 통합과 함께 사라지는데, ESM 픽스처는 9건 **전부 전액
취소**다 — 부분 취소라는 축이 상수 0으로 눌려 있어 **픽스처만으로는 영영 안 잡힌다.**
그래서 세계를 일부러 더럽혔다:

```js
// 한 건만 부분 환불로 바꾼다 — 나머지 8건은 전액 그대로다
UPDATE fact_claim SET amount = 1000 WHERE source_key = (…)
```

**«단 명시한다»가 규칙의 절반이다.** 합성은 픽스처의 권위를 빌리지 않는다 — 실파일이
그렇게 생겼다는 증거가 아니라 «이런 파일이 오면»이라는 가정이다. 이름에 안 적으면
다음 사람이 그 수를 정답지로 읽고, 언젠가 실파일과 대조하다 없는 사고를 좇는다.
`tests/order-rows.test.ts`의 «부분 취소 — 통합해도 금액을 잃지 않는다»가 그 표기다.

경계: **정답지는 합성하지 않는다.** 손으로 검산한 수는 실파일의 성질이므로 픽스처에서
짓는다(같은 파일의 «ESM 정답지» 절). 합성이 답하는 것은 «분기가 살아 있는가»이지
«얼마인가»가 아니다.

## 측정

12회 연속, `npm run e2e` (#13, 80,137행 적재까지):

```
195.2 · 211.2 · 217.4 · 228.9 · 230 · 235.3 · 237 · 238.2 · 242.6 · 243 · 248.5 · 249.7
중앙값 236.2 · 최대 249.7 / 256MB          12회 전부 통과
시간 4.9~5.0초 / 30초
행 수 적재 80,137 = 데이터 80,137 = 되세기 80,137
```

개정 전 4회는 `233 · 244.8 · 249 · 267.3`으로 4회 중 1회 초과였다.

단계별:

```
파싱만                  ~205MB
+ 정규화 + 매핑         ~207-218MB   (평탄화 이전에는 245MB)
+ SQLite 적재           ~246MB
```

**정규화+매핑의 몫이 사실상 0이 됐다.** 이 ADR이 노린 것은 그것이고 그것은 됐다.

## 정직하게 — 이 결과의 한계

기준은 충족했지만 **여유가 6.3MB(2.5%)뿐이고, 관측 폭이 54MB(195~250)다.**
13번째 회차가 256을 넘을 가능성을 배제할 수 없다.

그리고 벽이 옮겨갔다: **이제 파서 혼자 205MB로 예산의 80%다.** 정규화를 0으로 만들어도
파싱이 205MB면 적재 28MB를 얹는 순간 233MB이고, 남는 폭이 23MB다.
ADR-003이 "JS 파이프라인 232MB"라고 묶어 부른 것의 대부분은 **파싱이었다.**

## 재검토 트리거

1. 종단 재측정에서 256MB 초과 회차 발생 → **파서**를 본다. 정규화가 아니다
2. 파서 축소로도 여유가 안 나옴 → Extraction만 Rust 포팅 (ADR-001 조건 1의 단계별 교체)
3. 청크가 IPC나 디스크로 나감 → `KIND_*` 코드 표가 계약이 된다. 끝에만 추가한다
4. `raw` 소비자가 늘어남 → 위 목록을 갱신한다. 지연 로드는 그때 검토해도 늦지 않다
5. 컬럼 폭이 청크마다 달라지는 파일 등장 → 지금은 폭 초과 시 청크를 끊고 넓힌다
   (15개 픽스처에는 없음을 실측). 잦아지면 폭 고정 전략을 재설계한다
